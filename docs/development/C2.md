# C2 · Review Room — comments, threads and the corpus admin

**Branch:** `stage-c2-comments`
**Needs:** C1 (the frozen block list is what makes an anchor possible), C0 (the mail seam — but see §6, two of its templates were never written).
**Blocks:** nothing. This closes track C.
**Shape:** medium. Two models, one genuinely hard UI problem (turning a selection into a durable anchor), and one permission rule that is an ownership edge wearing a capability's clothes.
**Spec:** `root-sot/ecosystem/working/root-website-review-room.md` §3.3; build plan §5b C2.

**Acceptance:** an invited reviewer selects a passage in a frozen document, opens a thread on it, and Root replies in-thread and resolves it. A second reviewer on the same document sees **none** of that. Cutting a new round leaves both threads attached to the round they were written against.

---

## 1 · The anchor — the decision this stage turns on

Spec §3.3: *"A comment anchors to a character range in one snapshot."* C1 stored each block's **markdown source**. A reviewer selects text in **rendered HTML**. Those are different strings, and choosing which one the offsets count into is the whole design.

**Anchor to the block's rendered plain text, not its markdown source.**

| | Source offsets | **Rendered-text offsets** |
|---|---|---|
| Getting them from a DOM selection | inverse-map through `marked`, which emits no source positions | walk text nodes and sum lengths |
| Re-applying them on render | same problem again | walk text nodes again |
| Survives a renderer upgrade | yes | **no — see §1.1** |
| Offsets mean what the reviewer selected | no (`**bold**` counts its asterisks) | yes |

C1 already paid for the precondition: `marked` and `dompurify` are pinned to exact versions *specifically* so a frozen round does not shift on a dependency bump, and the blocks themselves never change. Within that, rendered text is stable — and it is the string the reviewer actually pointed at.

### 1.1 · Store the quote, and verify it — this is what makes the choice safe

The one real risk is a dependency bump silently shifting offsets. Make it loud:

```prisma
quote String   // exactly the text the reviewer selected
```

On render, check `renderedPlainText.slice(start, end) === quote`.

- **Match** → highlight the range.
- **Mismatch** → the thread is **detached**. Show it in the margin with its quote, unhighlighted, labelled as no longer locatable.

A detached comment is honest. A comment highlighting the *wrong* words is worse than one highlighting nothing, because a reviewer will read the highlight and not the quote. **Never fall back to a fuzzy re-find** — best-effort re-anchoring is how a comment silently comes to be about a different sentence.

### 1.2 · Offsets are within one block, never the document

`(blockId, start, end)`, not a global offset. That is why C1 split into blocks at publish and gave each a stable id. A global offset would make every anchor depend on every block before it.

## 2 · Schema

```prisma
model ReviewThread {
  id         String @id @default(cuid())
  documentId String
  document   ReviewDocument @relation(fields: [documentId], references: [id], onDelete: Cascade)

  /// The reviewer who opened it. This is the ownership edge that keeps
  /// parallel review parallel — see §3.
  authorId String
  author   User   @relation("ThreadAuthor", fields: [authorId], references: [id])

  blockId     String
  startOffset Int
  endOffset   Int
  /// The anchor's own witness (§1.1).
  quote       String

  resolvedAt   DateTime?
  resolvedById String?
  resolvedBy   User?     @relation("ThreadResolver", fields: [resolvedById], references: [id])

  createdAt DateTime @default(now())
  comments  ReviewComment[]

  @@index([documentId, authorId])
}

model ReviewComment {
  id       String @id @default(cuid())
  threadId String
  thread   ReviewThread @relation(fields: [threadId], references: [id], onDelete: Cascade)
  authorId String
  author   User   @relation(fields: [authorId], references: [id])
  body     String
  createdAt DateTime @default(now())

  @@index([threadId, createdAt])
}
```

**A CHECK worth hand-writing:** `startOffset >= 0 AND endOffset > startOffset`. A zero-width or inverted range is not a passage, and it will otherwise be created by an off-by-one in the selection code and then rendered as an invisible highlight nobody can find.

## 3 · "Reviewers do not see each other's comments" is an ownership edge

This is the rule most likely to be built as a capability and be wrong. It is not one.

- **Capability** — `review.participate` — decides *may you use the Review Room at all*.
- **Ownership** — `thread.authorId === me.id` — decides *which threads you see through it*.

Exactly house rule 2, and the same shape as `loadForActor` for contracts. Write the thread filter as one function beside the queries:

```ts
/** Root sees every thread; a reviewer sees only their own. Parallel
 *  independent review — one expert's read must not anchor another's
 *  (spec §3.3). */
const threadsVisibleTo = (user: User) =>
  can(user, 'review.admin') ? {} : { authorId: user.id };
```

**The unit of visibility is the thread, not the comment.** Root's reply lives inside a reviewer's thread and that reviewer must see it; a *different* reviewer must see neither. Filtering comments individually gets this wrong in both directions.

**Do not leak existence.** A reviewer must not see that a passage has *someone's* thread on it — no highlight, no count, no marker. The spec's reason is that one expert's read should not anchor another's, and a marker saying "somebody commented here" anchors it just as well as the words would.

## 4 · Threads and rounds

Spec §3.3: when a new round is cut, threads **stay attached to the round they were written against**, labelled, rather than re-anchored or dropped.

That is already structural — `ReviewThread.documentId` → `ReviewDocument.roundId`. Nothing to build except the **label**: when reading a round that is not the newest, say so, and link to the current one.

**Do not build cross-round thread migration.** It is the "fuzzy re-find" of §1.1 at document scale, and the spec ruled it out. A thread is about the text it was written against; that text still exists, frozen, and that is the whole reason C1 was expensive.

## 5 · The corpus admin

Build plan §5b: *"the allowlist manifest, which sha the current round came from, reviewer invite (through C0) and revoke."*

Most of this is **read-only display**, because the manifest lives in `root-sot` and the round is frozen: which sha, which paths, when published, by whom. C1 already stores all of it.

**Reviewer invite is the one real piece, and it does not exist yet.** `inviteCustomer` (`resolvers/admin.ts:89`) is guarded by `customers.manage`, creates a `CUSTOMER`, and takes no roles argument. A reviewer invite needs its own mutation:

- Guarded by **`review.admin`**, not `customers.manage` — inviting a specialist to read a corpus is not account administration, and F3 kept those apart deliberately.
- Creates a user with `roles: ['REVIEWER']`.
- Reuses the existing invite-token machinery; only the template and the role differ.

**Revoke removes the role, and keeps the comments.** A reviewer's threads are Root's record of the review — deleting them on revoke destroys the thing the feature exists to produce. Drop `REVIEWER` from `roles`; leave everything they wrote. (Note the empty-roles CHECK from F3: a user whose only role was `REVIEWER` cannot be left with none. Either they keep a role or the row needs a different disposition — decide this explicitly, it is a constraint violation waiting in the revoke path.)

## 6 · C0 built two templates, not five

Build plan §5b C0 promises *"bilingual templates in the recipient's own locale for invite, reset, **reviewer-invite, new-comment** and contract-revised."* `lib/mailTemplates.ts` has **invite and reset**. Its own header says so honestly — *"the two mail flows that exist today"* — but the build plan does not.

So C2 writes two of the three missing ones:

- **reviewer-invite** — §5.
- **new-comment** — Root gets one when a reviewer opens a thread; the reviewer gets one when Root replies in theirs. **Never notify a reviewer about another reviewer's thread** (§3) — the notification is a side channel around the visibility rule, and it is the likeliest way to break it.

Both need entries in the key-parity test that already covers the existing pair.

**Digest, not per-comment, if a round gets busy.** Not required now; worth not painting out. A reviewer working through a document generates a burst, and one email per passage is how a specialist mutes the address.

## 7 · Traps

**T1 · The selection API is the fiddly part, and it is worth isolating.** Turning a `Range` into `(blockId, start, end)` and back is pure logic over a DOM subtree. Put it in `lib/anchor.ts` with its own tests over a constructed fragment, not inside a component. It is the single most bug-prone thing in the stage and the easiest to test once separated.

**T2 · Selections that cross blocks must be refused, not truncated.** A reviewer dragging across two paragraphs has no valid anchor. Refuse with a plain message; do not silently anchor to the first block, which produces a highlight that does not match what they selected.

**T3 · `dir` and selection offsets.** Offsets are logical (character index), not visual, so RTL is unaffected — but *verify* it rather than assuming, on a Persian block with mixed Latin words in it. That is the case where a visual assumption would have crept in.

**T4 · A resolved thread is not a deleted one.** It collapses; it stays readable; its anchor still highlights on demand. Resolution is a state, not a hide.

**T5 · The Review Room is the most externally-reachable surface in the app.** Every mutation here is callable by someone Root met once. Guard each one on the server; the section nav is cosmetic.

**T6 · Rate limiting still does not exist.** R2 recorded this for the public reader and deferred it. C2 adds authenticated writes by outside parties, which is a smaller surface but a real one. Still defensible to defer — note it again rather than let the third stage in a row pass silently.

## 8 · Tests

**Unit** — `lib/anchor.ts`: a range inside one text node; a range spanning two inline elements (`**bold**` in the middle); a cross-block range refused; round-tripping offsets → range → offsets; quote-mismatch detection.

**Integration** — a reviewer's thread is invisible to a second reviewer and visible to Root (the property this whole stage rests on); a reviewer cannot read, reply to, or resolve another's thread by id; Root's reply appears in the author's thread; resolving sets `resolvedAt` and does not delete; a thread on an older round stays on it after a new round is published; the offset CHECK refuses an inverted range.

**e2e** — reviewer selects a passage, opens a thread, Root replies and resolves, and a second seeded reviewer sees an unmarked document.
