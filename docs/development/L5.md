# L5 — The dependency board

**Stage:** L5 of `ecosystem/working/root-studio-lifecycle-build-plan.md` (1.0),
**§3 "L5 · The dependency board"** — independent of the critical path,
depending only on L1 (`Project`). **Spec:**
`root-website-project-lifecycle.md` §7 (dependencies), §11 (the two
dashboards, stage 5). **Status:** built, verified against a real database,
including a shadow-database migration replay.

---

## 0 · Why this stage, stated once

The plan calls this "the best value-per-line in the whole plan" — a table
with dates and a nag. **The banked trap is the entire feature**: "they said
we have a host" is what failed at the engagement the plan is drawn from;
"we deployed a test file to the host" is what the board exists to force.
A `verifiedAt` with no recorded *how* would rebuild the very promise this
replaces, dressed up as though it were checked. Symmetry is the other half
of the point — a Root-side dependency is the same object as a customer-side
one, under the same rule, on the same board, because Root's own slippage
(F5) is one of the frictions this is built to make visible. Nothing here may
be a mechanism that can only nag the customer.

## 1 · What was built

### 1.1 · `Dependency`

One new model, one new enum (`DependencySide`: `CUSTOMER` | `ROOT`), owned by
`Project` (`onDelete: Cascade` — a dependency with no project to belong to is
not a commitment about anything). Every row carries:

- `side`, `titleFa`/`titleEn`, `dueAt` — the commitment itself.
- `createdById`/`createdAt` — who logged it, and when.
- `verifiedAt`/`verifiedById`/`verifiedNote` — the verification step, held
  together by a hand-written CHECK (`Dependency_verified_both_or_neither`):
  all three set, or none. `verifiedNote` **is** the banked trap's fix — the
  column that holds *what was done*, not only that something was checked.

**`overdue` is derived, never stored** (`lib/dependency.ts`'s `isOverdue`):
`dueAt < now() AND verifiedAt IS NULL`, computed fresh on every read, the
same F5 discipline `computeProjectProgress` already holds to for phase
progress. A verified dependency is never overdue however late the
verification came; an unverified one is overdue the instant its due date
passes, with nothing for anyone to remember to flip.

### 1.2 · The board, both sides, one rule

`createDependency(projectId, side, titleFa, titleEn, dueAt)` is the only
door a `Dependency` is created through — staff-authored regardless of which
side owes it, the same reasoning `addScopeItem` gives for why Root typing an
item into the registry is itself the agreement act (L1 §2 decision 4). A
Root-side row is created, tracked, and can go overdue through exactly the
same mutation and the exact same schema as a customer-side one — there is no
second model, no second set of columns, and no code path that treats one
side differently from the other except the label on `side` itself.

`verifyDependency(dependencyId, note)` is the one mutation that writes
`verifiedAt`, and it refuses (`VERIFICATION_NOTE_REQUIRED`) without a
non-blank `note` — checked in the resolver (`lib/dependency.ts`'s
`verificationRequiresNote`) before the database's own CHECK would refuse it
with a less specific code. `unverifyDependency` clears all three columns
together, the same decide/undecide shape `ScopeItem` already uses (L1 §1.2)
— for a verification made in error, rather than leaving a wrong claim on the
record.

### 1.3 · Overdue, on both dashboards

`Query.overdueDependencies` (staff, `contracts.manage`) returns every
overdue row across **every** project, both sides — the full board, not
scoped to one contract. `Query.myOverdueDependencies` (any signed-in caller)
returns the caller's own overdue **`CUSTOMER`-side** rows across every
project they own — never a `ROOT`-side row: a customer seeing "Root is late"
is not what the portal's own half of this board is for, and nothing in spec
§11's projection table asks for it.

- **Desk:** `Overview.tsx` gained a third panel, "Overdue dependencies,"
  listing every overdue row (both sides) with which project and customer it
  belongs to — spec §11's "full dependency board, both sides." The contract
  workspace gained its own `dependencies` tab (`DependenciesTab.tsx`) for
  authoring and verifying a single project's board in full (not only the
  overdue rows).
- **Portal:** `ContractDetail.tsx` gained a rail card, "Your commitments,"
  listing the project's own `CUSTOMER`-side dependencies (all of them, not
  only overdue ones — spec §11's "own commitments with due dates staring
  back"), with an overdue row visually marked rather than merely dated.

`Project.dependencies` (a live field resolver, the same pattern
`scopeTrades`/`phases`/`progress` already use) returns every dependency on a
project, both sides, unfiltered — the desk tab and the portal card both read
this one field and each does its own filtering/rendering, rather than two
different queries risking two different shapes of the same fact.

## 2 · Decisions taken inside the stage

1. **`Dependency.project` and `Project.customer` were added so the staff
   dashboard can name whose commitment a row is.** `overdueDependencies`
   spans every project at once, and nothing before this stage let a
   cross-project list say which project — or which customer — a row
   belongs to (`Project` had no `customer` field in the GraphQL schema at
   all). Both are thin, cheap additions: `Project.customer` reads the
   already-present `customerId` scalar column directly, no new query.
2. **Verification is staff-authored on both sides, not only for
   `CUSTOMER`-side rows.** The plan's symmetry argument is about the board
   showing the same overdue treatment for both sides, not about who may
   click verify. A customer cannot mark their own commitment verified —
   verification is Root confirming a commitment was actually met (or, for a
   Root-side row, Root confirming its own work), the same "Root logs the
   registry" precedent `createDependency` already follows. Revisit if a
   real engagement asks for a customer-side self-certify flow; nothing in
   the plan asks for one.
3. **No capability narrower than `contracts.manage` was introduced.** Same
   reasoning as L4 §2 decision 1 — every registry-adjacent surface since L1
   reuses this one capability, and nothing in the plan names a reason this
   stage should be the first exception.
4. **`Dependency` rows are hard-deleted (`deleteDependency`), not
   soft-tombstoned.** Unlike `ApiToken`'s `revokedAt` tombstone (kept
   because a revoked credential is itself evidence worth retaining), a
   mistakenly-logged commitment carries no comparable audit value once
   removed, and nothing in the plan asks for a history of deleted rows.
5. **No new `ChangeAction` values.** Creating, editing, verifying,
   unverifying or deleting a dependency does not write to `ChangeLog` —
   consistent with every prior stage's own precedent for registry-adjacent
   activity (L1 decision 8, L3 decision 5, L3b decision 7, L4 decision 4).
6. **`updateDependency` may edit `titleFa`/`titleEn`/`dueAt` freely, even on
   an already-verified row.** The plan does not ask for a freeze once
   verified, and refusing an edit (a typo fix, say) after verification would
   be a heavier mechanism than the stage's own acceptance bar asks for —
   the same "convention, not machinery" reasoning D2/L2.2 already applied to
   the demo review window.
7. **`side` is a plain enum column, not a role or a capability.** Whether a
   commitment is `CUSTOMER`- or `ROOT`-owed is a fact about the row, decided
   once at creation and never re-derived from who is looking — keeping it
   this way is what makes the "same object, same rule" symmetry (§0) a
   property of the schema, not a convention every query has to remember to
   honour.

## 3 · What was deliberately not built

- **A notification when a dependency goes overdue, or comes due soon.**
  The board surfaces overdue rows on both dashboards on read; nothing pushes
  an email or a reminder. The plan's own description ("a table with dates
  and a nag") reads as the dashboard panel itself being the nag — a
  scheduled reminder job is real future work this stage does not invent
  ahead of L6's own scheduler question (build plan L6's banked trap: "there
  is no scheduler" applies here too, and this stage does not need one to
  meet its acceptance bar).
- **A customer-facing "propose a dependency" or "mark mine done" flow.** All
  authoring stays staff-side (§2 decision 2). The customer's own commitments
  are visible and dated; acting on them (supplying the host, say) happens
  outside the product, exactly as it does today — this stage tracks the
  commitment, not the delivery of it.
- **A `Contract!`-returning convention for `overdueDependencies`/
  `myOverdueDependencies`.** Both are cross-project lists with no single
  contract to reload — the same reasoning `activity`/`needsRootQueue`
  already establish for the desk's other cross-contract reads (V4.md T1).
  The authoring mutations (`createDependency` and its siblings) do return
  `Contract!`, matching every other registry-adjacent mutation since L1.
- **Linking an overdue-dependency dashboard row to its contract.** The desk
  Overview panel names the project and the customer but is not a clickable
  link — a `Dependency` names its `Project`, and this codebase has no
  "which contract represents this project" answer available without an
  extra lookup (`firstContractId`'s own documented shortcut, L1 §2 decision
  3). Not worth a special-cased query for one dashboard row; the contract
  workspace's own `dependencies` tab is where the real editing happens.

## 4 · The migration

Hand-authored:
`apps/api/prisma/migrations/20260921140000_l5_dependency_board/migration.sql`.

Derived from the same combined `prisma migrate diff --from-schema-datamodel
<pre-L4 schema> --to-schema-datamodel <post-L4+L5 schema> --script` run L4's
own migration was split from (see `L4.md` §4) — this file is the other half.
No correction for a NOT NULL-with-no-default trap was needed: `Dependency`
is a brand-new table and starts empty, so every `NOT NULL` column on it is
free. What the raw diff cannot express, and this file adds by hand:
`Dependency_verified_both_or_neither`, the three-column "both or neither"
CHECK — the same route L1's `ScopeItem_decided_both_or_neither` already
takes, over three columns instead of two.

Applied for real, on this machine, to both `root_website` and
`root_website_test` via `npx prisma migrate deploy` in the same pass as L4's
migration (they were deployed together, in order, since both were written
before either was applied — see L4.md §7). Each migration is independently
correct and independently reviewable regardless of the order they happened
to ship in this session.

## 5 · Traps, checked against what was actually built

1. **Verification is the whole feature (the banked trap).** Confirmed by
   the integration suite (§7): `verifyDependency` without a note is refused
   in the resolver, and the database itself refuses a `verifiedAt` written
   with no `verifiedNote` even when the resolver is bypassed entirely
   (a direct `prisma.dependency.update` in the test, the same
   CHECK-bypassing-the-resolver discipline L3b's own suite established).
2. **Symmetry — the same board, the same rule, both sides.** Confirmed:
   `createDependency`, `verifyDependency`, `unverifyDependency` and
   `deleteDependency` take no `side`-conditional branch anywhere in
   `resolvers/admin/dependencies.ts` (grep confirms `side` is read, in these
   five mutations, only inside `createDependency`'s own `data:` object —
   never compared or branched on). The integration suite's own symmetry test
   creates one dependency per side on the same project and asserts both come
   back from `overdueDependencies` with `overdue: true`.
3. **Root's own slippage is visible, not only the customer's.** Confirmed:
   `overdueDependencies` (the staff dashboard) has no `side` filter in its
   `where` clause — both sides return. `myOverdueDependencies` (the
   customer's own half) *does* filter to `CUSTOMER`, which is the
   deliberate, documented asymmetry (§2 decision 2's own reasoning): the
   customer's board shows their own commitments, not a report card on Root.
4. **`overdue` is derived, never stored.** Confirmed by reading the schema:
   `Dependency` has no `overdue` column at all. The GraphQL field is a pure
   function of `dueAt`/`verifiedAt`, computed in `fields.ts` on every read.
5. **House rule 2 (ownership vs. capability).** Every mutation in
   `resolvers/admin/dependencies.ts` gates on
   `requireCapability(ctx, 'contracts.manage')`. `myOverdueDependencies`
   gates on `requireUser` plus a `project: { customerId: user.id }` filter
   in the `where` clause — an ownership edge, never a role test.
6. **House rule 6 (API code, web sentence).** The one new user-facing error
   this stage introduces, `VERIFICATION_NOTE_REQUIRED`, carries an English
   `message` plus the code; `DependenciesTab.tsx` never needs to render it
   as a sentence because the form has no way to submit an empty note in the
   first place (the submit button stays disabled) — the same "make the
   wrong state unreachable" approach several other forms in this codebase
   already take.
7. **House rule 14 (digits).** `DependenciesTab.tsx`'s due-date `<input
   type="date">` carries `num-latin` (the widget itself, matching
   `PhasesTab.tsx`'s own `reviewWindowStart`/`reviewWindowEnd` inputs) while
   every *rendered* date (`fullDateTime`, `relativeTime`) goes through the
   locale-aware helpers unchanged — checked by reading, since no bare
   `toLocaleDateString`-style Latin numeral leaks into rendered text.
8. **The naming check against `desk/sections.ts`.** No new desk section was
   added for this stage (`dependencies` is a workspace *tab*, not a
   top-level section) — confirmed by grep: `desk/sections.ts`'s diff for
   this stage is empty. No new identifier contains the bare word "review."
9. **D5 stays decided.** `git diff -- apps/api/src/lib/gate.ts
   apps/api/src/lib/gate.test.ts` is empty (checked once, covering both L4
   and L5 in the same diff — see L4.md §5.8). No line this stage added sets
   `approvedAt` or `chosenAt`.

  Enamad commitments tracked on a live board — is outside what this session

  spec for the new tab itself. The same gap L4's own verification section
  left open for its two new screens, and L3b's for `Builds.tsx` before that.
