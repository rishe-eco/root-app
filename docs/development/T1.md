# T1 — template types, scope templates, `ScopeItem.kind`

**Built:** 2026-09-29 · **Plan:** `root-sot/ecosystem/working/root-studio-journeys-build-plan.md` §5 "T1", PD-5
**Branch:** `stage-t1-templates` — built by a Sonnet lane (`bee8703`), reviewed by Opus

Site types are data now. A designer (`templates.types`) keeps the list of types; sales (`templates.scope`) keeps each type's pages, features and deliverables. The registry learns what kind each item is, and which contract agreed it. Nothing *uses* the templates yet — J4's brief picks a type, J5 seeds a contract's scope from it.

## 1 · What was built

- **Migration `20260929130000_t1_templates`:** `ScopeKind {PAGE, FEATURE, DELIVERABLE, EXTRA}`; `ScopeItem.kind` (required, **no default** — every creator sets it, so a forgotten one is a type error, not a silent guess) and `ScopeItem.contractId` (SET NULL); `TemplateType`, `TemplateScopeItem`; CHECK `TemplateScopeItem_kind_not_extra` (templates never hold the checklist's kind), proven by a direct insert. **Backfill in SQL:** `checklist.*` → EXTRA, the `PAGES` keys → PAGE, the rest → FEATURE; `contractId` = the project's first contract (`createdAt`, then `id` — `firstContractId` has no tie-break, the backfill needs one).
- **`lib/templates.ts`:** `scopeKindForKey` — the one classification rule, shared by the legacy creators and mirrored by the migration (a unit test asserts the migration's page-key list equals `PAGES`). `lib/templateScope.ts`: slug, key and list validators.
- **API:** `templateTypes(activeOnly)` (readable with either template capability or `contracts.author` — J4's picker), `createTemplateType`, `updateTemplateType` (deactivate, never delete — J4's `Restrict`), `reorderTemplateTypes`, `setTemplateScope` (replace-all in one transaction, **the type row locked `FOR UPDATE`** so two concurrent saves cannot interleave). Codes: `INVALID_SLUG`, `INVALID_KEY`, `DUPLICATE_TEMPLATE_KEY`, `INVALID_TEMPLATE_KIND`, `LABEL_REQUIRED`, `TEMPLATE_SLUG_TAKEN`, `REORDER_MISMATCH`, `NOT_FOUND`, `FORBIDDEN` first.
- **Every `ScopeItem` creator** sets kind and contract: `createContract` (checklist rows EXTRA, named to the new contract), `applyContractTemplate`, `addScopeItem` (optional `kind`, else the key decides), `executeScopeTrade` (the contract is set when the item becomes AGREED; a proposal starts with none), the seed.
- **Web:** desk section `templates`, visible with either capability — a nav row's `capability` may now be a list ("any of"), and `canSeeSection` serves both the nav and the route guard; tabs Types and Scope, each read-only without its capability; the scope list edited as a draft and saved whole. Seed: five types with placeholder lists, labelled as placeholders in both languages.
