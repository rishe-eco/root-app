**Stage:** L3 of `ecosystem/working/root-studio-lifecycle-build-plan.md` (1.0).
**Depends on:** L1 (`Project`, the scope registry), L2 (`Phase`, `Demo`, the
live demo surface). **Spec:** `root-website-project-lifecycle.md` §6, §5.
**Decisions:** D3 (the decider is the project's customer), D4 (dumb

## 1 · What was built

### 1.1 · Naming, settled first (build plan L3's first banked trap)

`apps/web/src/desk/sections.ts` already has `review` and `reviewAdmin` for
the Review Room — Root's own documents read by outside specialists, an
unrelated feature. So every new identifier in this stage avoids the bare
word "review": the model is `DemoFrame` (not `ReviewFrame`), the desk section
stays `demos` (added at L1/L2, untouched here), and "review frame" / "demo
review" are prose only. Grepping the diff for `\breview\b` inside a new
identifier returns nothing.

### 1.2 · `DemoFrame` and `DemoFrameLine` — the review frame, generated

A `DemoFrame` is at most one per `Demo` (`@@unique demoId`). It carries an
optional bilingual `summary` and an ordered list of `DemoFrameLine`s, each in
one of the four buckets spec §6 asks for: `NEW`, `KNOWN_MISSING`,
`TEMPORARY`, `DECIDED`.

**Generation, not authoring from scratch.** `generateDemoFrame` (staff only)
derives lines from the registry via `lib/demoFrame.ts`'s pure
`deriveFrameLines`:

- **NEW** — scope items on *this demo's own phase* that have reached
  `IN_DEMO`.
- **KNOWN_MISSING** — scope items on this phase still `IN_BUILD`.
- **TEMPORARY** / **DECIDED** — read project-wide, not phase-scoped: a known
  stand-in or a settled decision does not stop mattering once its own phase
  closes. Both still require the item to be agreed or beyond
  (`lib/scope.ts`'s `isAgreedOrBeyond`) — a declined item is not part of the
  build the frame describes.

One item can land in more than one bucket at once (an `IN_DEMO` item that is
also `temporary` appears under both) — that is two true things about the
same fact, not a bug to collapse.

**Generation is additive, on purpose.** A second call to `generateDemoFrame`
never edits or deletes an existing (scope item, bucket) line — it only adds
ones not already present. Making it replace-and-recreate instead would
silently pull a line, and the feedback already anchored to it, out from
under a reviewer who had already commented. A line Root types by hand
(`addDemoFrameLine`) has no `scopeItemId` and can never be touched by
generation.

**Lines are a snapshot, not a live view.** `textFa`/`textEn` are copied from
the source scope item's label at generation time, the same reasoning
`agreedScopeSnapshot` already uses for Appendix 1 (L1). Editing a scope
item's label later does not retroactively rewrite what a past, possibly
already-reviewed, frame line says.

### 1.3 · The publish gate — "a demo cannot be published naked"

`Demo.publishedAt` is new. Null means draft: visible to staff shaping the
phase, invisible to the customer's own portal query. `publishDemo` (staff
only) is the sole writer, and refuses with `NO_FRAME` unless a `DemoFrame`
row already exists for that demo — the existence of the row is the gate, not
its contents, so a project with nothing temporary, missing or decided yet
can still publish an honestly empty frame.

`Project.phases`'s field resolver (`fields.ts`) now takes the caller into
account: a demo with `publishedAt: null` is filtered out of the `demos` list
for anyone who is not staff. This closes the gate at the read side too — the
promise is about what the customer's query can ever return, not only about
what the publish mutation refuses.

Publishing sends `demoPublishedEmail` to the project's customer (§1.6).

### 1.4 · `FeedbackItem` and `FeedbackComment` — per-item intake, never a blob

`FeedbackItem` binds to exactly one of `DemoPage` or `DemoFrameLine` — the
same shape `Signature` already uses for `contractRevisionId`/`amendmentId`,
enforced by a hand-written CHECK
(`FeedbackItem_exactly_one_target`), because Prisma cannot express "exactly
one of these two."

**Duplicate collapse (D4) lives in the schema, not only in application
logic.** `demoPageId` and `frameLineId` each carry their own unique index —
at most one `FeedbackItem` may ever point at a given target. `submitFeedback`
looks the row up first (`find-or-create`) and appends a `FeedbackComment`
to an existing item rather than creating a second one; the unique indexes
are the backstop that makes that invariant a database fact, not a resolver
convention that could quietly slip.

Each individual voice on an item is a `FeedbackComment` — one row per
submission, oldest first — so "any number of customer-side contributors may
comment" (spec §6, F8) is representable without inventing a second item per
voice.

### 1.5 · Interception (D4) — dumb, and it stays that way

`lib/feedback.ts`'s `checkInterception` is a pure property check against the
*target's own scope item* (only a `DemoFrameLine` carries one — a `DemoPage`
target can never be intercepted, since a page does not point at a single
scope item): if `decidedAt` is set, or `temporary` is true, submission is
intercepted. No model, no semantic matcher, no network call — the whole
check is three comparisons against fields already in hand.

**Nothing is written on an intercepted, unconfirmed attempt.** `submitFeedback`
returns a `FeedbackSubmitResult` with `item: null`, `intercepted: true`, and
the reason plus the scope item interception is asking about. The caller
resubmits identically with `confirmReopen: true` to proceed; only then does
the `FeedbackItem` row (and its `reopenedScopeItemId`) get written.

**House rule 6, held at the boundary.** `FeedbackInterceptionReason` is a bare
enum (`DECIDED` / `TEMPORARY`); the sentence — "this was settled on ⟨date⟩ —
do you want to formally reopen it?" — is built entirely in
`DemoFeedbackPanel.tsx`'s `interceptionSentence`, from the reason and the
scope item's own `decidedAt`/`decidedNote`/`temporary`/labels. No prose
crosses the API boundary for this feature.

### 1.6 · Ratification (D3) — signature-shaped, not a `Signature`

`ratifyFeedback(demoId, itemIds)` moves every named item that is currently
`OPEN` and belongs to that demo to `RATIFIED`, stamping `ratifiedAt` and
`ratifiedById` on each row. Anything named that is not `OPEN` (already
ratified, or a bogus id) is silently skipped — the same idempotent shape
`resolveReviewThread` already uses for "already done."

**Who may ratify** is D3's own answer, applied without a new edge: ownership
against `project.customerId`, with a staff bypass, exactly the shape
`resolvers/demo.ts`'s `loadDemoForActor` already uses for `reportDemoPath` —
reused here rather than rewritten (`resolvers/feedback.ts` imports and
exports it from `demo.ts`). There is no "decider" role, no delegation edge,
and nothing added to `lib/capabilities.ts` for this: the check is
`project.customerId === user.id`, in code, not "is a `CUSTOMER`."

**Not a `Signature`.** `ratifiedAt`/`ratifiedById` are two plain columns on
`FeedbackItem`, recording who decided what, when — deliberately not routed
through the `Signature` model, which attests to hashed bytes of a legal
instrument. Widening it to also mean "the customer approved this feedback
batch" would weaken the one word in this product that is load-bearing (build
plan L3's fourth banked trap).

**`FeedbackStatus` carries three states this stage never writes** —
`ADDRESSED`, `ACCEPTED`, `DECLINED` — on the same precedent L1 used for
`ScopeStatus.ACCEPTED`: built before anything can reach it, so the surface
this stage builds (the fate badges in `DemoFeedbackPanel`) can already render
whatever L3b's build ledger eventually sets, without a second migration to
add the enum values. Nothing in this stage writes them; that is L3b's job.

### 1.7 · Notifications — the mechanism, not polish (build plan L3's second banked trap)

Three new bilingual templates in `lib/mailTemplates.ts`, sent from three
places:

| Event | Sent to | Template |
|---|---|---|
| `publishDemo` succeeds | the project's customer | `demoPublishedEmail` |
| `submitFeedback` succeeds, and the actor is not staff | every account holding `contracts.manage` | `feedbackSubmittedEmail` |
| `ratifyFeedback` moves at least one item | every account holding `contracts.manage` | `feedbackRatifiedEmail` |

The "who is staff" lookup (`contractManagers()` in `resolvers/feedback.ts`)
mirrors `reviewThreads.ts`'s own `reviewAdmins()` — filtered in application
code against `lib/capabilities.ts`'s `can`, never by testing a role
directly. All three sends are best-effort (`.catch(console.error)`), the
same discipline the Review Room's own notifications already use — a failed
email must never fail the mutation that triggered it.

House rule 14 shows up here for the first time on the API side: the
ratification email's Persian body needed a count rendered in Persian digits,
and the API had no digit-formatting helper of its own (only the web side's
`formatCount`). `mailTemplates.ts` gained a small local `toPersianDigits`
for exactly this — versions/refs/hashes stay Latin everywhere else in this
stage; the one count is what house rule 14 is about.

### 1.8 · Desk and portal surfaces

One shared component, `apps/web/src/components/DemoFeedbackPanel.tsx`, used
by both `PhasesTab.tsx` (desk, `canAuthor`) and `ContractDetail.tsx` (portal,
read/comment/ratify only) — the same pattern `DemoViewport` already set for
the live-site frame itself, so the interception-confirm flow and the
ratify-selection UI exist in exactly one place.

Staff-only, inside the panel: generate/refresh the frame, edit its summary,
add/edit/delete hand-authored lines, and publish (disabled with a plain
message once `NO_FRAME` would refuse it). Available to anyone who can see a
published demo: a comment box per frame line and per declared page, the
interception prompt and its confirm step, and ratification checkboxes over
every currently-`OPEN` item.

**The one place this codebase's "no tab calls refetch" rule bends.**
`submitFeedback` returns `FeedbackSubmitResult`, not `Contract!` — an
interception result is not a Contract-shaped fact — so a brand-new
`FeedbackItem` has nowhere for Apollo's normalized cache to insert itself
automatically. `ContractWorkspace.tsx`'s `WorkspaceContext` grew a `refetch`
field for exactly this one caller; every other mutation in this stage
(`generateDemoFrame`, `publishDemo`, `ratifyFeedback`, …) still returns the
whole `Contract!` and needs none of it.

### 1.9 · A pre-existing defect this stage's own verification found

Running `npm run e2e` at all (§7) is new as of this session — L1 and L2 both
recorded it as "not run, no database." The very first attempt failed eight
of twenty-nine specs, every one of them past the first customer/admin
sign-in, with `GRAPHQL_VALIDATION_FAILED` on `MyContracts`, `AllContracts`
and `CreateContract` — three of the most-used operations in the app.

**Not caused by this stage.** `git diff` on `apps/web/src/lib/queries.ts` is
insertions-only; the `phaseId` selection inside `CONTRACT_FIELDS`'s
`scopeItems { … }` block predates this stage (it shipped with L2's phase
board). The `ScopeItem` GraphQL type in `typeDefs.ts`, however, never
declared a `phaseId` field at all — so every query built from
`CONTRACT_FIELDS` has failed schema validation outright since L2 shipped it,
invisibly, because nothing before this session ever sent that query to a
running server. TypeScript does not check a `gql` template literal against
the schema, and the 173 (now 182) integration specs all use small
hand-written query strings rather than the web app's own fragments.

Fixed here (`typeDefs.ts`'s `ScopeItem` type gains `phaseId: ID`, one line,
no resolver change needed — the Prisma column and the `scopeItems` include
already return it on every row) rather than deferred, because it blocked
verifying this stage's own new surface at all. A small script validating
every exported operation in `queries.ts` against the schema (`graphql`'s own
`validate`) is what actually found it and confirmed the fix — see §7. That
script is not committed as a test; it is worth turning into one so this
exact class of defect cannot recur silently, and is flagged rather than
built here, since a decision about where such a check should live (a new
web-side test file? a CI step reading both workspaces?) is bigger than this
stage's remit.

## 2 · Decisions taken inside the stage

1. **Interception keys off the scope item, not the frame-line bucket.** A
   line's `kind` (e.g. `NEW`) and its underlying scope item's live
   `decided`/`temporary` flags are independent facts — an item can be both
   newly `IN_DEMO` and `temporary` at once, landing on two lines. Interception
   reads the scope item directly, so commenting on *either* line intercepts
   identically. Checked by `feedback.test.ts` and by the L3 integration
   suite's decided-item test.
2. **`generateDemoFrame` both creates the frame and seeds its lines** — there
   is no separate "create an empty frame" mutation. `addDemoFrameLine` and
   `updateDemoFrameSummary` also upsert the frame if it does not exist yet,
   so a demo with nothing in the registry worth surfacing can still be
   authored by hand from a blank state, without an extra round trip.
3. **`submitFeedback` requires the demo to be published** (`DEMO_NOT_PUBLISHED`
   otherwise). Feedback against a draft demo's pages or lines has no meaning
   yet — the customer cannot see the demo at all per §1.3, and staff testing
   a draft demo have no reason to file feedback against their own
   in-progress authoring.
4. **`ratifyFeedback` returns `Contract!`; `submitFeedback` does not.**
   Ratifying only ever changes rows Apollo's cache already knows about
   (existing `FeedbackItem`s moving `OPEN → RATIFIED`), so the ordinary T9
   convention applies cleanly. Submitting can create a row the cache has
   never seen, which is the one case T9 does not cover — see §1.8.
5. **No `ChangeAction` values were added.** Publishing a demo, submitting
   feedback and ratifying a batch do not write to `ChangeLog` — consistent
   with L1's own decision 8 (registry activity does not feed the desk's
   activity feed either), and nothing in the plan asked for it this stage.
6. **`FeedbackComment.body` has no length ceiling beyond "non-empty, trimmed."**
   `Comment.body` (the existing contract-conversation model) has none
   either; matching that rather than inventing a new rule for a shape this
   codebase already has an answer for.

## 3 · What was deliberately not built

- **L3b's build ledger.** `FeedbackStatus.ADDRESSED`/`ACCEPTED`/`DECLINED` are
  in the enum; nothing writes them. That is explicitly the next stage's job,
  and the build plan is explicit that shipping L3 without it is worse than
  shipping neither — see §5 below.
- **A `DemoFrame` publish/freeze concept of its own.** The frame can be
  edited after the demo is published (adding a hand-authored line, tweaking
  the summary); nothing locks it. D2/L2's "the review window is a
  convention, not machinery" reasoning applies again here rather than being
  re-argued: a frozen frame is a heavier mechanism than this stage's
  acceptance criterion asked for.
- **Moving a stray item between channels** (spec §5's "an item entering the
  wrong channel is moved, not handled") — no admin-work / support-ticket
  triage exists yet; that is L4's `Ticket` surface.
- **A "many voices, one decider" UI beyond a plain comment list.** F8 is
  still handled the way D3 itself says it is handled: socially, through one
  customer login. `FeedbackComment.author` records who actually typed each
  voice, which is the whole of what this stage does about it.
- **Deleting/editing a `FeedbackComment`.** Comments are append-only, the
  same shape `Comment` and `ReviewComment` already use elsewhere in this
  codebase.

## 5 · Traps, checked against what was actually built

1. **The naming collision (banked trap #1).** Confirmed by grep: no new
   identifier in this stage's diff contains the bare word "review." The
   model is `DemoFrame`; the file is `lib/demoFrame.ts`; the desk section is
   still `demos`.
2. **The notification half is not polish (banked trap #2).** Three templates
   shipped with this stage, not deferred — see §1.7. Every one of the four
   integration-test scenarios that exercises `publishDemo`, `submitFeedback`
   or `ratifyFeedback` also exercises (and, via the dev-transport console
   log, visibly triggers) its notification.
3. **The interception prompt is bilingual prose built on the web (banked
   trap #3).** Confirmed by reading `resolvers/feedback.ts`: the only thing
   it returns for an interception is `interceptionReason` (a bare GraphQL
   enum) and `interceptionScopeItem` (plain fields — `decidedAt`,
   `decidedNote`, `temporary`, two labels). The sentence itself exists only
   in `DemoFeedbackPanel.tsx`.
4. **Ratification is not bound to `Signature` (banked trap #4).** Confirmed
   by reading `schema.prisma`: `FeedbackItem.ratifiedAt`/`ratifiedById` are
   plain columns with no relation to `Signature`, `ContractRevision`, or
   `Amendment`.
5. **D5 stays decided.** `grep -rn "chosenAt\|approvedAt"` across every file
   this stage touched finds no write — `DemoFrameLine.scopeItem` and the
   design-image toggle it sits beside remain reads only.
   `gate.test.ts` is untouched and green (see §6).
6. **House rule 2 (ownership vs. capability).** `submitFeedback` and
   `ratifyFeedback` gate on `project.customerId === user.id` (via the reused
   `loadDemoForActor`), with a staff bypass — never a `CUSTOMER` role test.
   Every frame-authoring mutation in `resolvers/admin/demoFrame.ts` gates on
   `contracts.manage`, the capability, exactly like every other admin
   mutation.
7. **House rule 6 (API code, web sentence).** See trap #3 above — the one
   place this stage introduces genuinely new user-facing prose logic, and
   the one place the rule was explicitly at risk of being broken a second
   time (the build plan names R4's first draft as the prior casualty).
8. **House rule 14 (digits).** `FeedbackItem`/`DemoFrameLine` carry no
   position or count rendered as a bare number in the new UI beyond what
   `formatCount`/`fullDateTime` already produce correctly; the one new
   server-authored count (the ratification email) is covered in §1.7.

here) and starts its own API/web servers on ports 4101/4173 against

The first attempt was **not** green: 7 passed, 8 failed, 14 did not run,
every failure from `02-contract-flow.spec.ts` onward reading
`GRAPHQL_VALIDATION_FAILED` in the dev-server log for `MyContracts`,
`AllContracts` and `CreateContract`. That traced to §1.9's pre-existing
`ScopeItem.phaseId` gap, not to this stage's own mutations — the
`GRAPHQL_VALIDATION_FAILED` code names a malformed *request*, and
`validate()` (graphql's own function, run directly against `typeDefs` and
every operation exported from `apps/web/src/lib/queries.ts`) confirmed
exactly one error, repeated across three operations: `Cannot query field
"phaseId" on type "ScopeItem"`. Fixed per §1.9; the same validation script
then reported **zero errors across all 102 operations** in `queries.ts`.

with a ✘ in the runner's own output
(`02-contract-flow.spec.ts:124`, "a keyboard user can open a contract") is a
pre-existing `test.fail(true, …)`-annotated known gap in `Contracts.tsx`
(the row has no keyboard affordance) — Playwright counts an *expected*
failure as a pass, which is why the final tally reads 29/29. Nothing in the
29 specs exercises `DemoFeedbackPanel` directly (no spec file references
`feedback`, `DemoFrame`, or the frame by name) — this stage's own review
frame and feedback-intake UI is covered by the 9 new integration specs
listed just above, not by e2e. What e2e does confirm, for the first time on this
machine, is that this stage's schema and resolver changes did not regress
any of the other twenty-eight flows a real browser drives against a real
server — including the phase board (`04-workspace.spec.ts`) this stage adds
the most code beside.
