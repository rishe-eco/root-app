# L7 — Services: the product-import panel

**Stage:** L7 of `ecosystem/working/root-studio-lifecycle-build-plan.md` (1.0).
**Depends on:** L1 (`Project`), L6 (the billing edge). **Spec:** `root-website-project-lifecycle.md` §9.
**Status:** built and verified against a real database.

---

## 1 · What was built

### 1.1 · A service is a panel, a run history, and a billing edge

The plan asks for this stage to be framed as *the first of a class* rather than
as one feature, so the second service is configuration rather than a rewrite.
That shape is what `ServiceRun` encodes: a run belongs to a project, carries an
uploaded file, moves through a status lifecycle, holds its diffed rows, and
points at an optional `BillingEntry`. Nothing in the model knows the word
"product" except the row shape it validates.

### 1.2 · The lifecycle, and the gate inside it

`ServiceRunStatus` is `UPLOADED → PREVIEWED → APPLIED`, plus `FAILED`.

**`PREVIEWED` is a gate, not a label.** `applyServiceRun` refuses with
`NOT_PREVIEWED` from any status other than `PREVIEWED`, and refuses with
`ALREADY_APPLIED` from `APPLIED`. **There is no path from `UPLOADED` to
`APPLIED` that skips the diff.** The plan's banked trap says the preview *is*
the feature — an import that applies without one is a destructive operation on
a live store — so the gate lives in the status machine rather than in a UI flow
that a second caller could bypass.

`previewServiceRun` may be called repeatedly on `UPLOADED`, `FAILED`, or
`PREVIEWED` runs. Re-uploading is expected to preview again rather than to
construct a second run.

### 1.3 · The diff

`ServiceRunRow` holds one row per line of the uploaded file with a
`ServiceRowAction` — `CREATE`, `UPDATE`, `UNCHANGED`, or `REJECTED`. That is
spec §9's "rows to create, update, leave, plus rejects" as data rather than as a
rendered summary, which is what lets the run history stay auditable after the
fact.

**A rejected row must say why**, held by
`ServiceRunRow_reject_reason_required` — the same "declined-because" CHECK shape
L1 and L3b already use. A `FAILED` run likewise requires its `failureReason`
(`ServiceRun_failure_reason_required`). A nullable reason ships null.

### 1.4 · The Persian fold — reused for matching, refused for storage

This is the trap the stage was most likely to get wrong, and the resolution is
worth stating precisely because it is *not* simply "reuse R1's fold".

`foldPersian` (`lib/library.ts`) **is** reused — as the SKU **comparison key**,
so the same product typed with an Arabic yeh or kaf matches itself across
imports. It is **never written back** as a stored `sku`, `nameFa`, or `nameEn`.
Three reasons, all recorded in `lib/serviceImport.ts`'s own header:

- **ZWNJ is not noise here.** R1's fold strips it, which is right for a search
  query and wrong for a product name — Persian compounds carry it meaningfully,
  and a name that collides with itself after losing a ZWNJ is a different name.
- **A SKU is a machine key** (house rule 14) and the fold lowercases. Folding it
  for a comparison is reasonable; storing the folded form would violate the rule
  on the column closest to a "ref" in the rule's own sense.
- **Forcing Arabic yeh/kaf to Persian forms is an orthographic rewrite**, not a
  normalization, for text intentionally in Arabic script — a brand name, a
  loanword. R1 accepts that rewrite because matching a *query* benefits from it.
  A stored catalogue does not get to make that trade on the customer's behalf.

Digit-script normalization before parsing a number is a separate and
unambiguous reuse: the result is a `bigint`, so nothing about the fold's
opinions survives into stored text.

**This is the brief's instruction followed rather than worked around** — R1's
fold is subtly wrong for the write path, and the answer was to say so loudly and
narrow its use, not to quietly fork it.

### 1.5 · Ownership, and the widened file CHECK

A customer uploads, previews, and applies runs for **their own project** —
`project.customerId`, an ownership edge, never a role test (house rule 2).

`StoredFile`'s private-file CHECK previously required a `contractId`. A service
run's upload belongs to a **project**, not a contract, so the constraint is
widened to accept either. That is a real change to an existing invariant and it
is recorded here rather than buried in the migration.

## 2 · What was deliberately not built

- **No live target-system integration.** "The store" a run diffs against is the
  set of rows the previous applied run established. Wiring this to a real
  storefront is a per-customer integration, and the plan's sequencing call is
  explicit: the live customer's import is **delivered by hand**; this stage
  productizes the mechanism. Building the general integration first would put
  the platform's least-leveraged stage on the critical path of the
  most-leveraged engagement.
- **No second service.** The class is the point; one member proves it.

Correctness there rests on the integration specs, typecheck, and a clean build.

integration to run it against; see §2.

## 4 · A gap found while finishing this stage

`DESK_SECTIONS` gained `services` in its key union but **never gained its row**,
and `desk.navServices` was missing from both locale files — so the section was
routable but invisible in the nav. Both fixed here. The section is gated on
`contracts.manage`, the same reasoning `tickets` and `billing` already record:
nothing in the plan asks for a narrower staff persona yet, and every Root-side
working surface added since L1 has reused that capability rather than growing
its own.
