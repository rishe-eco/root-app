Sales can open a customer, disable or restore them, and grant tools. An ADMIN invites staff and changes roles without the CLI. `/desk/users` is **the first slice of the Users place** (PD-12) — everything else the founder means by it builds on this page, not beside it. The customer-facing Services surface is now **Tools** («ابزارها»), shown only to a customer holding a grant.

## 1 · What was built

- **Migration `20260929140000_s3_tool_grants`:** `ToolKey {PRODUCT_IMPORT}`, `ToolGrant` (with `revokedById` beside the plan's columns), and the hand-written partial unique index `ToolGrant_one_active_per_tool` (`WHERE "revokedAt" IS NULL`), proven by a direct insert.
- **`capabilities.ts`:** `isStaffRole`, `hasStaffRole`, `hasCustomerRole`, `isSuperuser` — the role reads resolvers need, kept in the one file allowed to read roles (house rule 1).
- **API (`resolvers/people.ts`):** `customer(id)` (money gated by `mayReadMoney`, tickets by `tickets.answer`, contracts by `contractVisibleTo`); `allUsers`; `myTools`; `setUserState`; `grantTool` / `revokeTool`; `inviteStaff`; `setUserRoles`. L7's customer paths — queries, mutations and the import upload — answer `NOT_FOUND` without an active grant (house rule 13: the tool does not exist for them).
- **Web:** `/desk/customers/:id`, `/desk/users`, the Tools rename with `/app/services` redirecting, the rail item only with a grant.

## 2 · What the build settled that the plan did not

1. **Disabling revokes every outstanding token**, not only INVITE / LOGIN_CODE / SIGNIN_FACTOR. `resetPassword` sets an account ACTIVE, so a password-reset link issued before the disable was a way to undo it. Backstop: `acceptInvite` and `resetPassword` refuse a DISABLED account. Both proven.
2. **A mixed account (customer + staff role) needs `staff.manage`** to disable — the plan's rule, applied to a role *set*.
3. **`LAST_SUPERUSER` holds under concurrency:** the active ADMIN rows are locked `FOR UPDATE` inside the transaction, so two admins disabling or demoting each other at once leave exactly one standing. Both races tested.
4. **Restoring an invitee who never accepted** returns them to INVITED, never to a passwordless ACTIVE.
5. **`inviteStaff`'s phone is required only when a role needs the factor** (`PHONE_REQUIRED_FOR_STAFF`), not always as the plan wrote; it never repurposes an existing account (`ALREADY_ACTIVE`, `ACCOUNT_DISABLED`, `ACCOUNT_EXISTS`, `IDENTIFIER_CONFLICT`).
6. **L7's service strings had never been in the locale files** — both service pages rendered raw keys on `main`. Added in both languages.
7. `CustomerProfile` carries an `id`, or Apollo cannot merge a grant's result into the page (found by the e2e).
