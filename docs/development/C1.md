# C1 · Review Room — documents, snapshots and the corpus

**Branch:** `stage-c1-corpus`
**Needs:** F2 (a desk to hang it on), F3 (`review.participate` / `review.admin`, both provisioned and both still unused), C0 (built — the reviewer-invite template already exists).
**Blocks:** C2, entirely.
**Shape:** medium, and lopsided. The reading surface is small; the **publish step is a new kind of thing this repo has never had** — a process that crosses from a git repo the API cannot see into Postgres.
**Spec:** `root-sot/ecosystem/working/root-website-review-room.md` §3.1, §3.2, §3.3; build plan §5b C1.

**Acceptance:** Root publishes a review round — a `root-sot` sha plus an allowlist — and an invited reviewer signs in, sees exactly the allowlisted documents at that sha, and reads them. No comments yet; C2 owns those. A document not on the allowlist is not merely hidden, it is **absent**.

---

## 0 · Two things to fix in your head before starting

**1 · The API never reads a git tree.** `root-sot` is not on the VPS and is not going there (spec §3.1). Everything below follows from that: the publish step runs somewhere that *has* both repos, and it pushes. Nothing pulls.

**2 · "The default points allow" in the build plan means an *allowlist*, not permission.** Build plan §5b reads *"the default points **allow**"*, which parses naturally as "access is allowed by default" — **the exact opposite of the decision**. The spec (§3.2) is unambiguous: the choice is between denylist and allowlist, and *allowlist wins*, meaning **a file is outside the corpus until someone names it**. `personal-canon.md` is the concrete case and the reason this is a decision rather than a convention. If you read only the build plan, you would build the wrong thing.

## 1 · What a round is

> A **round** = one `root-sot` commit sha + one allowlist manifest + the rendered snapshots of exactly those paths.

Frozen at publish. Nothing about a round changes afterwards — that is the whole point (spec §3.1: *"the only [option] where a comment still means something six weeks later"*).

```prisma
model ReviewRound {
  id        String   @id @default(cuid())
  /// The root-sot commit this round froze. Recorded, never fetched.
  sha       String
  label     String?  // "Learn Module 1 review, August"
  publishedAt DateTime @default(now())
  publishedById String
  publishedBy   User   @relation(fields: [publishedById], references: [id])
  documents ReviewDocument[]
  @@index([publishedAt])
}

model ReviewDocument {
  id      String @id @default(cuid())
  roundId String
  round   ReviewRound @relation(fields: [roundId], references: [id], onDelete: Cascade)
  /// Path within root-sot, as the manifest named it.
  path    String
  title   String
  /// sha256 over the canonical serialization of `blocks` — see §3.
  contentHash String
  /// The frozen document, as an ordered block list. See §2 — this shape is
  /// what makes C2's passage anchors possible.
  blocks  Json
  order   Int
  @@unique([roundId, path])
  @@index([roundId, order])
}
```

**No `ReviewGrant` model, and that is the design.** Spec §3.2 reversed itself deliberately: one corpus for everyone holding `review.participate`. Do not reintroduce per-reviewer grants "for flexibility" — the security surface is *what is in the corpus at all*, and a grant table moves it back.

## 2 · The block list — the decision C2 depends on

Spec §3.3: *"A comment anchors to a character range in one snapshot."* **How the snapshot stores its text decides whether that is easy or impossible**, and C1 is where it gets decided. Get this wrong and C2 cannot be built without re-publishing every round.

**Do not store rendered HTML.** Anchors into rendered output shift the day the markdown renderer is upgraded, and a "frozen" document whose anchors move on a dependency bump is not frozen.

**Do not store one raw string and anchor offsets into it either.** It works, but every anchor is then a global offset that the renderer has to map back into the DOM — which couples C2's UI to the renderer emitting source positions.

**Store an ordered list of blocks**, split once, at publish time:

```ts
type Block = {
  /** Stable within the document, assigned at publish. Never re-derived. */
  id: string;        // "b12"
  kind: 'heading' | 'paragraph' | 'code' | 'list' | 'quote' | 'table';
  depth?: number;    // headings
  /** The block's markdown source, verbatim. */
  text: string;
};
```

Then a C2 comment anchors to `(blockId, start, end)` — offsets *within one small block*, which stay meaningful no matter how the block is rendered, and which the UI can map to a DOM range without the renderer's help. Blocks are frozen with the round, so nothing moves under them.

**The split happens in the publish step and is stored, not recomputed.** If the splitter is ever improved, old rounds keep their old blocks — correct, because their anchors point into them.

### 2.1 · Hashing reuses `lib/revision.ts`, and needs its own format tag

`canonicalize` and `contentHash` (`lib/revision.ts`) are already the one canonical serialization, and the spec asks for them by name. Reuse the functions; **do not reuse `SNAPSHOT_FORMAT`.** A document snapshot is a different shape from a contract snapshot, and a shared version number that means two things is a version number that means neither. Add `DOCUMENT_SNAPSHOT_FORMAT = 1` beside it.

## 3 · The publish step — the genuinely new part

**It runs where both repos exist, and it pushes.** A CLI in `root-app`:

```
npm run publish-round -- --sot ../Root --sha <sha> --manifest review-manifest.json --label "…"
```

What it does, in order:

1. `git -C <sot> rev-parse <sha>` — resolve and verify the commit exists. **Refuse a dirty tree or a symbolic ref**; a round must name an immutable commit, not "whatever main was".
2. Read the manifest **at that sha** (`git show <sha>:review-manifest.json`), not from the working tree. Otherwise the round freezes one thing and is described by another.
3. For each allowlisted path, `git show <sha>:<path>` → split into blocks → hash.
4. POST the whole round to an authenticated mutation, guarded by `review.admin`.

**The manifest lives in `root-sot`**, version-controlled beside what it describes, so adding a document to the corpus is a reviewable commit rather than a form field. That is the property that makes `personal-canon.md` safe: nobody adds it by accident, and adding it deliberately leaves a trace.

```json
{ "documents": [ { "path": "ecosystem/canon/02-pillars/learn.md", "title": "Learn" } ] }
```

### 3.1 · Traps in the publish step

- **A path in the manifest that does not exist at that sha must fail the whole round**, loudly. A partially published round is a corpus with a hole a reviewer cannot see and will not ask about.
- **Refuse a path outside the repo** (`../`, absolute). It is a CLI run by Root, not attacker input — but `git show` will happily resolve a traversal and the failure is silent.
- **Republishing the same sha + manifest should be idempotent or refused, not duplicated.** Decide which; either is defensible, two rounds identical but for their id are not.
- **The mutation is the trust boundary, not the CLI.** Validate server-side — paths, block shapes, hashes recomputed rather than trusted. The CLI is convenience; the endpoint is the API.

## 4 · The reading surface

A `review` section in `DESK_SECTIONS`, capability `review.participate`. F2's table already makes this three lines.

- `/desk/review` — rounds, newest first; within one, the document list in manifest order.
- `/desk/review/:roundId/:documentId` — the document, rendered from its blocks.

**A reviewer holds `review.participate` and nothing else** (F3's `REVIEWER` grant), so the desk shows them exactly one section — already proven by the seeded reviewer F2 added.

**Rendering markdown is a new dependency.** Nothing in this app renders markdown today. Pick one small library, pin it, and render **per block** — which is also what keeps block boundaries visible in the DOM for C2 to anchor to. Sanitize: the corpus is Root's own writing, but it is rendered into the app's origin and a reviewer is an outside party; `dangerouslySetInnerHTML` over unsanitized HTML is a stored-XSS waiting for the day someone pastes a snippet into canon.

**The corpus is bilingual-ish and mostly English with Persian passages.** R2's `:lang(en)` fix (R2.md §1) is a prerequisite in practice — a Persian block inside an English document has exactly the same problem, in the other direction. If R2 has not landed when C1 does, C1 pays for that block instead.

## 5 · Traps

**T1 · The round is a record of a sha, not a link to one.** Nothing in the app should ever try to resolve, fetch or validate the sha against a remote. It is a string that lets a human check what was reviewed.

**T2 · `review.participate` is the most externally-held capability in the app.** It is the first one granted to someone outside Root. Every resolver added here is reachable by a person Root has met once. Guard each one; do not rely on the section nav.

**T3 · Do not let a reviewer see the round list of a round they were invited "after".** There is no such concept — one corpus, all rounds. Decide out loud whether an invited reviewer sees *previous* rounds (lean: yes; it is the same corpus and hiding history serves nobody) and record it, because it looks like a permission question and is not one.

**T4 · Comments are not in this stage.** The pull to add "just a simple comment field" while the document renderer is fresh is strong, and C2's model — passage anchors, threads, resolution, and reviewers not seeing each other's comments — is not simple. A comment model built casually here is one C2 has to migrate.

**T5 · `personal-canon.md` is the test case, and should be an actual test.** An integration test asserting a non-allowlisted path is absent from a published round — named for the file the decision was made about — is the one that will still make sense to someone reading it in a year.

## 6 · Tests

**Unit** — the block splitter: headings/paragraphs/code fences/lists, stable ids, and a document that is one long paragraph. Round-trip: `contentHash(blocks)` is stable under re-serialization and changes when any block's text changes.

**Integration** — publishing a round writes one `ReviewDocument` per manifest entry and no more (**T5**); a manifest naming a missing path fails the whole publish; a reviewer can read a published round; a **customer** and an unauthenticated caller cannot; `review.admin` is required to publish and `review.participate` is not enough.

**e2e** — the seeded reviewer signs in, lands on the desk with one section, opens a round and reads a document.
