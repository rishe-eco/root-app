# J1 — phone identity, SMS, the notification router, rate limits, the staff second factor

**Built:** 2026-09-29 · **Plan:** `root-sot/ecosystem/working/root-studio-journeys-build-plan.md` §5 "J1", PD-10, PD-15, PD-16, PD-18, PD-20, P0-4
**Branch:** `stage-j1-phone` — built by a Sonnet lane (`45c49ba` → `d6a0480`), reviewed and finished by Opus (`d0ec149`, `7aef8af`)

A customer can now be invited by SMS, sign in with a phone and a password, and recover by an SMS code. Staff in the roles that touch a customer's contract or money sign in with a second factor. Every notification the product sends goes through one router, `lib/notify.ts`, which picks email and/or SMS by what the account has. **The SMS provider is an empty slot on purpose** (PD-18): development and e2e run on `DevSmsTransport`; production, until the founder names a provider, sends nothing and says so.

---

## 1 · What was built

- **Schema** (`20260929120000_j1_phone_identity`): `User.phone` (E.164, unique), `User.email` optional, **CHECK `User_has_identifier`** (phone or email), `User.passwordChangeRequired`, `AuthToken.attempts`, `TokenPurpose` + `LOGIN_CODE` / `SIGNIN_FACTOR`, `SmsLog`.
- **lib:** `phone.ts` (`normalizePhone` — Persian/Arabic digits, every Iranian spelling, `libphonenumber-js` min metadata; the account key, tested exhaustively), `loginCode.ts` (6 digits, HMAC-stored, 5 minutes, 5 attempts), `rateLimit.ts` (PD-15 — `askRateLimit.ts` generalized; `/ask` keeps its numbers), `sms.ts` + `smsProvider.ts` (the transport, the dev transport and its e2e outbox, the **stub adapter** that throws `SMS_PROVIDER_NOT_CONFIGURED`), `smsTemplates.ts`, `notify.ts` (never throws — each channel caught).
- **`capabilities.ts`:** `requiresSecondFactor(user)` — ADMIN, SALES, DESIGNER, DEVELOPER (PD-20).
- **`context.ts`:** `requireUser` refuses `PASSWORD_CHANGE_REQUIRED` while the flag is set (PD-10); `me`, `signOut`, `setNewPassword` use `requireUserAllowingPasswordChange`.
- **API:** `signIn(identifier, password)`; `verifySignInFactor`; `requestLoginCode` (always `true`, the send deferred past the response, `SMS_UNAVAILABLE` for every phone alike without a provider); `verifyLoginCode`; `setNewPassword`. Every former `sendMail` call site moved to `notify`. The invite takes a phone (email optional); the desk still shows the link.
- **CLI:** `create-admin --phone`, and `set-phone <email|phone> <new phone>` (PD-20's recovery path — the last ADMIN can never be locked out by a missing number).
- **Web:** one identifier field on sign-in, the factor screen, phone recovery → forced new password, the PD-18 banner for ADMIN, the phone field on the customer invite.
- **e2e:** `helpers.ts`'s `signIn` completes the factor from the outbox transparently, so every existing spec signs in unchanged; `10-phone-auth.spec.ts`.

## 2 · Found on review (Opus)

1. **An unhandled rejection could end the process.** `requestLoginCode` fired `void issueCode(...)` inside `setImmediate`, after the response; a failed token insert there was an unhandled rejection, which terminates Node by default. Now caught and logged.
2. **`setNewPassword` took any session.** It was meant as the second half of the SMS recovery, but it accepted any signed-in session, so a stolen cookie could replace the password without the current one and lock the owner out. It now refuses `PASSWORD_CHANGE_NOT_REQUIRED` unless a forced change is pending. A voluntary change, if one is built, asks for the current password.
3. **Sign-in timing said which accounts exist.** An unknown identifier returned before bcrypt ran; a known one after. `burnPasswordCheck` compares against a real hash of nothing, at the same cost. This was true of the email-only sign-in before J1 as well.
4. **The e2e suite could not sign in more than ten times.** The real budgets (10 per 15 minutes per identifier and per IP) tripped a third of the way into the suite, because the e2e API is one long process and every spec signs in from the same address. An e2e-only route (`POST /__e2e/rate-limits/reset`, behind `SMS_E2E_OUTBOX`, refused in production) resets the buckets before each sign-in. The limits themselves are proven in `rateLimit.test.ts` and `j1.test.ts`.
5. `publishTestRound` still signed in by email and did not complete the factor; the invite spec asserted English on a link that carries the new customer's locale (Persian by default); helper fetches met `ECONNRESET` on reused keep-alive sockets. All fixed.

The lane itself also found the SDL `Role` enum missing SALES and DESIGNER, independently of the S1 web lane (fixed once, on S1).
