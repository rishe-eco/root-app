# R3 · Library — the concept tree

**Branch:** `stage-r3-concepts`
**Needs:** R1 (the flat concepts), R2 (a public surface to hang the tree on).
**Blocks:** nothing. R4 uses concepts but does not need them nested.
**Shape:** small schema, disproportionate care. One nullable column and one integer, and about four ways to make an infinite loop.
**Spec:** `root-sot/ecosystem/working/root-website-research-lab.md` §2, §5; build plan §5 R3.

**Acceptance:** Root can add, rename, reorder and nest concepts from the desk, and cannot create a cycle. A public visitor sees the tree beside the Lab's list, hovers a node to surface its titles, and clicks to filter.

> **Placed here on purpose** — *"deliberately after there are entries worth an ontology"* (build plan §5). If the corpus is still a handful of entries when R3's turn comes, **say so and skip ahead to C1.** A tree over twelve entries is a worse product than a flat tag list, and building it early means designing the hierarchy before anyone knows what it should be.

---

## 1 · The migration is three columns

R1 left `parentId` out deliberately (§2.3: *"a column nothing reads is a column that will acquire a wrong meaning before it acquires a right one"*). It costs nothing to add now — nullable self-FK, no backfill, no data change.

```prisma
model LibraryConcept {
  // …existing…
  parentId String?
  parent   LibraryConcept?  @relation("ConceptTree", fields: [parentId], references: [id], onDelete: Restrict)
  children LibraryConcept[] @relation("ConceptTree")

  /// Sort position among siblings. Sparse on purpose — see §3.
  position Int @default(0)

  @@index([parentId, position])
}
```

**`onDelete: Restrict`, not `Cascade`.** Cascading a delete down a concept subtree also cascades `LibraryEntryConcept`, so deleting one mid-level node silently untags every entry beneath it. §4 is what happens instead.

---

## 2 · Cycles — the bug this stage exists to not have

Nothing in the schema stops `A.parent = B; B.parent = A`. A self-referential FK is perfectly happy with a cycle; the **renderer** is not, and neither is any recursive query. The failure is a hung request or a blown stack, in production, on a page a visitor loaded.

**Check on write, in `setConceptParent`:** walk from the proposed parent up through `parentId` until null; if you meet the node being moved, refuse with `CONCEPT_CYCLE`. Bound the walk (§2.1) so a cycle that somehow already exists cannot hang the checker that is supposed to find it.

```ts
/** Refuses a move that would make `id` its own ancestor. Bounded, because a
 *  cycle-detector that loops forever on an existing cycle is not a detector. */
async function wouldCycle(id: string, parentId: string | null): Promise<boolean> {
  if (!parentId) return false;
  if (parentId === id) return true;
  let cur: string | null = parentId;
  for (let hops = 0; cur && hops <= MAX_DEPTH + 1; hops += 1) {
    if (cur === id) return true;
    cur = (await prisma.libraryConcept.findUnique({
      where: { id: cur }, select: { parentId: true },
    }))?.parentId ?? null;
  }
  return true; // ran past MAX_DEPTH: treat as a cycle rather than allow it
}
```

**Returning `true` on exhaustion is deliberate.** The alternative — assume it is fine — is how a cycle gets committed by the code meant to prevent it.

### 2.1 · Cap the depth

`MAX_DEPTH = 6`, refused at the same site with `CONCEPT_TOO_DEEP`. Two reasons, and the second is the real one: it bounds every recursive read in §5, and **an ontology nested seven deep is not navigable** — the hover-to-surface interaction the spec asks for stops working long before the database minds.

This is a product constraint wearing a technical hat. Say so where it is defined, or someone will "fix" it by raising the number.

## 3 · Reordering, without rewriting every sibling

"Reorder" naively means `position = index` and a write per sibling on every drag.

**Use sparse positions.** Insert at `(prev.position + next.position) / 2`, spacing new nodes by 1000. One row written per move. When two neighbours land adjacent (no integer between), renumber that parent's children — rare, and local to one parent.

**Or take integers and rewrite the sibling list.** With a realistic ontology — tens of nodes, a handful of siblings each — this is genuinely fine, and it is simpler to reason about. *Recommendation: integers and a rewrite,* unless the tree grows past a few hundred nodes. Whichever you pick, **write down which and why**, because the next person will assume the other.

---

## 4 · Deleting a node that has children or entries

Three cases, and the spec answers none of them:

| | Behaviour | Why |
|---|---|---|
| Leaf, no entries | delete | nothing to lose |
| Has children | **reparent children to the deleted node's parent**, then delete | the alternative loses a subtree to a single click |
| Has entries | delete the tag links, keep the entries | `LibraryEntryConcept` cascades already; the entries are the corpus and are never collateral |

**Reparenting is the honest default.** A node vanishing takes its own meaning with it; it should not take its descendants' meaning too. If Root genuinely wants a subtree gone, deleting from the leaves up is explicit and takes as many clicks as it deserves.

**R1 already refreshes `searchText` for every entry linked to a deleted concept** (`deleteLibraryConcept`, `resolvers/library.ts:421`). Reparenting must keep that behaviour and add nothing: an entry's search text carries **its own** tags' titles, never its ancestors' — see §6.

## 5 · Entry counts — the decision that shapes the queries

Spec §2: *"Each node shows its entry count."* It does not say whether a parent counts its descendants' entries.

**Roll them up.** A parent whose children hold everything would otherwise show `0` beside a subtree of forty, which reads as an empty branch and is the opposite of what a map is for.

Which makes the count a **recursive** read, and gives R3 its one real query-shape decision:

- **Load the whole tree and roll up in memory.** Concepts number in the tens; one `findMany` plus a `groupBy` on `LibraryEntryConcept`, then sum upward in JS. **Recommended** — no recursive CTE, no raw SQL, no Prisma escape hatch, and `MAX_DEPTH` bounds the fold.
- **A recursive CTE.** Correct, and the right answer at a scale this will not reach. It needs `$queryRaw`, which nothing in this codebase uses yet, and it puts the count rule in SQL where `lib/` cannot test it purely.

**The public tree must count only publicly visible entries** — R2's `publiclyVisible`, applied to the `groupBy`. The desk tree counts everything. Two callers, one fold function, different filters passed in; not two folds.

---

## 6 · What R3 must not do to search

R1 bakes a concept's titles into every tagged entry's `searchText`, and refreshes on rename and delete. **Do not extend that to ancestors.** Tempting — "an entry under *Psychology › Emotion* should be findable by *psychology*" — and wrong three ways:

- Renaming a root concept would rewrite `searchText` for the entire corpus beneath it.
- Re-parenting a node would silently rewrite it again, for a set of entries nobody touched.
- The tree is the navigational answer to that need. Clicking *Psychology* filters to the subtree; that is what the tree is *for*.

If ancestor search is ever genuinely wanted, it belongs in the **query** (expand the concept filter to the subtree at read time), never in the stored haystack.

---

## 7 · The public interaction

Spec §2: *"hovering a node surfaces its related titles; clicking filters the list."*

**Hover must not fetch.** A request per hover is an N+1 driven by mouse movement. The tree query returns each node's titles — capped, `take: 8`, ordered by recency — in the same payload. The whole tree with eight titles a node is one small query for a corpus this size.

**Hover is not an interaction on touch, and not one for keyboard.** Whatever hover reveals must also appear on focus and on tap — otherwise the tree is mouse-only, which is the same class of gap the contract list already has (`02-contract-flow.spec.ts:124`, annotated `test.fail`). **Do not add a second one.** `:focus-visible` alongside `:hover`, and the panel reachable by tab.

**Filtering by concept is a URL, not component state**: `/:lang/library/research?concept=<slug>`. Shareable, back-button-correct, and R2's list already reads its filters from somewhere — extend that, do not add a parallel mechanism.

## 8 · Traps

**T1 · The desk tree and the public tree are the same fold, different filters.** One function, `buildTree(concepts, counts)`; the caller supplies the count filter. Two implementations drift, and the visible one will be the one that looks right.

**T2 · `position` is per-parent, not global.** `@@index([parentId, position])`, and every ordering query filters by parent first. A global position ordering appears to work until the first node is nested.

**T3 · Moving a node must revalidate depth, not just cycles.** Attaching a 3-deep subtree to a 4-deep parent makes a 7-deep tree without any single node exceeding the limit on its own. Check the depth of the **deepest descendant** of the moved node, plus the new parent's depth.

**T4 · `library.editTree` already exists and is already withheld from CONTRIBUTOR.** F3 provisioned it; R1 used it for rename and delete. R3 adds nesting and reordering under the same capability. **Creating** a concept stays `library.write` — R1's reasoning holds and is worth not re-litigating: a contributor filing an entry needs a tag that does not exist yet.

**T5 · Persian counts.** Node counts are counts, so `Intl.NumberFormat` via `formatCount` — not `num-latin`. See the R1 review: the entry list currently disagrees with its own pagination footer on this, and R3 should not add a third opinion.

## 9 · Tests

**Unit** — `buildTree` folds a flat list into a tree; rolls counts up through `MAX_DEPTH`; is stable under sibling reorder. `wouldCycle` for self-parent, direct A↔B, a 3-hop loop, and a legal deep move.

**Integration** — nesting A under its own descendant is refused with `CONCEPT_CYCLE`; exceeding `MAX_DEPTH` directly and *by moving a subtree* (T3) both refused; deleting a mid-tree node reparents its children and leaves entries intact but untagged; the public tree's counts exclude drafts and private entries; a CONTRIBUTOR is refused nesting and reordering but can still create.

**e2e** — an admin nests one concept under another and the public tree shows it nested with a rolled-up count; the hover panel is reachable by keyboard.
