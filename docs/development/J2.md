# J2 — requests: a project before a contract

**Built:** 2026-09-29 · **Plan:** `root-sot/ecosystem/working/root-studio-journeys-build-plan.md` §5 "J2"; lifecycle plan §0.3.4–5
**Branch:** `stage-j2-requests` — built by a Sonnet lane (`27ed799`, `8e31896`), reviewed by Opus

A customer submits a request from the contracts list; it sits as a pending row; opening it is a chat; sales archives it with a reason or converts it into a contract. A project can now hold **more than one contract** — the conversion is one route there, the Q5 "feature for an existing site" case the other.

## 1 · What was built

- **Migration `20260929150000_j2_requests`:** `ProjectStatus.REQUESTED`; the request columns on `Project`; `RequestMessage` in its own table (never shared with tickets or J3's staff notes — two audiences in one table is one missed filter from a leak); CHECK `Project_archived_has_reason` (hand-written, proven by insert); **`Contract.projectId` NOT NULL** — the migration `RAISE`s if any contract has no project, then sets it (its guard block is run over a project-less contract inside a rolled-back transaction by `j2.test.ts`); the FK becomes `Restrict`. `NO_PROJECT` and every null-project branch are gone.
- **API** (`resolvers/requests.ts`): `submitRequest`, `postRequestMessage` (`REQUEST_CLOSED` once not pending), `archiveRequest` (reason required), `myRequests`, `allRequests`, `request`; `createContract(projectId?)` converts a REQUESTED project or adds a contract to an ACTIVE one, in one transaction with the project row locked (`PROJECT_CUSTOMER_MISMATCH`, `PROJECT_ARCHIVED`). Rate limits on requests (10/day) and messages (60/hour) per account — every one of them notifies every sales account.
- **`lib/visibility.ts`:** `requestVisibleTo` — the customer who asked, or `contracts.readAll`; design and development never see requests. `canAuthorBuildOnProject` ignores discarded contracts.
- **Notifications** (`lib/notify.ts`): `REQUEST_SUBMITTED` (every active holder of `contracts.author` — `recipientsHolding(capability)`, now shared with feedback's recipients), `REQUEST_MESSAGE` (the other side), `REQUEST_ARCHIVED` (the customer, with the reason by email; SMS bodies carry no free text, so segment cost stays ours).
- **Web:** the portal's New request modal, request rows above contracts, the drawer chat (`?request=`, refetch on focus); the desk's `requests` inbox and thread, Archive, Convert → the create-contract form prefilled; the origin request as a read-only card on the contract.

## 2 · `firstContractId` is gone

It assumed one contract per project (L1 §2.3). Its replacements in `resolvers/admin/shared.ts`: `contractOnProject(projectId, named?)` (a named contract must be on that project — `NOT_FOUND` otherwise), `reloadOnProject`, `primaryContractId` (the first, `createdAt` then `id`), `linkContractId(projectId, audience)` (the newest live contract a link should point at), `assertProjectActive` (`PROJECT_NOT_ACTIVE`). **33 mutations take an optional `contractId`** and return the contract the caller names; the web always passes it (`useWorkspaceMutation` binds it per workspace). Two hidden one-contract assumptions the helper's name did not reveal were found and fixed: `executeScopeTrade`'s own "contract to amend" lookup (now the contract that agreed the outgoing item), and the portal `setScopeItem`'s `contracts[0]`.
