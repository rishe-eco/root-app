# V4 · Admin overview and review queue

**Branch:** `stage-v4-overview`
**Needs:** F2 (the section), and V1–V3 for there to be anything to read.
**Blocks:** nothing.
**Shape:** small. Three staff queries, one migration, one screen.
**Spec:** versioning §3 (Overview); build plan §4 V4.

**Acceptance:** the desk's Overview answers, without clicking into anything:
how many contracts are in each status, which ones are waiting on Root and for
how long, and what customers have done recently that Root should look at.

V4 is last because it reads only what the earlier stages produce. If it is built
early it invents its own state, and then V2 has to unbuild it.

---

## 1 · The three panels

**1.1 · Status tiles** — counts across every contract.

`contractStatusCounts` (`resolvers/query.ts:27`) **is not this query.** It is
scoped to `customerId: user.id`, so an admin calling it sees the count of their
*own* contracts, which is zero. Reusing it would produce a dashboard of zeroes
that looks like an empty database rather than a bug.

Add `allContractStatusCounts`, guarded by `contracts.manage`, with no customer
filter. Leave the existing query alone — the portal's chips use it.

**1.2 · The Needs-Root queue** — contracts in `WAITING_ON_ROOT`, longest-waiting
first. This needs a date the database does not currently have — see §2.

**1.3 · The review queue** — recent customer actions worth Root's attention,
read from `ChangeLog`. Defined in §3.

A global activity feed is the same query with no action filter; build it as one
resolver with an optional filter rather than two.

---

## 2 · `statusChangedAt` — the missing column (defect D7)

"Oldest first" needs to know when a contract entered its current status. Nothing
records it:

- `nudgeStatus` (`resolvers/contracts.ts:87`) writes `Contract.status` and
  **does not log**. Most status changes are automatic, so most of them leave no
  trace.
- Only the manual `setContractStatus` writes a `STATUS_CHANGED` entry.
- `updatedAt` is not a substitute: any write bumps it, including a customer
  ticking a scope item.

**Add a column rather than logging the nudge.** Logging it would put "Root
changed the status to Waiting on Root" into the customer's own history panel
immediately after their comment, which reads as bureaucracy rather than as
information — and the history panel is a customer-facing surface, not an
operational one.

```prisma
model Contract {
  // …
  /// When the contract entered its current status. Not updatedAt, which any
  /// write bumps — this is what the Needs-Root queue orders by, and a queue
  /// ordered by "was touched at all" is not a queue.
  statusChangedAt DateTime @default(now())

  @@index([status, statusChangedAt])
}
```

Migration: add with a default, then backfill existing rows from `updatedAt` —
the best available guess, and better than `now()`, which would tell the queue
every contract just arrived.

Both writers set it, **and only when the status actually differs**:

- `nudgeStatus` already early-returns when `contract.status === next`
  (`contracts.ts:89`) — add the field to the update it then performs.
- `setContractStatus` (`admin.ts:441`) does **not** check equality: setting a
  contract to the status it already has writes a `STATUS_CHANGED` log line and
  would reset the clock. Add the equality check there too, or the queue can be
  cleared by touching a dropdown.

## 3 · What belongs in the review queue

The spec's examples are "customer signed" and "customer re-chose concept,
approvals reset". Generalised: **things the customer did that change what Root
should do next.**

```ts
const REVIEW_ACTIONS: ChangeAction[] = [
  'SIGNED', 'RE_SIGNED', 'AMENDMENT_SIGNED',
  'APPROVED_CONTRACT', 'RE_APPROVED', 'AMENDMENT_APPROVED',
  'DESIGN_COMPLETE',
  'CHOSE_CONCEPT',      // may have reset a set of approvals
  'UNAPPROVED_PAGE',    // the customer took an approval back — always worth a look
  'COMMENTED',
];
```

Deliberately excluded: `APPROVED_PAGE` (routine progress, and there are four per
concept), `SCOPE_ON`/`SCOPE_OFF` (noise), and every action Root itself takes —
`CREATED`, `PUBLISHED`, `CONTRACT_REVISED`, `DESIGN_REVISED`, `STATUS_CHANGED`.
Those belong in the activity feed, not in a queue of things to respond to.

**Filter by actor as well as by action**, and note *which* mechanism that is: it
is `actorId === contract.customerId`, an **ownership edge**, not a capability
test. An admin who comments on a contract has not created work for Root, and
asking "does this actor hold `contracts.manage`" would get it wrong for anyone
holding a staff role for unrelated reasons — the same mistake F3 found and fixed
in `addComment` (house rule 2).

### There is no read/unread flag, and that is a decision

A "reviewed" flag is a whole workflow — who dismissed it, does it come back when
the customer acts again, is it per-person. Not in V4.

Instead the queue shows **the contract's current status beside each entry**, so
an entry whose contract has since moved to `WAITING_ON_CUSTOMER` has visibly
been handled. That is dismissal by state rather than by flag, it costs one extra
field, and it cannot go stale. Revisit only if it stops working in practice.

## 4 · Query surface

```graphql
"A contract, thin. Enough to name and link to one, and nothing more."
type ContractRef {
  id: ID!
  ref: String!
  titleFa: String!
  titleEn: String!
  status: ContractStatus!
  customerName: String!
  statusChangedAt: DateTime!
}

type ActivityItem {
  id: ID!
  contract: ContractRef!
  actor: User!
  action: ChangeAction!
  arg: String
  createdAt: DateTime!
}

type Query {
  "Staff. Counts across every contract — not the caller's own."
  allContractStatusCounts: [StatusCount!]!
  "Staff. Waiting on Root, longest-waiting first."
  needsRootQueue(limit: Int = 20): [ContractRef!]!
  """
  Staff. Recent activity across every contract. `reviewOnly` narrows it to
  customer actions that want a response.
  """
  activity(limit: Int = 40, reviewOnly: Boolean = false): [ActivityItem!]!
}
```

All three `requireCapability(ctx, 'contracts.manage')`.

## 5 · Traps

### T1 · `ContractRef`, not `Contract` — this is the whole performance story

If `ActivityItem.contract` were typed `Contract`, every row would resolve through
`contractInclude`: concepts, pages, every article, every comment and the **whole
change log**, per item. Forty rows would be forty full contract loads, several of
them the same contract, each dragging its own change log — the feed would be
reading itself.

`ContractRef` is a `select`, not an `include`. Same reasoning for
`needsRootQueue`: it is a list of links, not a list of documents.

This is the first place in the codebase where the "one include shape, fetched
once" convention is the wrong tool, and it is worth a comment saying so, because
the convention is otherwise right and someone will try to restore it.

### T2 · `ChangeLog` has no index for a global read

`@@index([contractId, createdAt])` serves the per-contract history. A query
across every contract ordered by `createdAt desc` has nothing. Add
`@@index([createdAt])`.

An `(action, createdAt)` composite does *not* help the review query — it filters
`action IN (…)` and orders by time, which a leading-column-on-action index
cannot answer in order. Take the simple one.

### T3 · The counts query and the queue disagree by design

`allContractStatusCounts` counts every contract including unpublished drafts;
`needsRootQueue` shows contracts a customer is waiting on. A contract in `DRAFT`
that has never been published appears in one and not the other. That is correct
and will be reported as a bug. Label the tiles clearly enough that it is not.

### T4 · Do not add a queue that needs V2 to be finished before it says anything

If V4 is built before V2 has been used in anger, every panel will be empty and
the temptation is to seed something. Do not. An empty Overview on a system with
one contract is accurate.

### T5 · `arg` is rendered on the client, in the reader's language

`ChangeLog` stores an action plus one variable argument; the sentence is built
client-side from the `log.*` namespace (`ContractDetail.tsx:117-150`). The desk
needs the same rendering, and it must not grow a second copy of that map — the
`changeAction.test.ts` drift test reads exactly one map, in `ContractDetail.tsx`,
and a second one would be invisible to it.

**Extract the map and the sentence-builder into a shared module** (e.g.
`apps/web/src/lib/changelog.ts`), have both screens import it, and update the
test's `actionKeyMap()` to read the new location. The test parses source text —
moving the map without updating the parser makes it fail loudly, which is the
correct outcome and is why it is safe to move.

### T6 · Persian numbers in tiles

Counts go through `Intl.NumberFormat('fa-IR')` — `lib/format.ts` already has the
locale tag helper. A tile showing "12" in a Persian page is a small tell that
nobody looked at it in Persian.

## 6 · Tests

**Integration:**

1. `allContractStatusCounts` counts contracts belonging to other people;
   `contractStatusCounts` still does not. Assert both in one test so the two can
   never be confused again.
2. `needsRootQueue` orders by `statusChangedAt` ascending, and a contract
   nudged into `WAITING_ON_ROOT` more recently sorts after one nudged earlier.
3. `setContractStatus` to the status a contract already has does **not** move
   `statusChangedAt`.
4. `activity(reviewOnly: true)` includes a customer's `COMMENTED` and excludes
   an admin's; excludes `APPROVED_PAGE`; includes `UNAPPROVED_PAGE`.
5. A customer calling any of the three gets `FORBIDDEN`.

**Unit:** none needed — this stage has no new pure logic beyond the action list,
and a test that restates a constant is not a test.

**e2e:** one — an admin sees a non-zero count on the Overview after the flow
spec has run. Keep it cheap; the value here is in the integration tests.
