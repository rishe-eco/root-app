## 0 · The scheduler decision, stated once, before anything else

`BillingEntry` existed since the first migration and was never surfaced.
Making it real means answering a question the plan poses directly:
**"generates entries each period" has nothing to run it.** This process is a
plain Express server; nothing in this codebase runs a job on a timer. Three
options were on the table:

1. **Lazy-on-read** — compute due periods when billing is opened.
2. **`npm run bill` under system cron** on the VPS.
3. **A real scheduler** (a queue, a worker process).

**Decided: lazy-on-read**, and the reason is the one the plan itself names —
it is the only one of the three that *cannot silently stop running*. A cron
entry can be missing after a deploy that forgot to reinstall it; a scheduler
process can die and nobody notices until a customer asks where an invoice
went. Lazy generation has no "is it still running" question: the next time
anyone opens billing — the portal's own rail, or the desk's report — the
entries that should already exist are computed and written before the read
returns. `lib/billing.ts`'s `ensureSubscriptionEntries` is the whole
mechanism, and `ensureDueEntriesFor` is its plural form for a staff-side read
spanning many customers.

**The cost, stated honestly:** a subscription accruing quietly with nobody
ever opening billing for it produces no entries until someone does. At this
volume — spec §8 names SMS as "the cheapest recurring probe" — that is an
acceptable trade, and it is the one the plan itself calls "almost certainly
right."

## 1 · What was built

### 1.1 · `Subscription`, and how it generates entries

One new model, one new enum (`SubscriptionPeriod`: `MONTHLY` | `QUARTERLY` |
`YEARLY`), owned by `User` (`customerId`) with an optional `projectId` — the
same nullable shape `Ticket.projectId` already uses (build plan L4's banked
trap): a subscription may track one engagement, or an ongoing customer
relationship with no single project to name.

`amount` is `BigInt`, Toman, per period — a flat recurring charge, never a
float. **"Amount or metered basis" was taken as amount only.** No
usage-tracking model exists anywhere in this schema (an SMS-send count,
say), and inventing one to back a "metered" option nothing yet measures
would be exactly the speculative-structure mistake this codebase's own
precedents refuse elsewhere (L1's deferred Milestone model, L4's
un-auto-generated ticket brief). This is recorded as a deviation from the
spec's literal wording, not a silent narrowing — see §3.

`activeFrom`/`activeUntil` are the active range; `activeUntil` null means
ongoing. **Ending a subscription (`endSubscription`) sets `activeUntil`
rather than deleting the row** — deleting would erase which periods were
ever billed under it, the same "financial history is not deleted" reasoning
that gives `BillingEntry` no delete mutation either.

`lib/billing.ts`'s `duePeriods(sub, asOf)` is the pure arithmetic: every
period whose start has passed, from `activeFrom` up to
`min(activeUntil, asOf)`, calendar-month aware (`addPeriod` uses
`setUTCMonth`, never a fixed day count, so a monthly subscription tracks the
calendar month rather than drifting by a day or two every few cycles). **A
period becomes due at its own start** — a subscription created "now" is due
for its first period immediately, which is intentional: the first charge is
the one that made the subscription real.

`ensureSubscriptionEntries` writes every due-and-unbilled period via
`prisma.billingEntry.createMany({ skipDuplicates: true })` against the
migration's own unique index (`BillingEntry_subscriptionId_periodStart_key`)
— **the idempotency guarantee is the database's, not the function's.** Two
concurrent reads computing the same due period each attempt the insert, and
Postgres drops the second one silently rather than the function needing to
catch a race. This is build plan L6's own banked trap named directly: "a
lazy generator that double-charges on a refresh is the worst bug in this
stage," and it is structurally impossible here, not merely tested against
(though it is also tested against — see §7).

### 1.2 · `BillingEntry` grown up

Four things were added to the existing, previously-unsurfaced model:

- **`SUBSCRIPTION`** joins `BillingSource`'s original three.
- **`subscriptionId`/`periodStart`/`periodEnd`** — set only for a
  subscription-generated entry; the unique index above lives on the first
  two.
- **`phaseId`** — the milestone linkage (spec §8: "the portal shows what
  each payment is gated on"). **No separate `Milestone` model was built.**
  `Phase.milestoneLabel` already exists as the free-text stand-in
  `schema.prisma`'s own comment named for "when L6 lands" — this stage
  reuses that row rather than inventing a second model for the one fact it
  would hold. See §3 for why this is a deviation worth flagging rather than
  hiding.
- **`ticketId`** (unique) — build plan L4's second banked trap, built here:
  the edge from a ticket Root marked billable to the charge it produces.

`descriptionFa`/`descriptionEn` for a subscription-generated entry are the
subscription's own bilingual label, unchanged — **no server-authored date
string is baked into them.** `periodStart`/`periodEnd` are real `DateTime`
columns instead, so the web renders "the period of ⟨start⟩–⟨end⟩" through
the locale-aware date helpers (house rule 14) rather than a Latin-digit date
sitting inside what is supposed to be translated prose.

### 1.3 · The billable-ticket edge (build plan L4's second banked trap)

`createTicketBillingEntry(ticketId, amount, descriptionFa, descriptionEn)` —
staff only. Refused `NOT_BILLABLE` unless `Ticket.billable` is set
(`setTicketBillable`, L4, is the only way to set it), and refused
`ALREADY_BILLED` if a charge already exists — the unique `ticketId` column
is the backstop a bypassed resolver could not get past. Built here, once,
exactly as L4 deferred it: "building it in both places means building it
twice."

### 1.4 · The general ledger mutation, and its one refusal

`createBillingEntry(customerId, contractId?, phaseId?, source, descriptionFa,
descriptionEn, amount)` authors a one-off entry — a contract milestone, a
manual service charge, a manual ticket charge. **`source: SUBSCRIPTION` is
refused (`INVALID_SOURCE`)** — those rows are only ever written by
`ensureSubscriptionEntries`, from a subscription's own periods. Letting this
mutation create one too would open a second door onto the exact row the
unique `(subscriptionId, periodStart)` index exists to keep singular.

`markBillingEntryPaid`/`unmarkBillingEntryPaid` toggle `paidAt` — the
decide/undecide shape `Dependency`'s own verify/unverify already uses, for a
mark-paid made in error. **No delete mutation exists for `BillingEntry` or
`Subscription`** — a charge or a subscription's billing history is a
financial record, and this codebase does not delete those (compare
`ScopeItem`, which stays `DECLINED` rather than disappearing).

### 1.5 · The report

`lib/billing.ts`'s `computeBillingReport` is a pure function over a list of
entries: `totalIssued`/`totalPaid`/`totalOutstanding`, and the same three
split by source. `Query.myBillingReport` (the caller's own) and
`Query.billingReport(customerId?)` (staff — one customer's, or across every
customer when `customerId` is omitted, spec §8: "for the desk, the same
query across customers") both catch up due subscription entries first, then
compute the report over what is actually in the database.

### 1.6 · The portal's `billing` rail goes live

`SOON` in `PortalLayout.tsx` drops `'billing'`; the link is now a plain
`NavLink` to `/app/billing`. `portal/Billing.tsx` (new) shows the report
(three tiles: issued/paid/outstanding), the caller's own subscriptions
(read-only — a customer never authors one), and every entry with its origin
named (subscription label, ticket subject, phase's `milestoneLabel`, or
contract ref) and its paid/outstanding state.

### 1.7 · The desk billing surface

`desk/Billing.tsx` (new): a customer filter, the same three-tile report
scoped to the filter, subscription authoring (create, end), ad hoc entry
authoring, and mark-paid/unmark-paid on every row. `DESK_SECTIONS` gains
`{ key: 'billing', capability: 'contracts.manage' }`, placed after `tickets`
and before the credential-issuing `apiTokens` section (which stays last on
its own existing precedent).

`desk/Tickets.tsx` gained the billing action in place, beside the billable
checkbox it already had — once `billable` is set and no charge exists yet, a
small inline form (amount) replaces the checkbox's neighbour; once a charge
exists, it shows the amount and paid/outstanding state instead. The action
lives where the flag lives, rather than duplicated on the billing screen.

## 2 · Decisions taken inside the stage

1. **A metered basis was not built.** Spec §8 says "amount or metered
   basis." No usage-tracking model exists in this schema for anything a
   subscription might meter (SMS sends, say), and building one to back an
   unused option would be speculative structure this codebase's own
   precedents refuse elsewhere. `Subscription.amount` is a flat recurring
   figure. Revisit when something in the system actually meters something.
2. **No separate `Milestone` model.** `BillingEntry.phaseId` reuses
   `Phase.milestoneLabel` — the free-text stand-in the schema already
   carried, explicitly named for this moment. A `Milestone` model holding
   only a label duplicates a fact `Phase` already states.
3. **Ending a subscription sets `activeUntil`; nothing is ever deleted.**
   `Subscription` and `BillingEntry` both have create/update/mark-paid
   mutations and no delete — the same reasoning `Dependency`'s hard-delete
   does *not* apply here: a financial record is evidence, not a mistake to
   be erased. (`Dependency`'s own precedent, §2 decision 4 of L5.md, is
   deliberately *not* followed here — the two domains differ on exactly this
   point.)
4. **`createBillingEntry` refuses `source: SUBSCRIPTION` structurally.**
   Not merely "unused" — actively refused with its own code
   (`INVALID_SOURCE`), so a client cannot open a second door onto rows the
   lazy generator's own uniqueness invariant depends on being written one
   way.
5. **No new capability was introduced.** `billing` reuses `contracts.manage`,
   matching every registry-adjacent surface since L1. Nothing in the plan
   asks for a narrower "billing only" staff persona.
6. **`allBillingEntries`'s `projectId` filter is an OR across four origins**
   (phase, contract, subscription, ticket) rather than one column — a
   `BillingEntry` names a project only indirectly, through whichever origin
   produced it, since the model predates `Project` (D1) and was never
   re-keyed to it directly.
7. **The billable-ticket charge is authored on the Tickets screen, not a
   second form on the Billing screen.** The flag and the action that follows
   from it live together; the Billing screen's own "add entry" form covers
   every other source.
8. **No `ChangeAction` values were added.** Creating, updating, marking
   paid/unpaid, or authoring a subscription does not write to `ChangeLog` —
   consistent with every prior stage's precedent for registry-adjacent
   activity.

## 3 · What was deliberately not built, and the one deviation flagged loudly

- **A metered basis** — see §2 decision 1. This is a narrowing of the
  spec's literal wording ("amount **or metered basis**"), recorded here per
  the brief's own instruction to flag deviations rather than let them pass
  silently.
- **A real `Milestone` model** — see §2 decision 2. `Phase.milestoneLabel`
  carries the one fact needed; a model would carry it a second time.
- **A payment gateway of any kind.** The schema's own comment on
  `BillingEntry` — "record-keeping only... separate from Hesab" — holds
  exactly as before. A subscription is the first thing that *feels* like it
  wants to charge a card on its own; nothing here does that. Every entry is
  created and marked paid by a human at Root, unchanged from the schema
  comment's original intent.
- **A customer-facing "subscribe me to this" flow.** All subscription
  authoring is staff-side, matching `createDependency`'s own precedent
  (L5 §2 decision 2) — the customer sees their own subscriptions and
  entries; they do not create either.
- **A notification when a new billing entry is generated or a subscription
  is about to renew.** The portal/desk surfaces show the current state on
  read; nothing pushes an email. Real future work, not invented ahead of a
  need the way L5 left overdue-dependency notifications for later.

## 4 · The migration

Hand-authored:
`apps/api/prisma/migrations/20260921150000_l6_billing/migration.sql`.

Derived from `npx prisma migrate diff --from-schema-datamodel <pre-L6 schema>
--to-schema-datamodel <post-L6 schema> --script`, cross-checked statement by
statement against the generated diff — same discipline as every prior stage.
**No correction for a NOT NULL-with-no-default trap was needed**:
`Subscription` is a brand-new table and starts empty, and every new column
on `BillingEntry` (`subscriptionId`, `periodStart`, `periodEnd`, `phaseId`,
`ticketId`) is nullable — a pre-existing entry has none of these and stays
legitimately absent forever for most rows.

**What the raw diff cannot express, and this file would normally add by
hand: nothing, this time.** Unlike L1/L4/L5's CHECK constraints, this
stage's one correctness rule — "a subscription's period is billed at most
once" — is a plain uniqueness rule, not a "these columns agree" rule, so
Prisma emits the unique index (`BillingEntry_subscriptionId_periodStart_key`)
on its own. There is no gap here a hand-written CHECK needed to fill.

`ALTER TYPE "BillingSource" ADD VALUE 'SUBSCRIPTION'` runs first and nothing
in this file's own DDL reads the new value in the same transaction — checked,
not assumed, the same note L4's migration recorded for `ADMIN_REQUEST`.

Applied for real, on this machine, to both `root_website` and
`root_website_test` via `npx prisma migrate deploy` — see §7.

## 5 · Traps, checked against what was actually built

1. **The scheduler decision is recorded, not merely made.** §0 above states
   it and the reasoning; `lib/billing.ts`'s own top comment restates it
   beside the code it governs, so a future reader hits the reasoning at the
   point of doubt.
2. **BigInt survives the wire.** Confirmed by the integration suite (§7):
   `Subscription.amount`/`BillingEntry.amount` and the report's three totals
   all cross GraphQL as strings (`fields.ts`'s `BillingEntry`/`Subscription`/
   `BillingReport`/`BillingSourceTotal` exports), and a test asserts
   `typeof amount === 'string'` on a nine-digit Toman figure, not merely
   that the value round-trips.
3. **No float ever touches a charge.** `lib/billing.ts`'s
   `isValidTomanAmount` refuses anything that is not a plain digit string
   before `BigInt(...)` is ever called — checked directly against `"100.5"`,
   `"-100"`, `"1e10"` in `billing.test.ts`, and against the same inputs
   through the GraphQL mutation in `l6.test.ts` (`INVALID_AMOUNT`).
4. **Lazy generation produces exactly one entry per due period, and is
   idempotent on repeated reads** — the trap the brief calls out as the one
   that matters most. Confirmed twice in `l6.test.ts`: a subscription's
   first read generates every period elapsed since `activeFrom`, and an
   immediate second read returns the identical set of entry ids, not a
   longer one. A third test issues two reads concurrently
   (`Promise.all`) and asserts, by reading the table directly, that no
   `periodStart` was ever billed twice — the property the unique index
   guarantees regardless of request ordering, not merely under a single
   thread's own accidental serialization.
5. **Keep the no-gateway boundary.** Confirmed by grep: no code path in this
   stage calls out to any external payment API, and `BillingEntry`'s own
   schema comment — "record-keeping only... separate from Hesab" — is
   unedited except to note what grew around it.
6. **House rule 2 (ownership vs. capability).** Every mutation in
   `resolvers/admin/billing.ts` gates on `requireCapability(ctx,
   'contracts.manage')`. `myBillingEntries`/`myBillingReport`/
   `mySubscriptions` gate on `requireUser` and filter by `customerId: user.id`
   in the `where` clause — an ownership edge, never a role test. Confirmed
   in `l6.test.ts`: a stranger's `myBillingEntries` returns an empty list,
   never another customer's rows.
7. **House rule 6 (API code, web sentence).** Every new `GraphQLError` in
   `resolvers/admin/billing.ts` carries a code
   (`NOT_BILLABLE`/`ALREADY_BILLED`/`INVALID_AMOUNT`/`INVALID_SOURCE`/
   `ALREADY_ENDED`/`NOT_FOUND`) plus an English `message`; the web never
   needs to render one of these as a sentence in the ordinary flow, since
   the desk forms make the wrong state hard to reach (an amount field
   accepting only digits, a bill action offered once).
8. **House rule 14 (digits).** `formatAmount` (Persian digits under `fa`)
   renders every Toman figure in both `portal/Billing.tsx` and
   `desk/Billing.tsx`; the amount `<input>`s carry `num-latin` (matching
   `DependenciesTab.tsx`'s own date inputs) since a figure being typed is a
   machine value, not a rendered one. Nothing in this stage renders a
   version, ref, or hash.
9. **The naming check against `desk/sections.ts`.** No new identifier
   contains the bare word "review." `billing` is the domain's own word, and
   it was never in tension with `review`/`reviewAdmin` to begin with.
10. **D5 stays decided.** `git diff -- apps/api/src/lib/gate.ts
    apps/api/src/lib/gate.test.ts` is empty. No line this stage added sets
    `approvedAt` or `chosenAt`.
11. **Bilingual strings.** Every new `en.json` key has an `fa.json`
    counterpart and vice versa, checked by the locale-parity unit suite
    (§7), which also caught one genuine mistake before it shipped: a
    "هر کدام" spelled with a space where the rest of the app spells it
    "هرکدام" — the parity suite's own "one sequence of Persian letters, one
    spelling" check, not a human proofread, is what found it.

**Not run, and why:**

- The founder's own manual smoke test — a real subscription accruing across
  real months, a real invoice reconciled against Root's own books — is
  outside what this session can run, the same limit every prior stage's
  verification section records.
- No dedicated Playwright spec drives `/app/billing` or `/desk/billing`

  29 pre-existing specs confirm this stage's schema and resolver changes did

  but the new screens' own correctness rests on the 11 integration specs
  exercising every resolver they call, a clean `vite build`, and reading the
  components — not on a browser-driven spec for either new screen. The same
  gap every prior stage's own verification section has left open for its
  own new screens (L3b's `Builds.tsx`, L4's `Support.tsx`/`Tickets.tsx`,
  L5's `DependenciesTab.tsx`).
