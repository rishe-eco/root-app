# R1 · Library — model and admin entry editor

**Branch:** `stage-r1-library`
**Needs:** F1 (storage), F2 (the desk), F3 (capabilities) — **all built**.
**Blocks:** R2 (the public reader has nothing to read until this fills the corpus), R3, R4.
**Shape:** medium-large. One new model cluster, one migration with two hand-written pieces, an upload-route change, and one desk section.
**Spec:** `root-sot/ecosystem/working/root-website-research-lab.md` §3, §4, §5, §7; build plan §5 R1.

**Acceptance:** Root can create a Library entry from the desk — type, bilingual metadata, translation provenance, rights basis, concepts — upload a hosted PDF where the rights allow it, be **refused** the upload where they do not, and publish it. A contributor can do all of that except publish. Nothing appears on the public site: R2 owns that.

---

## 0 · Read this first

Three things about this stage are different from everything in track V, and each one is a place the V-track habits are actively wrong.

**1 · This is the first content that is bilingual as *data*.** Every string in the product so far lives in `apps/web/src/i18n/locales/*.json` and is chosen by the reader's locale. A Library entry is not that. It carries a Persian title *and* an English title as columns, both present at once, and R2 will show them side by side on one page. **Entry content never goes near the locale files**, and the locale files never gain a key per entry. The `desk.library.*` namespace this stage adds is for the *editor's chrome* — labels, buttons, validation messages — and nothing else.

**2 · The public storage class has no read path.** `RESEARCH_TEXT` is `PUBLIC` (`lib/files.ts:88`), which means Nginx serves those bytes straight off disk and **the API is never in the request**. Every rule about who may read a hosted PDF has to be enforced when the file is *offered*, because at read time there is no code left to consult. Build plan §6.9 says this; §1 below is what it means concretely, and it is the single most important section in this file.

**3 · R1 is admin-only and must stay that way.** Do not touch `App.tsx`'s public routes, `Nav.tsx`'s locked `cast` slot, or the `nav.locked` string. R2 opens the content lock, and it does so by restructuring routes in a way that is much easier to review on its own. If you find yourself editing a public page in this stage, stop.

## 1 · The rule that shapes the schema

The spec asks for two flags that each decide whether bytes may be world-readable, and **it never makes them meet**:

- **§3 — rights basis.** `LINK_ONLY` means "no hosted file — abstract, Root's note, and a link out."
- **§4 — visibility.** An entry in the private register is "never surfaced here."

Take them together and there is a state the spec describes but does not resolve: **a `PRIVATE` entry with a hosted PDF.** The entry is invisible in every list, every search, and every reader view — and its full text is sitting at a public URL that Nginx will serve to anyone who asks. The entry being hidden hides the *link*, not the *file*. This is the same failure as `LINK_ONLY` with a file, arriving down a different road, and the spec only guards the first road.

So both rules are one rule, and it is worth stating in exactly one place:

> **A hosted file may exist only when the entry is `PUBLIC` **and** its rights basis is not `LINK_ONLY`.**

### 1.1 · Which side the foreign key goes on decides whether this is expressible

This is the part to get right before writing any Prisma, because reversing it later is a data migration.

A `CHECK` constraint can only see **one row of one table**. If the association is modelled the obvious way — `StoredFile.entryId`, matching the existing `StoredFile.contractId` — then the constraint needs `rightsBasis` and `visibility` from `LibraryEntry` while sitting on `StoredFile`, and that is not a CHECK. It is a trigger, or it is a rule enforced only in application code, which build plan §6.9 has already ruled insufficient.

**Put the reference on the entry:**

```prisma
fullTextFileId String?     @unique
fullTextFile   StoredFile? @relation("EntryFullText", fields: [fullTextFileId], references: [id], onDelete: Restrict)
```

Now `rightsBasis`, `visibility` and `fullTextFileId` are three columns of one row, and the rule is a single CHECK:

```sql
ALTER TABLE "LibraryEntry" ADD CONSTRAINT "LibraryEntry_hosted_text_is_publishable"
  CHECK (
    "fullTextFileId" IS NULL
    OR ("rightsBasis" <> 'LINK_ONLY' AND "visibility" = 'PUBLIC')
  );
```

Note what this buys beyond refusing a bad insert: **it also refuses the bad *update*.** Flipping a hosted entry to `LINK_ONLY`, or to `PRIVATE`, fails at the database unless the file reference is cleared first — which forces the mutation to deal with the bytes rather than silently orphaning them. That ordering is the whole point, and §4.3 is where it gets handled.

`onDelete: Restrict` matches how `DesignConcept` holds its image: a file a published entry depends on cannot be deleted out from under it.

**One asymmetry to expect and not "fix":** `StoredFile.contractId` exists and points the other way, because a contract has *many* files and the private read path needs the edge on the file. An entry has *one* full text and needs the edge on the entry. Two different shapes for two different problems — do not unify them.

## 2 · Schema

```prisma
enum EntryType {
  PAPER           // peer-reviewed
  BOOK
  ARTICLE         // article / web
  ROOT_RESEARCH   // Root's own — "distinct: grown here" (spec §2)
}

enum TranslationProvenance {
  PUBLISHED   // an existing translation; cite translator + edition
  ROOT        // Root translated it; labelled as such
  NONE_YET    // original only; a reader may request one
}

enum RightsBasis {
  PUBLIC_DOMAIN
  OPEN_LICENCE
  PERMISSION_GRANTED
  LINK_ONLY
}

enum EntryVisibility { PUBLIC PRIVATE }

model LibraryEntry {
  id   String @id @default(cuid())
  /// The public reader's URL segment (R2). Unique, immutable once published —
  /// a URL that has been handed out is not free to change.
  slug String @unique
  type EntryType

  // ---- the work, in its own language ----
  /// BCP-47-ish tag ("fa", "en", "de"). Deliberately NOT the app's Locale
  /// enum: the app has two UI languages, the corpus has as many source
  /// languages as it has sources, and conflating them caps the Library at two.
  originalLang     String
  titleOriginal    String
  /// Free text, as written on the paper. Not a relation, not an array —
  /// author disambiguation is a research-data problem this stage is not solving.
  authors          String
  venue            String?
  year             Int?
  doi              String?
  sourceUrl        String?
  abstractOriginal String?

  // ---- the translation ----
  /// Required, no default. See §2.1.
  translationProvenance TranslationProvenance
  titleTranslated       String?
  abstractTranslated    String?
  /// Where the "published" state's credit goes: translator, edition, link.
  translationCredit     String?

  // ---- rights ----
  /// Required, no default. See §2.1.
  rightsBasis    RightsBasis
  /// OPEN_LICENCE records the licence URL; PERMISSION_GRANTED records where
  /// the yes is. Both optional in the schema, both prompted by the editor.
  rightsNote     String?

  // ---- the hosted text (§1.1: the edge lives here) ----
  fullTextFileId String?     @unique
  fullTextFile   StoredFile? @relation("EntryFullText", fields: [fullTextFileId], references: [id], onDelete: Restrict)

  visibility  EntryVisibility @default(PUBLIC)
  /// Null means draft. Set by `publishLibraryEntry`, which needs `library.publish`.
  publishedAt DateTime?

  /// Normalized haystack, maintained on write. See §5.
  searchText String @default("")

  concepts LibraryEntryConcept[]

  createdById String
  createdBy   User   @relation(fields: [createdById], references: [id])

  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt

  @@index([publishedAt, visibility])
  @@index([type])
}

model LibraryConcept {
  id      String @id @default(cuid())
  slug    String @unique
  titleFa String
  titleEn String

  entries LibraryEntryConcept[]

  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt
}

/// Explicit join model rather than an implicit m-n: R3 will want ordering and
/// possibly a "primary concept", and an implicit relation cannot grow columns.
model LibraryEntryConcept {
  entryId   String
  conceptId String
  entry     LibraryEntry   @relation(fields: [entryId], references: [id], onDelete: Cascade)
  concept   LibraryConcept @relation(fields: [conceptId], references: [id], onDelete: Cascade)

  @@id([entryId, conceptId])
  @@index([conceptId])
}
```

### 2.1 · Two enums with no default, and why that is the whole point

`translationProvenance` and `rightsBasis` are **required with no `@default`**. This is not an oversight to tidy up later — it is the mechanism, and the spec says so twice in the same words: *"always shown, never implied"* only holds if omission is impossible, and **a defaulted field is omission with a friendly face.**

Concretely: a default on `rightsBasis` means an entry can be created without anyone deciding what Root is allowed to do with the source, and the value it lands on will look like a decision to every later reader. The same for provenance — a defaulted `NONE_YET` publishes "original only" about a work someone may well have translated.

`visibility` **does** carry `@default(PUBLIC)`, per spec §4, and the contrast is deliberate: the Lab is a public library, so public is the honest default, and the private register is protected by the entry being a **draft** (`publishedAt` null) until someone publishes it deliberately. If that ever stops feeling safe, the fix is to flip this default, not to add a fourth flag.

### 2.2 · Three axes, and they are orthogonal

Do not collapse these, and do not derive one from another:

| Axis | Field | Question | Who moves it |
|---|---|---|---|
| Editorial | `publishedAt` | is it finished? | `library.publish` |
| Register | `visibility` | may the world see it at all? | `library.write` |
| Rights | `rightsBasis` | may we host the text? | `library.write` |

A public reader sees an entry when `publishedAt != null` **and** `visibility = PUBLIC`. That test lives in **one** helper — see §4.1 — the same way `loadForActor` is the one ownership edge for contracts.

### 2.3 · Concepts are flat in R1

R3 owns the tree: hierarchy, reordering, hover-to-surface-titles. R1 needs concepts only as **tags**, because an entry carries them (spec §3) and the editor has to set them.

**Do not add `parentId` now.** R3's migration is a nullable self-relation with no backfill and no data change — it is genuinely free later, and a column nothing reads is a column that will acquire a wrong meaning before it acquires a right one. The one thing R1 *does* pay forward is the explicit join model above, because that cannot be changed cheaply.

## 4 · Server surface

### 4.1 · One visibility helper, and every read goes through it

```ts
// lib/library.ts
/** The public reader's test, in one place. R2 will import this; nothing
 *  should ever inline `publishedAt: { not: null }` beside its own idea of
 *  visibility. */
export const publiclyVisible = { publishedAt: { not: null }, visibility: 'PUBLIC' } as const;
```

Staff reads are the un-filtered set, gated by `library.write`. This is the same split as contracts — the capability decides whether you may use the surface, the filter decides which rows come back — and the same rule applies: **never merge them** (house rule 2).

### 4.2 · Mutations

All guarded with `requireCapability`. The verb column is the whole reason F3 exists:

| Mutation | Capability |
|---|---|
| `createLibraryEntry(input)` | `library.write` |
| `updateLibraryEntry(id, input)` | `library.write` |
| `deleteLibraryEntry(id)` | `library.write` |
| `setEntryConcepts(id, conceptIds)` | `library.write` |
| `detachEntryFullText(id)` | `library.write` |
| `publishLibraryEntry(id)` | **`library.publish`** |
| `unpublishLibraryEntry(id)` | **`library.publish`** |
| `createLibraryConcept(input)` | `library.write` |
| `updateLibraryConcept(id, input)` | **`library.editTree`** |
| `deleteLibraryConcept(id)` | **`library.editTree`** |

Two of these are worth arguing about now rather than in review:

- **`createLibraryConcept` is `library.write`, not `editTree`.** A contributor filing an entry will need a concept that does not exist yet, and forcing them to stop and ask an admin makes the tag field useless in practice. *Creating* one is part of writing; *renaming, nesting and deleting* one is tending the ontology, which is R3's verb. If the founder wants creation locked down too, it is a one-line change — but it should be a decision, not a default.
- **`publishLibraryEntry` must re-run the §1 rule.** The CHECK already refuses a bad row, but publishing changes `publishedAt`, not the three columns the CHECK reads, so the database will not stop you publishing an entry whose state was fine when it was a draft. There is no such state today — `visibility` and `rightsBasis` are checked on every write — but "the constraint covers it" is exactly the reasoning that goes stale. Assert it in the resolver too.

### 4.3 · Changing rights or visibility on an entry that has a file

This is where the CHECK earns its place, and where the resolver has real work:

```
updateLibraryEntry sets rightsBasis = LINK_ONLY (or visibility = PRIVATE)
  → entry.fullTextFileId is not null
  → the UPDATE will be refused by the database
```

**Do not catch that error and reword it.** Handle it before the write, in a transaction:

1. Read the entry.
2. If the change would make hosting illegal and a file is attached, **delete the bytes** (`storage.remove(key)`) and the `StoredFile` row, and null `fullTextFileId`.
3. Apply the update.

Deleting the bytes is not optional and not deferrable to a cleanup job. The file is at a public URL that Nginx serves without asking anyone; leaving it on disk means the entry says "link only" and the PDF is still there for whoever noted the URL. **Nulling the foreign key changes the database's opinion, not the world's.**

The transaction matters for the same reason V2's publish paths became transactional (defect D2): a crash between the delete and the update leaves a row pointing at bytes that are gone.

### 4.4 · Queries

```graphql
type Query {
  "Staff. Every entry, drafts included. Thin — see T1."
  libraryEntries(search: String, type: EntryType, limit: Int = 50, offset: Int = 0): LibraryEntryPage!
  "Staff. One entry, in full, for the editor."
  libraryEntry(id: ID!): LibraryEntry
  "Any staff. The tag picker needs these; R3 gives them a tree."
  libraryConcepts: [LibraryConcept!]!
}
```

**`libraryEntries` is paginated from the first commit.** Defect D10 is `allContracts` fetching the full detail shape for every contract, unbounded — recorded as debt because contracts are few and Root-created. The Library is the corpus that is *meant* to grow, and a list screen written the same way is the same bug with a worse ceiling. Return a thin row type (id, slug, type, titles, year, provenance, rights, published, concept count) — not the full entry, and above all not the abstract.

## 5 · Search — the spike, and its actual finding

Build plan §5 asks for a search spike here rather than a discovery in R2, and §6.7 flags Persian search quality as a *product* risk. Having looked: **the risk is not stemming. It is that Persian text does not compare equal to itself.**

### 5.1 · The real problem

The same Persian word is routinely stored as several different byte sequences, and Postgres has no opinion about it:

| | Codepoint | Looks identical to |
|---|---|---|
| Arabic yeh **ي** | U+064A | Persian yeh **ی** U+06CC |
| Alef maksura **ى** | U+0649 | Persian yeh **ی** U+06CC |
| Arabic kaf **ك** | U+0643 | Keheh **ک** U+06A9 |
| ZWNJ (نیم‌فاصله) | U+200C | *nothing — it is invisible* |
| Tatweel **ـ** | U+0640 | *nothing — it is decorative* |
| Harakat | U+064B–U+0652 | *nothing — optional vowel marks* |
| Arabic-Indic **٠١٢** | U+0660+ | Persian **۰۱۲** U+06F0+ |

Consequences, all of which read as "the search is bad" rather than as a bug:

- A visitor on an **Arabic keyboard layout** — which is what most non-Iranian Arabic-script users have, and what several phone keyboards default to — types «كتاب» with U+0643 and finds nothing, because Root typed «کتاب» with U+06A9.
- «می‌رود» (with ZWNJ), «میرود» and «می رود» are three different strings.
- Pasting from a PDF brings harakat and tatweel along.

**None of this is fixed by a better stemmer**, and all of it is fixed by folding both sides before comparing.

### 5.2 · What to build

A SQL folding function, added by hand to the migration (§3.2):

```sql
-- Fold Persian/Arabic orthographic variants so text compares equal to itself.
-- IMMUTABLE because a generated column or an index would require it, and
-- because it genuinely is: same input, same output, forever.
CREATE OR REPLACE FUNCTION library_fold(t text) RETURNS text AS $$
  SELECT lower(
    translate(
      regexp_replace(coalesce(t, ''), '[ً-ْـ‌]', '', 'g'),
      'ىيكأإآ٠١٢٣٤٥٦٧٨٩۰۱۲۳۴۵۶۷۸۹',
      'ییکااا01234567890123456789'
    )
  );
$$ LANGUAGE sql IMMUTABLE STRICT;
```

**Verify the two `translate` arguments are the same length in characters before trusting this.** `translate` maps position to position and silently *deletes* any character in the first string that has no partner in the second — so a miscount does not error, it quietly removes letters from the corpus. Count them in a test (§7, unit test 1), not by eye. The escape syntax for `\u` in `regexp_replace` also differs between Postgres versions and `standard_conforming_strings` settings; check what actually landed by selecting the function's output, not by reading the migration.

`LibraryEntry.searchText` is then maintained **in application code on every write**: concatenate the fields worth searching (both titles, authors, venue, both abstracts, concept titles) and store `library_fold(...)` of the result. Query it with `ILIKE '%' || library_fold($1) || '%'`, folding the needle the same way.

### 5.3 · What deliberately is *not* built

**No `tsvector`, no GIN index, no generated column — yet.** All three were considered and all three are premature:

- The corpus will hold **tens of entries** at the end of R2, not millions. A sequential scan over a folded text column is instant at that size, and an index that is never the bottleneck is pure carrying cost.
- A generated `tsvector` column is something Prisma does not model, so it has to be hand-written and then defended against `migrate diff` on every subsequent migration.
- The two-configuration question the build plan raises — English stemming wants `to_tsvector('english', …)`, Persian has no usable stemmer and wants `'simple'` — is a **real** question, and it is answerable much better once there is a corpus to test recall against. Answering it now means guessing.

**Record this as a deliberate deferral, with its trigger:** when the corpus passes a few hundred entries, or when R2's public search is measurably slow, revisit — and at that point the folding function is still the foundation, because a `tsvector` built over unfolded Persian has exactly the same equality bug with a faster index on top of it. The correctness work done here is not thrown away by the performance work done later. That is why it is the half worth doing first.

If you do reach for `to_tsvector` later: use the **two-argument** form. The one-argument form reads the config from a session GUC, which makes it non-`IMMUTABLE` and therefore illegal in a generated column or index — the error message when this bites is unhelpful.

## 6 · The upload path needs a change, and it is not cosmetic

F1 built the route to serve one consumer. `POLICY.RESEARCH_TEXT` already exists (`lib/files.ts:88`) with the right visibility, size and type — but it carries `requiresContract: false` (`:95`), and **there is no other owner field**. As it stands, a `RESEARCH_TEXT` upload names nothing, so there is nothing to check the §1 rule against.

**Generalise the owner, do not special-case the entry.** `requiresContract: boolean` becomes something the policy can express for either owner:

```ts
/** Which owning row an upload must name. The rules that decide whether a file
 *  may exist at all live on that row, so an upload that names nothing cannot
 *  be checked — see build plan §6.9. */
owner: 'contract' | 'entry';
```

The route then, for `entry`:

1. Load the entry. Missing → 404 (**"no such thing", not "not allowed"** — house rule 13).
2. **Refuse if `rightsBasis === 'LINK_ONLY'` or `visibility === 'PRIVATE'`**, with a chosen error code (`RIGHTS_FORBID_HOSTING`). This is §1's rule at the only moment it can be enforced.
3. Refuse if the entry already has a file — replacing is `detachEntryFullText` then upload, so that the delete of the old bytes is explicit rather than implicit.
4. Sniff, size-check, store, create the `StoredFile`, set `fullTextFileId`.

Steps 2 and 4 must be one transaction with the file write, or an entry flipped to `LINK_ONLY` concurrently gets a hosted file anyway. The CHECK catches it at the final update — which is the backstop working as designed — but the bytes are on disk by then and must be cleaned up. **Write the storage first, the row second, and delete the bytes if the row fails.** `storage.put` before `prisma.create` is the correct order precisely because the compensating action for an orphaned file is possible and the one for an orphaned row is not.

## 7 · The desk section

One new row in `DESK_SECTIONS` (`apps/web/src/desk/sections.ts`):

```ts
{ key: 'library', capability: 'library.write' },
```

That is the whole access story on the client. The nav, the index redirect and the route guard all read this table (F2), so a section cannot be visible-but-locked or reachable-but-hidden. **The server is still the authority** — the client guard is there so a contributor does not see a door that opens onto a `FORBIDDEN`.

Screens:

- **`/desk/library`** — the entry list. Search box, type filter, paginated. Draft and published both shown, visibly distinguished.
- **`/desk/library/new` and `/desk/library/:id`** — the editor. One screen, sections for metadata / translation / rights / full text / concepts.
- **`/desk/library/concepts`** — a flat list with create. Rename and delete are `library.editTree` and render disabled without it; R3 turns this into the tree.

**The editor forces both choices.** Translation provenance and rights basis render as required radio groups with **no preselection**, and save is refused until both are answered — the client half of §2.1. A preselected radio is a default wearing a different hat.

**i18n:** a `desk.library.*` namespace, both locale files, every string. Persian is never letter-spaced and never uppercased (house rule 6). Entry *content* is not in these files (§0.1).

**Numbers** — counts, years, page counts — through `Intl.NumberFormat` with the locale tag, as V4's tiles do. A year is the one place to consider `num-latin` instead: «۱۹۹۸» for a paper's publication year is correct Persian typography but unhelpful next to a DOI. Pick one, write down which, and be consistent.

## 8 · Traps

### T1 · The list query is where this stage's performance is decided

See §4.4. `libraryEntries` returning full entries with abstracts is D10 rebuilt on a corpus designed to grow. Thin row type, paginated, from the first commit — retrofitting pagination once R2's reader is written against an unpaginated shape is two stages of churn.

### T2 · `originalLang` is not the app's locale

The app has two UI languages. The corpus has as many source languages as it has sources — a German paper with an English translation is an ordinary entry. Typing `originalLang` as the `Locale` enum caps the Library at two languages and will be discovered by the first entry that is neither.

### T3 · Deleting an entry does not delete its bytes

`onDelete: Restrict` on `fullTextFile` means the *file* cannot be deleted while an entry points at it — it says nothing about the reverse. `deleteLibraryEntry` must remove the file (storage + row) before deleting the entry, or the bytes stay at a public URL forever and the only record of what they were is gone. Same reasoning as §4.3, opposite direction, and much easier to miss.

### T4 · A slug is a URL, and R2 will hand it out

`slug` is unique and is the reader's URL segment. Generate it from the title, allow an override, and **stop allowing changes once `publishedAt` is set** — or accept that R2 ships with broken external links. Decide now; it is a validation rule in this stage and a redirect table in a later one.

Persian titles need real thought here: a transliterated slug and a percent-encoded Persian slug are both defensible, and «یادگیری-ماشین» in a URL bar is not obviously worse than `yadgiri-mashin`. Pick one, write down why. *(Every existing route segment in this app is ASCII, so this is the first one that isn't.)*

### T5 · The private register is the reason `visibility` exists — do not make it a folder

Spec §4 is explicit: *"visibility is a field on the entry, not a folder someone must remember to check."* The temptation, once there are a hundred entries, is a "private" collection or a separate list screen. Both re-introduce the failure the field was chosen to prevent — an entry ending up in the wrong place because someone filed it there rather than flagged it.

### T6 · `library.publish` is withheld from CONTRIBUTOR, and the editor must degrade honestly

A contributor opens the same editor and sees a disabled publish control with a reason, not a hidden one and not a control that errors on click. F2's pattern is the reference: the section nav hides what you cannot reach, but inside a screen you can reach, a thing you cannot do is shown as unavailable.

### T7 · Do not put entry text in the locale files

Stated in §0 and repeated because it is the mistake this stage is *structurally* set up for: the editor's labels go in `en.json`/`fa.json`, and every reflex built over the last six stages says "user-facing string → locale file". Entry titles and abstracts are **rows**.

### T8 · `searchText` goes stale silently

It is maintained on write. Every path that changes a searchable field — including `setEntryConcepts`, which changes concept titles' contribution — has to rebuild it. Build it in **one** function (`buildSearchText(entry, concepts)`) called from every write, rather than inline at each site (house rule 3). A stale haystack does not error; it just fails to find things, which is the hardest class of bug to notice in a feature whose job is not finding things.

## 9 · Tests

**Unit** (`src/lib/*.test.ts`, pure, no DB):

1. **`library_fold`'s character table is balanced** — the two `translate` arguments have equal character length. This is the test that stops the function silently deleting letters (§5.2). Assert on the SQL text if the function is not reachable without a database; assert on both if it is.
2. `buildSearchText` includes both titles, authors, and concept titles, and folds them.
3. Slug generation: Persian title, duplicate collision, override.

**Integration** (`src/test/`, real Postgres):

4. Creating an entry **without** `rightsBasis` or `translationProvenance` is refused by GraphQL (they are non-null in the SDL) — the schema-level half of §2.1.
5. **`LINK_ONLY` + a file is refused at upload** with `RIGHTS_FORBID_HOSTING`, and no `StoredFile` row and no bytes are left behind. This is build plan §6.9, held by a test.
6. **`PRIVATE` + a file is refused the same way.** The road the spec did not guard (§1).
7. Flipping a hosted entry to `LINK_ONLY` **deletes the bytes**, not just the reference — assert `storage` no longer has the key (§4.3).
8. The same for flipping to `PRIVATE`.
9. `deleteLibraryEntry` on a hosted entry removes the file (T3).
10. A `CONTRIBUTOR` can create and update an entry, and is refused `publishLibraryEntry` with `FORBIDDEN`.
11. A `CUSTOMER` is refused every Library query and mutation.
12. `publiclyVisible` excludes a draft, excludes a `PRIVATE` published entry, and includes a published public one — the three cases of §2.2 in one test.
13. **Search finds an entry typed with Arabic yeh/kaf when it was stored with Persian ones, and vice versa** (§5.1). This is the test that would have caught the whole class.

15. `libraryEntries` respects `limit`/`offset` and does not return abstracts (T1).
