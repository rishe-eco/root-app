# L4 — Ratified item → change ticket; the three channels

**Stage:** L4 of `ecosystem/working/root-studio-lifecycle-build-plan.md` (1.0),
**§3 "L4 · Ratified item → change ticket; the three channels"**.
**Depends on:** L3b (`FeedbackItem.status`, ratification, the resolution
ledger). **Spec:** `root-website-project-lifecycle.md` §5 (the three
channels), §6 (the brief), §10.2 (admin as a product, parked). **Standing
constraint:** D5 (never write `PageDesign.approvedAt` / `DesignConcept.chosenAt`).
**Status:** built, verified against a real database, including a shadow-
database migration replay.

---

## 0 · Why this stage, stated once

`Ticket`/`TicketMessage` have existed since the very first migration and were
never reachable from the API. This stage surfaces them, adds the fourth
channel (`ADMIN_REQUEST`) beside the original three, and builds the one
mechanism the plan calls out as the actual point: **a ratified feedback item
becomes a ticket that is already usable as a brief**, so "faster to fix it
myself than write the brief" stops being true. If the generated ticket were
not actually usable as a brief, this stage would have failed even while
compiling — see §1.2 for what "usable" was taken to mean.

## 1 · What was built

### 1.1 · `Ticket` grown up, and the fourth channel

`TicketType` gains `ADMIN_REQUEST` — site administration Root does not
currently sell, per spec §10.2. It is never a customer's own choice at
`createTicket` (`INVALID_TICKET_TYPE`, `lib/ticket.ts`'s
`canChooseTicketType`): nobody arrives already knowing their request is one
Root does not sell, so a customer files an ordinary support ticket and staff
reclassify it via `moveTicketChannel` once it is recognized as one — spec
§5's "an item entering the wrong channel is moved, not handled," applied to
the one channel this stage actually builds a door between.

`Ticket.projectId` is new and nullable — the banked trap, taken exactly as
named: `Ticket.customerId` already points at a user; a change ticket derived
from a demo now belongs to a project too, while a support ticket raised
after delivery may have none. Both fields exist on the row, decided here
rather than inherited as one ambiguous edge.

**`Ticket.billable → BillingEntry` was not built.** The flag itself
(`billable: Boolean`) already existed in the schema and is now toggleable
(`setTicketBillable`), but nothing reads it and no `BillingEntry` is ever
created from it — the plan's own second banked trap, explicit that this edge
belongs with L6's billing work and building it here would mean building it
twice.

### 1.2 · The brief — what "usable" was taken to mean

`createTicketFromFeedback(itemId, currentState, desiredState, lang)` converts
a `RATIFIED` `FeedbackItem` into a `CHANGE_REQUEST` ticket, snapshotting five
things onto the new row at conversion time (never a live view — the same
reasoning `DemoFrameLine.textFa`/`textEn` and Appendix 1 already use):

| Field | Source | Who supplies it |
|---|---|---|
| `briefPageFa`/`briefPageEn` | the target's own label (`DemoPage.labelFa`/`labelEn`, or a frame line's own `textFa`/`textEn`) | compiled automatically — `lib/ticket.ts`'s `briefPageFromTarget` |
| `briefAnnotation` | every `FeedbackComment` on the item, verbatim, oldest first, each prefixed with its author's name | compiled automatically — `compileAnnotation` |
| `briefCurrentState` | what the page shows today | **written by whoever performs the conversion** |
| `briefDesiredState` | what it should show instead | **written by whoever performs the conversion** |
| `briefLang` | which language the last two were written in | supplied alongside them |

**Why current/desired state are not auto-generated.** The plan lists four
things a brief carries — page, annotation, current state, desired state —
as facts already in hand. Two of them genuinely are (the page's own label,
the comment thread). The other two are not: synthesizing "what it looks like
now vs. what it should look like" from a pile of unstructured comments would
be inventing structure the raw data does not have, exactly the reasoning
L3b applied to *not* auto-generating a bilingual `DemoFrameLine` from a raw
build note (`docs/development/L3b.md` §1.4). So this stage asks a person for
two short fields rather than fabricating them — and because the page and the
annotation arrive pre-compiled, "faster to fix it myself than write the
brief" is measured against writing two sentences, not a document.

Refused `NOT_RATIFIED` unless the item is currently `RATIFIED` — the same
gate L3b's `declareBuild` applies (D3's ratification is still the door), and
refused `ALREADY_CONVERTED` if a ticket already exists for the item (the
unique `sourceFeedbackItemId` is the database backstop).

### 1.3 · Moving a ticket between channels — a first-class action

`moveTicketChannel(ticketId, type)` updates the row's `type` in place.
"First-class, not a copy-paste" (spec §5) is taken literally: the naive
alternative — delete and recreate in the target channel — would lose the
message thread; this mutation is the one that does not. Staff-only
(`contracts.manage`); a move to the channel a ticket is already in succeeds
rather than being refused, matching this codebase's general preference for
idempotent admin actions over a pedantic `NO_OP`.

### 1.4 · The `ADMIN_REQUEST` counter — queryable, not a feeling

`Query.adminRequestCount` counts every `ADMIN_REQUEST` ticket ever filed,
regardless of its current status. **Decision:** the signal spec §10.2 wants
is demand, not backlog — closing a ticket must not shrink the number a
business decision is waiting on. Staff-only, shown on the desk's Tickets
screen as a real number (`formatCount`, house rule 14) rather than left as an
impression.

### 1.5 · The portal's `support` rail goes live

`SOON` in `PortalLayout.tsx` drops `'support'`; the link is now a plain
`NavLink` to `/app/support`, no "soon" tag. `Support.tsx` (new) lists the
caller's own tickets (`myTickets`), lets them file one (`createTicket`,
restricted to the three customer-choosable types), and reply
(`addTicketMessage`). A converted ticket's brief renders as its own block —
page, current state, desired state, annotation — so the customer sees the
same structured record staff do, not a plain message thread pretending
nothing preceded it.

### 1.6 · The desk support surface

`desk/Tickets.tsx` (new): every ticket (`allTickets`, filterable by status
and type), the `adminRequestCount` tile, and per-ticket controls — status,
urgency, the channel-move select, the billable checkbox, and the reply
thread. Gated on `contracts.manage` — see §2 decision 1 for why no narrower
capability was introduced. `DESK_SECTIONS` gains `{ key: 'tickets',
capability: 'contracts.manage' }`, placed after `builds` and before
`apiTokens` (the credential-issuing section stays last on purpose, per its
own existing comment).

### 1.7 · `DemoFeedbackPanel` gained the conversion form

For staff viewing a `RATIFIED` item with no ticket yet, a "convert to ticket"
control opens a small form (current state, desired state, the language
picker already built for `BuildChangeEntry.noteLang`) and calls
`createTicketFromFeedback`. Once converted, the item shows a plain
"converted to a ticket" badge instead — never offered twice.

**A converted item leaves the build-feedback queue.** `openFeedbackQueue`
and `declareBuild`'s own read of open items now both exclude any
`FeedbackItem` with a `ticket` already set (`ticket: null` in both `where`
clauses). Without this, an item moved to the ticket channel would sit in
L3b's build queue forever, since it is genuinely still `OPEN`/`RATIFIED` —
and "every open feedback item needs a disposition" would then mean the
queue could never drain the day a single item took this path. This is a
cross-stage integration point L4 had to add to L3b's own code, not something
L3b anticipated.

## 2 · Decisions taken inside the stage

1. **No new capability was introduced for the support desk.** `tickets`
   reuses `contracts.manage`, matching every other Root-side working surface
   added since L1 (phases, demo frames, the registry) — none of which grew
   its own capability either. Nothing in the plan asks for a narrower
   "support-only" staff persona, and inventing one speculatively would be
   the same mistake D6's own reasoning warns against in the other direction
   (granting a role more than its job needs). Revisit if that persona ever
   earns itself.
2. **`createTicket` is always self-authored.** There is no "log a ticket on
   a customer's behalf" mutation — matching the gap L1 left `inviteDeveloper`
   with (no generic on-behalf-of act exists anywhere in this codebase yet).
   Staff wanting to record a phone call as a ticket create it under their own
   account and reclassify with `moveTicketChannel` if it turns out to be an
   `ADMIN_REQUEST`.
3. **The brief's five snapshot columns travel together, structurally.**
   `Ticket_brief_all_or_none` (a hand-written CHECK, the same route L1's
   `ScopeItem_decided_both_or_neither` takes) refuses a half-written brief —
   all five null, or all five set. A ticket created the ordinary way
   (`createTicket`) simply never touches any of them.
4. **No new `ChangeAction` values.** Creating a ticket, moving it, replying,
   or converting a feedback item does not write to `ChangeLog` — consistent
   with L1's decision 8 and L3/L3b's own precedent (registry, feedback and
   build activity do not feed the desk's activity feed either), and nothing
   in the plan asks for it here.
5. **`FeedbackItem.ticket` is a shallow include everywhere it appears.**
   `feedbackItemInclude` (`resolvers/feedback.ts`) adds `ticket: true` — a
   plain row, no nested include — because every caller that asks for it
   (the desk feedback panel, the ticket's own `sourceFeedbackItem` field)
   only ever selects scalar fields off it. `Ticket`'s own `sourceFeedbackItem`
   resolves through the same `feedbackItemInclude`, one level nested, with no
   further recursion — the two never form a cycle because neither re-expands
   the other's own relations.
6. **`Ticket.customer`/`Ticket.project` are plain Prisma includes, not field
   resolvers.** Every mutation and query that returns a `Ticket` includes
   both directly (`ticketInclude` in `resolvers/tickets.ts`) rather than
   resolving them lazily — a ticket list is small enough that eager loading
   costs nothing, and it keeps `resolvers/tickets.ts` self-contained (no new
   field resolver was added to `fields.ts` for this stage).

## 3 · What was deliberately not built

- **The `BillingEntry` edge for a billable ticket.** See §1.1 — explicitly
  L6's, and building it here would mean building it twice.
- **A `Ticket` → `FeedbackItem` reverse conversion, or moving build feedback
  into a support ticket.** The plan's "three channels" are build feedback,
  support, and admin requests; only the admin-request axis (support ↔
  admin request, via `moveTicketChannel`) and the one-way "ratified item
  becomes a ticket" conversion are asked for. A support ticket becoming
  build feedback has no requesting page or frame line to attach to and
  nothing in the plan asks for it.
- **A generic "assign a ticket to a project after the fact" mutation.**
  `projectId` is set at creation (`createTicket`) or by
  `createTicketFromFeedback`; nothing lets staff attach an existing ticket to
  a project later. Not asked for, and speculative before a real need shows up.
- **Any UI for `Ticket.urgency` beyond a plain select**, and no
  urgency-based sorting or highlighting on the desk screen — the plan does
  not ask for it, and the field already existed in the schema untouched.
- **A per-developer or per-support-agent assignment on a ticket.** Every
  account holding `contracts.manage` sees and may act on every ticket, the
  same precedent `REVIEWER`/`review.participate` and `DEVELOPER`/
  `builds.author` already set (L3b §2 decision 2).

## 4 · The migration

Hand-authored:
`apps/api/prisma/migrations/20260921130000_l4_change_tickets_and_channels/migration.sql`.

`npx prisma migrate diff --from-schema-datamodel <pre-L4 schema>
--to-schema-datamodel <post-L4+L5 schema> --script` was run first (no
database needed) against the combined L4+L5 schema change, then hand-split
into this file's half and L5's — the raw diff is one flat script and does
not know these are two stages. Cross-checked statement by statement against
the split. No correction for a NOT NULL-with-no-default trap was needed:
every new column on `Ticket` is nullable (a pre-existing ticket has no
project and no source feedback item, and both stay legitimately absent
forever for most tickets), and `ALTER TYPE "TicketType" ADD VALUE` needs no
backfill. What the raw diff cannot express, and this file adds by hand:
`Ticket_brief_all_or_none`, the five-column "all or none" CHECK — the same
route L1's `ScopeItem_decided_both_or_neither` and L3b's
`BuildChangeEntry_at_most_one_origin` already take, generalized from two
columns to five.

`ALTER TYPE … ADD VALUE` runs before anything in the same file could use the
new value, which matters on Postgres: a value added and then read inside the
same transaction is refused. Nothing in this migration's own DDL reads
`ADMIN_REQUEST`, so there is no hazard, but it is worth stating since the
ordering was checked rather than assumed.

Applied for real, on this machine, to both `root_website` and
`root_website_test` via `npx prisma migrate deploy` — see §7.

## 5 · Traps, checked against what was actually built

1. **The brief is genuinely usable, not merely present.** Confirmed by the
   integration suite (§7): `createTicketFromFeedback` populates all five
   fields, the page and annotation from data already in hand, current/
   desired state from the caller's own arguments — never blank, never a
   placeholder string.
2. **`Ticket.billable → BillingEntry` was not built.** Confirmed by grep: no
   `BillingEntry` is created anywhere in `resolvers/tickets.ts`, and
   `setTicketBillable` only ever writes the boolean column.
3. **House rule 2 (ownership vs. capability).** `createTicket` and
   `addTicketMessage` (the customer's own acts) gate on ownership
   (`loadTicketForActor`, `customerId === user.id`, staff bypass) — never a
   role test. Every other mutation in `resolvers/tickets.ts` gates on
   `requireCapability(ctx, 'contracts.manage')`.
4. **House rule 6 (API code, web sentence).** Every new `GraphQLError` in
   `resolvers/tickets.ts` carries an English `message` plus an
   `extensions.code`; `Support.tsx`'s `errorMessage` is the one place a code
   becomes a sentence, on the web side.
5. **House rule 14 (digits).** `desk/Tickets.tsx`'s `adminRequestCount` tile
   runs through `formatCount` (a count, Persian digits under `fa`); nothing
   in this stage renders a version, ref or hash that would need to stay
   Latin — there isn't one here.
6. **The naming check against `desk/sections.ts`.** Confirmed by grep: no
   new identifier in this stage's diff contains the bare word "review."
   `Ticket`, `TicketMessage`, `tickets` (the desk section) are all the
   domain's own, pre-existing words.
7. **`ChangeLog` is not this.** Confirmed: no `ChangeAction` value was
   added, and no code in this stage writes a `ChangeLog` row.
8. **D5 stays decided.** `git diff -- apps/api/src/lib/gate.ts
   apps/api/src/lib/gate.test.ts` is empty. No line this stage added sets
   `approvedAt` or `chosenAt`.
9. **Bilingual strings.** Every new `en.json` key has a `fa.json`
   counterpart and vice versa — checked by the locale-parity unit suite
   (§7), which also confirmed no stray Latin letters or byte-identical
   fa/en pairs among the new keys.

**One check this session repeated from L3b's own precedent.**
`prisma migrate diff --from-migrations ./prisma/migrations --to-schema-
datamodel ./prisma/schema.prisma` against a freshly created shadow database
(`root_website_shadow`) reported **"No difference detected"** — replaying
all seventeen migrations in order (through both this stage's and L5's)
reproduces `schema.prisma` exactly. The shadow database was dropped
afterward.

**Not run, and why:**

- The founder's own manual smoke test — a real ratified item converted to a
  ticket in a live engagement — is outside what this session can run, the
  same limit every prior stage's verification section records for its own
  equivalent criterion.
- No dedicated Playwright spec drives `/app/support` or `/desk/tickets`

  drives against a real server, but the new screens' own correctness rests
  on the 14 integration specs exercising every resolver they call, a clean
  `vite build`, and reading the components — not on a browser-driven spec
  for either new screen. Adding one is reasonable follow-up work, the same
  gap L3b's own verification section left open for `Builds.tsx` and did not
  close there either.
