The developer submits each phase's demo as one package per iteration — the build, the page map confirmed, a fate for every open note, the change list, the frame lines including **how to test** — and a demo cannot publish until a named staff member's browser has seen the staging site report from its own origin. The customer approves each phase's demo, which accepts that phase's scope, locks it, and makes its tied invoice issuable. The customer sees the build timeline between design approval and the summary.

## 2 · Decided

1. **`HOW_TO_TEST` (trap 2): staging-only credentials.** Its help text says so in both languages, and **production credentials are never entered in the portal.**
2. Readiness is recorded by a browser and attributed to a person (L5's verification rule): the claim is "this staff member's browser received a report from that origin", not "the server proved it".
3. A published demo whose URL changes stays published but becomes not-ready; only `publishDemo` is gated.
4. `approveDemo` accepts IN_BUILD items too (the plan's "its scope items → ACCEPTED"); **founder to confirm** whether only IN_DEMO should be.
5. Legacy contracts accept phases through scope items as before; the page-map and readiness gates apply to legacy demos too.
6. The retired `approveStep` assertions in `s2`, `j7`, `j8`, `j9b` now expect `GRAPHQL_VALIDATION_FAILED`.
