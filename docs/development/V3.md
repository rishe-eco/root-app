# V3 · Customer revised-banner and re-approval

**Branch:** `stage-v3-revised`
**Needs:** V2 (nothing can publish a v2 or an amendment until it lands).
**Blocks:** V4 only by preference.
**Shape:** one new server-derived field with a diff behind it, and one banner
plus a version panel on the contract detail. Mostly UI.
**Spec:** versioning §2.7; build plan §4 V3.

**Acceptance:** publish a contract v2 → the customer's detail page leads with a
banner naming what changed and one action, and taking it works. Publish a design
v2 with one changed page → the banner asks for one re-approval, not four, and
the contract's approval and signature are visibly untouched. Issue an amendment
on a signed contract → the customer approves and signs it without the base
contract ever appearing to revert.

---

## 1 · The good news first

Most of the re-approval machinery already works, and it is worth knowing that
before designing around it:

- `approveContract` asserts `!gate.contractApproved`
  (`lib/gate.ts:62`). A newly published revision is unapproved, so approval is
  simply available again. It already logs `RE_APPROVED` when
  `revision.version !== 1` (`customer.ts:132`).
- `signContract` asserts `!gate.signed`. A new revision carries no signature, so
  signing is available again, and it already logs `RE_SIGNED` by the same test.
- The prior approval **is not erased**: `approvedAt` stays on the superseded
  revision. The spec asks for it to be "recorded against the older revision and
  visible in history", and it already is — V1b's `contractRevisions` returns it.
- Approvals carry forward across design revisions, chained: v3 carries from v2,
  which carried from v1.

So V3 adds no re-approval logic. It adds **the customer knowing that something
moved, and what.**

**One precondition:** defect **D1** must be fixed (V1b) or the design half of
this stage is unreachable — the client currently disables concept choice and
page approval whenever the contract is approved, which is exactly the state a
design revision on an approved contract produces.

---

## 2 · "Which previous revision?" — the question that decides the design

This is the part that will be got wrong if it is not written down.

There are two different "before"s and they answer different questions:

**A · What does the customer still need to look at?**
Carry-forward is chained, so a page still approved in the current revision is one
whose image has not moved since it was approved — transitively, across every
revision in between. Therefore:

> **The set of pages needing the customer's attention is exactly the set of
> unapproved pages in the current design revision.**

No revision-walking, no "which one did they last see". Three things land a page
in that set — Root changed it, it is new, or the customer un-approved it — and
all three genuinely want the customer's attention. This is the set the banner's
count and the action are built on.

**B · What did Root change this time?**
`diffDesign(previous.concepts, current.concepts)` from `lib/design.ts` — the
same function the carry-forward rule already runs. This gives `added` /
`changed` / `removed` / `unchanged` per page and is for **labelling**, not for
deciding. It is what lets the banner say "the About page is new" rather than
just "one page needs approval".

Build both. Do not build a third thing that tries to be both, and do not walk
the lineage looking for "the revision they approved" — the approval state
already encodes it.

For the **contract** lineage the equivalent "before" is unambiguous, because
approval is a single flag on a single revision:

```ts
prisma.contractRevision.findFirst({
  where: { contractId, approvedAt: { not: null } },
  orderBy: { version: 'desc' },
})
```

## 3 · Server surface

### 3.1 · A snapshot diff, in `lib/revision.ts`

Pure, no Prisma, unit-testable, beside the canonical serialization it diffs.

```ts
export type ArticleChangeKind = 'added' | 'changed' | 'removed' | 'unchanged';

export type SnapshotDiff = {
  titleChanged: boolean;
  amountChanged: boolean;
  articles: Array<{ number: number; titleFa: string; titleEn: string; kind: ArticleChangeKind }>;
};

/**
 * A null `before` means the earlier revision is **unsealed** — a backfilled v1
 * whose snapshot was never built. Everything then reads as `added`, which is
 * honest: there is no recorded text to have changed from.
 */
export function diffSnapshots(before: ContractSnapshot | null, after: ContractSnapshot): SnapshotDiff;
```

An article is `changed` when any of its four text fields differ. Match by
`number`, which is the article's identity in the document — not by position, and
not by title.

### 3.2 · One field on `Contract`

```graphql
enum ChangeKind { ADDED CHANGED REMOVED UNCHANGED }

type ArticleChange {
  number: Int!
  titleFa: String!
  titleEn: String!
  kind: ChangeKind!
}

type ContractDiff {
  "The version the customer last approved."
  fromVersion: Int!
  toVersion: Int!
  titleChanged: Boolean!
  amountChanged: Boolean!
  articles: [ArticleChange!]!
}

"""
What has moved since the customer last acted, and null when nothing has.
Derived on every read, exactly like the gate — the client never decides this,
and a stale copy of it would be a banner asking for something already done.
"""
type PendingReview {
  "The text was revised and wants approving again. Null when it was not."
  contractDiff: ContractDiff
  "Pages of the current design revision that are unapproved, with what Root did to each."
  designChanges: [PageChange!]!
  "A published amendment awaiting approval or signature."
  amendment: Amendment
}

type Contract {
  # …existing…
  pending: PendingReview
}
```

`PageChange` and `ChangeKind` are shared with V2's `CarryForwardPreview`. One
enum, one type — do not add a second pair with the same members.

**`pending` is null when all three are absent.** That is the banner's own
condition, computed once on the server, so the client renders a banner if and
only if the server says there is something to show.

### 3.3 · The three modes, precisely

| Mode | Condition | Action offered |
|---|---|---|
| **Contract revised** | current contract revision is unapproved **and** an earlier one has `approvedAt` | approve, then sign |
| **Design revised** | current design revision `version > 1` **and** `!gate.designComplete` | approve the named pages |
| **Amendment pending** | current contract revision has a **published** amendment with `approvedAt` null, or approved with no signature | approve, then sign the amendment |

**Contract-revised and amendment-pending are mutually exclusive**, and it is
worth knowing why rather than checking both defensively:
`publishContractRevision` refuses on a signed contract (`CONTRACT_SIGNED`), and
`issueAmendment` requires a signed one. A contract is one or the other.

Design-revised can co-occur with either.

## 4 · The screen

`apps/web/src/portal/ContractDetail.tsx`. Two additions, and a rule about where
they go.

**4.1 · The banner leads the page**, above the title, above section 1. It names
what moved, in the reader's language, and carries **one** primary action. Where
two things moved, the action is the one the gate will actually accept — see
**T1**.

**4.2 · The version panel** goes in the rail, under the existing status stepper
and above the history log. Two short lists side by side, from V1b's
`contractRevisions` and `designRevisions`:

```
Contract   v2  ·  approved 3 days ago
           v1  ·  superseded
Design     v3  ·  2 pages awaiting you
           v2  ·  superseded
           v1  ·  superseded
```

The spec's reason for it is worth honouring exactly: *"so it is always clear
that the design moved and the contract did not (or vice versa)"*. Two columns,
not one interleaved timeline — an interleaved one is precisely the false
lockstep the two-lineage model exists to avoid.

**4.3 · The amendment**, when one exists, renders as its own block below
section 4 (the e-signature), with the base contract's signature still shown and
still marked complete. It has its own approve and its own sign-by-typed-name
form. It must never make section 4 look unfinished.

## 5 · Traps

### T1 · The banner must not offer an action the gate will refuse

If both lineages moved, the customer must re-approve the design **before**
`approveContract` will be accepted — `assertCanApproveContract` requires
`gate.designComplete` (`gate.ts:57`). A banner offering "approve the revised
contract" in that state produces a `GATE_DESIGN_INCOMPLETE` error on click.

Rule: when `designChanges` is non-empty, the banner's action is the design one
and the contract change is named but not actionable yet. The gate is already the
authority; the banner is a signpost and must point the same way.

### T2 · Do not add anything to `Gate`

`computeGate` answers three questions and the rail's stepper renders exactly
those three. A fourth meaning inside it makes every existing reader ambiguous.
`pending` is its own field, next to `gate`, and V2 already put the amendment
assertions in `gate.ts` as separate functions rather than as extra gate fields.

### T3 · An unsealed earlier revision must not crash the diff

`readContractSnapshot` returns `null` for a revision the backfill created and
`npm run backfill` has not sealed (`revision.ts:139`). `diffSnapshots` takes
`before: ContractSnapshot | null` for exactly this reason. Do not `!` it; do not
assume `approvedAt != null` implies a snapshot exists — a backfilled v1 can
carry `contractApprovedAt` and no snapshot at all, which is the migration's
documented intermediate state.

### T4 · `pending` is derived per read, never cached

Same discipline as the gate. Every mutation returns the whole contract
(`reload()`), so a fresh `pending` arrives with each action and the banner
disappears at the right moment on its own. Do not memoize it in component state
and do not compute any part of it on the client — a client-side copy of "has
this changed" is the same class of mistake as a client-side copy of the gate,
and it fails in the direction of asking the customer to approve something twice.

### T5 · RTL for the diff markers

Added/removed/changed indicators are the classic place a `border-left` or a
`margin-right` slips in. Logical properties only: `border-inline-start`,
`padding-inline-start`. It will look right in English either way.

### T6 · Persian for a diff is prose, not symbols

"+3 / −1" reads left-to-right and lands badly in an RTL paragraph. Prefer
sentences from the locale files — «سه ماده تغییر کرده است» — with the numbers
interpolated, which is also what makes the change count agree with Persian's
plural rules. The `num-latin` class exists for the places a Latin numeral is
genuinely wanted (refs, article numbers, concept keys); a change count is not
one of them.

### T7 · Amendments arrive on the revision whether published or not

`contractInclude` fetches all of them and `ContractRevision.amendments` filters
unpublished ones out for non-staff (`fields.ts:72`). `PendingReview.amendment`
must apply the **same** filter — it is a different field on a different type and
will not inherit it. An unpublished amendment leaking into the banner shows the
customer Root's draft.

## 6 · Tests

**Unit** — `lib/revision.test.ts`:

1. `diffSnapshots` with a null `before` reports every article `added`.
2. A changed body reports `changed`; an identical article reports `unchanged`.
3. An article present before and absent after reports `removed`.
4. Title-only and amount-only changes set their flags and leave every article
   `unchanged`.

**Integration** — `src/test/`:

5. `pending` is `null` on the freshly seeded fixture.
6. Approve v1, publish v2, and `pending.contractDiff` names v1 → v2 with the
   right articles marked.
7. Publish design v2 with one changed page: `pending.designChanges` has one
   entry, `gate.contractApproved` is still `true`, and the signature is still
   there. This is the independence property the whole two-lineage model exists
   for, and it is worth a test that asserts all three in one place.
8. `approveContract` after a revision succeeds and logs `RE_APPROVED`;
   `pending` becomes `null`.
9. An **unpublished** amendment does not appear in `pending.amendment`; a
   published one does.
10. Both lineages moved: `pending` reports both, and `approveContract` is
    refused with `GATE_DESIGN_INCOMPLETE` until the pages are approved. This is
    T1, held by a test.
11. An unsealed v1 as the approved revision: `pending.contractDiff` renders with
    everything `added` and nothing throws.

**e2e** — extend the contract flow: as admin publish a design v2 with one page
changed, then as the customer see the banner, approve one page, and watch the
banner go. This is the one that would have caught defect **D1**.

**Browser, both languages.** The banner in Persian, right-aligned, with a
Persian change count.
