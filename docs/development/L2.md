**Stage:** L2 of `ecosystem/working/root-studio-lifecycle-build-plan.md` (1.0).
**Depends on:** L1 (`Project`, the scope registry). **Spec:** `root-website-project-lifecycle.md` §4 stage 6, §6. **Decisions:** D2, and D5 as a standing constraint.
**Status:** built. Unlike L1, **this stage was verified against a real database** — see §7, which is the first entry in this series that is allowed to use the word *tested*.

---

## 1 · What was built

### 1.1 · `Phase`

A slice of the build, ordered per project, binding scope items and demos, with a
`milestoneLabel` standing in for the real billing linkage until L6 exists to
hold one. `@@unique([projectId, number])` — two projects both have a phase 1.

`ScopeItem.phaseId` is nullable **at rest**, not merely during the migration:
an item can be agreed long before a phase exists to carry it, and NULL is
exactly that fact rather than a placeholder.

### 1.2 · `Demo` — the live staging site, embedded (D2)

Not a capture, not a proxy. The demo carries `stagingUrl`, an optional
`buildRef`, and a review window.

**The review window is convention, not machinery.** `reviewWindowStart` /
`reviewWindowEnd` record what Root has declared; nothing in the code locks a
deploy. D2 asked for exactly this and no more — the freeze is a habit plus a
recorded fact to argue from later, and building a deploy-lock would be
machinery for a problem a sentence solves.

`stagingUrl` is held to HTTPS by `assertHttps` at the write path rather than by
a database CHECK. Mixed content is a silently blank iframe, never an error
message, so the failure this prevents is one nobody would diagnose.

### 1.3 · The path → page mapping — *the actual feature*

L2.1 predicted the browsing surface would be cheap and the mapping underneath
it expensive. That held exactly.

`lib/demoPages.ts` is pure and has no Prisma import: `normalizePath` reduces a
reported path to a canonical form (trailing slash, query, locale prefix, index
suffix, percent-encoding), and `matchDemoPath` matches it against the pages the
demo declares **from the registry**. Both are unit-tested, which is what made
them worth writing as functions rather than as resolver bodies.

**Unmatched paths are visible, never silent.** `DemoUnmatchedPath` holds one
row per `(demo, normalizedPath)`, counted and timestamped by upsert. A note
filed against an unrouted path is the dead-end failure (F2) rebuilt one level
down, so the bucket is surfaced on the desk rather than dropped.

### 1.4 · The reporter snippet

`snippets/demo-reporter/` — a build-time include for the customer's *staging*
theme. It posts the current path to the parent on load and on `pushState` /
`popstate`.

Three guards, because a reporter posting a customer's browsing path out of
their **live** store is a small leak and a large embarrassment:

1. an explicit `data-enabled="true"` attribute — a tag left in a production
   build by mistake still does nothing;
2. it refuses to run unframed (`window.parent === window`) — top-level
   navigation is never a demo review;
3. it posts to a concrete `data-root-origin`, never `'*'`, so the browser
   itself refuses delivery if the page is framed by anyone but Root.

The portal holds the other half: `DemoViewport.tsx` validates `event.origin`
against the demo's declared staging origin and drops anything else. Without
that check, any page that frames the portal could inject page-change events.

### 1.5 · The viewport frame and the design-image toggle

An `<iframe>` whose width and height come from a preset table, scaled with
`transform: scale()` to fit the pane.

**The phone case is answered by saying so.** A customer reviewing on a phone,
inside a frame, simulating 1440px, is a bad experience with no fix. The portal
detects the narrow viewport and explains, rather than offering a control that
cannot work there.

The design-image toggle is `DemoPage.pageDesignId → PageDesign`, read-only.
L2.1 called it near-zero *conditional on the mapping*, and that was right: once
a path resolves to a page, showing the design beside it is a toggle.

### 1.6 · Coarse progress, derived

`computeProjectProgress` in `lib/phase.ts` derives "phase 3 of 5" from phase
state and scope-item status. **There is no stored percentage and there must
never be one.** F5 is the founder's own slippage; a hand-maintained number is
the first thing to go stale, and a stale honest-progress indicator is worse
than none, because the honesty *is* the product promise.

## 2 · D5, and how it is enforced rather than promised

The spike came back as the plan's lean predicted: **the machinery is not
reused; the page keys are.** It was settled by reading rather than a throwaway
branch, because `lib/gate.ts:computeGate` turns out to answer the question on
its own — `designComplete` is computed from `DesignRevision → concepts[].chosenAt`
and `pages[].approvedAt`, and from nothing else.

So the constraint is one sentence: **no lifecycle code may ever write
`PageDesign.approvedAt` or `DesignConcept.chosenAt`.** Reading `imageUrl` and
the page `key` is the whole of the permitted reuse.

It is held structurally, not by memory. `DemoPage.pageDesignId` is
`ON DELETE SET NULL` — deleting a page design must neither delete nor be
blocked by a demo page that merely displays it. The demo side is a reader; the
design side owes it nothing. `gate.ts` is untouched in this stage and
`gate.test.ts` is green.

## 3 · What was deliberately not built

- **Automatic capture-at-publish.** It needs a headless browser — the exact
  cost F1b already weighed and deferred (~350 MB image, ~250 MB RAM on a VPS
  whose runbook warns `vite build` may exhaust it). Nothing about that VPS has
  changed. The notes are the record, and a note keyed to a *page* does not need
  a picture to stay true. When it becomes worth paying, it should be paid once
  — demo captures and the server-side contract PDF together.
- **The rewriting reverse proxy.** D2 rejects it outright: permanently
  unfinished work, and an XSS vector pointed at Root's own cookies.
- **A deploy lock.** See §1.2.
- **The scope trade's customer-confirm half**, still outstanding from L1.

## 4 · Defects this stage found, and what found them

Three, and **the unit suite caught none of them.** Recorded because the pattern
matters more than the bugs.

1. **The GraphQL schema did not parse at all.** A description string written as
   `"\"A page we did not expect\" …"` inside a template literal: the escape
   collapses to a bare quote before GraphQL sees it, ending the description
   early. Every one of the twelve integration files failed to boot. `tsc` cannot
   see this — `typeDefs` is a template string, so to the type system it is just
   text. Fixed with a block string.
2. **`resolvers/demo.ts` imported at the wrong depth** (`../lib/…` from a file
   two levels down). This one *was* a typecheck error, and it is the only one of
   the three that was.
3. **Two integration tests hit `NO_PROJECT`.** Both fixtures insert a contract
   straight through Prisma, which as of L1 is the one remaining way to
   manufacture a contract with no project. Fixed in the fixtures, **not** in the
   resolvers — see §5.

## 5 · The `NO_PROJECT` decision, stated because the other choice was tempting

`Contract.projectId` is nullable, so a project-less contract is representable,
and the registry mutations refuse it with `NO_PROJECT`.

The tempting fix was to have `applyContractTemplate` create a project on
demand. **That was rejected.** `createContract` already makes the project in the
same transaction, and the L1 migration backfilled one for every contract that
already existed — so the nullable column is a *migration ordering artifact*,
not a state the application produces. Lazily creating a project would convert a
loud, diagnosable anomaly into a silent repair, and the anomaly can only arise
from a direct database insert, which is to say: from a test fixture, or from a
bug worth hearing about.

**Owed, and worth doing once the migration has run everywhere:** make
`Contract.projectId` non-nullable and delete `NO_PROJECT` entirely. Until then
it stays reachable, and any new code path that creates a contract must create a
project with it.

## 7 · Verification — and the ceiling is gone

The build plan's §7 P0 is **closed**. The `root` role and both databases already
existed; the earlier failure was `psql` defaulting to the OS username, not a
missing role. No Docker was needed.

**Run, and green:**

```
npx prisma validate
npx prisma migrate deploy      # root_website AND root_website_test — applied for real
npm run typecheck              # both workspaces, clean
npm run build                  # web builds
npm test                       # 233 API unit + 31 web unit, 0 failures
npm run test:integration       # 173 specs, 0 failures  ← never ran before
```

**The L1 hash seal is now proven, not argued.** The dev database holds a
published contract revision with a signature attached. Before the migration:
`contentHash = 938eb862…7c67`, snapshot bytes `md5 13668c60…`, and
`Signature.signedHash = 938eb862…7c67`. After applying both migrations: **all
three identical.** L1 §1.5 reasoned that published revisions stay byte-identical
because a snapshot is written once and read back verbatim; that reasoning now
has a measurement behind it, against a real signed row.

**Still not verified:** `npm run e2e` was not run. The demo surface has not been
exercised against a real framed staging site — the `postMessage` handshake,
the origin rejection path, and the viewport scaling are reviewed by reading and
covered by unit tests on the pure functions, not by a browser. **The snippet has
never run in a page.** That is the honest boundary of this stage.
