# F2 · The staff shell at `/desk`

**Branch:** `stage-f2-desk`
**Needs:** F1 ✔, F3 ✔. V1b should land first (it is smaller, and V2 needs both).
**Blocks:** V2, V4, R1, C1 — **every remaining stage.**
**Shape:** web only. No schema change, no resolver change, one small
capability fix.
**Spec:** build plan §2 F2; versioning spec §3.

**Acceptance:** a person holding only `review.participate` can sign in, lands on
`/desk`, sees a nav with exactly the sections they may use, and cannot reach
`/desk/contracts` by typing it. A person holding only `CUSTOMER` never sees
`/desk` at all. Both languages, RTL correct.

---

## 1 · What this is, and what it deliberately is not

Today's admin is one 243-line unstyled page (`apps/web/src/admin/Admin.tsx`):
invites, publish, status override. The route is already a splat
(`App.tsx:64`), so nested routing costs nothing.

The work is turning that page into a **shell with sections** — Overview,
Contracts, Customers, and later Library and Review Room — and moving it to
`/desk`.

**It is not a redesign of what is in those sections.** The invite form and the
contracts table move across roughly as they are. V2 replaces the contracts
section properly; V4 fills Overview. F2's job is the frame, the routing, the
access model and the styling foundation those two build on. Resist filling it.

### Why `/desk` and not `/admin`

It was "the admin" while `ADMIN` was the only staff role. With contributors and
reviewers it belongs to everyone who is not a customer, and `/admin` is the
wrong word in the URL bar for most of them. That route has never been public and
has never been handed to anyone, so the rename is free today and expensive once
three roles have bookmarked it.

**No redirect from `/admin`.** It falls through to `NotFound`. This is the
opposite of what R2 will do with `/cast` and `/blog`, which *do* redirect — and
the difference is the rule, not an inconsistency: a URL that has been public is
not free to delete, and one that never left the team is.

The customer portal stays at `/app`.

## 3 · The client's copy of the permission model

**Recommended, and small:** move `Role`, `Capability` and `can` out of
`apps/web/src/lib/queries.ts:3-20` into a new
`apps/web/src/lib/access.ts`, and add two things to it. The server's copy of
this model is a file you can point at (`api/src/lib/capabilities.ts`); the
client's is currently three exports buried in a file about GraphQL documents,
which is how a mirror stops being found. `queries.ts` re-imports the types it
needs for its own `User` type.

```ts
/**
 * Staff is "holds any capability at all", and that reads straight off the
 * model rather than being a special case: CUSTOMER maps to the empty
 * capability set (api/src/lib/capabilities.ts), so a customer has none and
 * everyone who is anything else has at least one.
 */
export const isStaff = (u: Pick<User, 'capabilities'> | null | undefined) =>
  (u?.capabilities.length ?? 0) > 0;

/** Where signing in puts you. Someone holding both lands on the desk and has a link to the portal. */
export const homeFor = (u: Pick<User, 'capabilities'> | null | undefined) =>
  isStaff(u) ? '/desk' : '/app/contracts';
```

### The section table

One declarative list, in `apps/web/src/desk/sections.ts`. The nav, the index
redirect and the per-route guard all read it — three behaviours that must agree,
so they read one source.

```ts
export type DeskSection = {
  key: 'overview' | 'contracts' | 'customers';
  /** null means "any staff capability", which is what Overview needs. */
  capability: Capability | null;
};

export const DESK_SECTIONS: DeskSection[] = [
  { key: 'overview',  capability: null },
  { key: 'contracts', capability: 'contracts.manage' },
  { key: 'customers', capability: 'customers.manage' },
];

export const visibleSections = (me) =>
  DESK_SECTIONS.filter((s) => (s.capability === null ? isStaff(me) : can(me, s.capability)));
```

V2 does not add a section. R1 appends `{ key: 'library', capability: 'library.write' }`
and C1 appends `{ key: 'review', capability: 'review.participate' }` — one line
each, which is the whole reason this is a table.

**The nav reads capabilities, never roles.** The build plan calls this out
specifically, and the wording matters: a role test in the nav is wrong twice
over — it misses a user holding contributor and reviewer together, and it needs
rewriting for every role added.

## 4 · Access control has three layers, and only one of them is real

| Layer | Where | What it is |
|---|---|---|
| **Server** | `requireCapability` in each resolver | the authority. Already built. |
| **Route guard** | each desk route | a redirect, so a typed URL does not render a broken screen |
| **Nav** | `visibleSections` | cosmetic. Hiding a link is not access control. |

Build all three anyway. The server refusing a query and the UI declining to show
the screen fail independently — `e2e/03-admin.spec.ts:5-11` already says so, and
it is worth keeping that comment when the file moves.

- **`DeskLayout`** redirects `!isStaff(me)` to `lp(locale, '/portal')`. That
  reproduces today's behaviour and the two-hop redirect the e2e asserts: `/desk`
  sends a customer to `/portal`, and `/portal` sends an already-signed-in user
  on to `/app/contracts`, so they land somewhere sensible rather than at a
  sign-in form they do not need.
- **`DeskHome`** (the index) redirects to `visibleSections(me)[0]`. Not a
  hardcoded `/desk/overview` and certainly not `/desk/contracts` — a reviewer
  bounced off the first section they are sent to is a bad first thirty seconds.
- **Each section** checks its own capability and redirects to `/desk` if absent.

## 5 · Styling

Two rules, and the second is the one that needs a decision recorded because the
build plan's wording is easy to over-read.

**5.1 · Do not edit `tokens.css` or `kit.css`.** They came from the design
handoff and are the portable layer. New layout goes in a new
`apps/web/src/styles/desk.css`, imported in `main.tsx` **after** `portal.css`
and **before** `print.css` (print must stay last so its `@media print` rules
win). Every value in it is a token reference — no raw colours, sizes, spaces or
radii.

**5.2 · The kit's *controls and surfaces* are shared; its *page furniture* is
the marketing site's.** The build plan says the desk "should adopt the token
layer, not the marketing kit", which read literally would mean reimplementing
buttons and text inputs. That is not the intent. The split:

| Use | Do not use |
|---|---|
| `.root-ui` (required — it establishes font and colour) | `.t-display`, `.t-h1`, `.beauty` |
| `.t-h2` `.t-h3` `.t-body` `.t-small` `.t-caption` `.t-eyebrow` `.sr-only` | `.section`, `.section-inner`, `.footer`, `.rule`, `.rule-cyan` |
| `.btn` + `.btn-primary/-secondary/-ghost/-sm` | `.btn-lg` |
| `.field` `.label` `.input` `.textarea` `.select` `.help` `.error` `.choice` | `.nav`, `.nav-brand`, `.nav-link`, `.nav-link-locked` |
| `.card`, `.card-panel`, `.card-quiet` | `.card-inverse`, `.card-topruled`, `.card-link` |
| `.badge`, `.badge-neutral` | `.badge-locked`, `.lock*` (the public nav's locked slot) |
| `.link`, `.link-action`, `.lang-switch` | |

Note that **all stylesheets are imported globally** in `main.tsx` — there is no
module scoping, so every class is technically reachable everywhere. This table
is discipline, not a mechanism. Nothing will stop you; it will just look like
the landing page.

**5.3 · Reuse components, not class names.** `StatusBadge`
(`components/StatusBadge.tsx`, using `.st-badge` + the modifiers in
`format.ts:5`) is a shared component and the desk should use it. `.ctable` and
`.table-wrap` live in `portal.css` and are already what `Admin.tsx` uses for its
tables; keep using them rather than writing a second table style. The line is:
**a class reached through a shared component is shared; a portal layout class
copied into desk markup couples two screens that will diverge.** Do not put
`.side`, `.work`, `.topbar`, `.detail` or `.rail` in desk markup — write the
desk's own shell grid in `desk.css`. It is about thirty lines.

**5.4 · Logical properties only.** `padding-inline`, `margin-inline-start`,
`inset-inline-start`, `border-inline-end`. The desk is a sidebar-and-main
layout, which is the exact shape that breaks in RTL if a single `left:` slips
in. It will look perfect in English.

## 6 · i18n

Today's `Admin.tsx` has about twenty hardcoded English strings — "Invites",
"Email", "Name", "Client / company", "Generate invite link", "Copy this now",
"Contracts", "Ref", "Title", "Customer", "Status", "Published", "Publish". Every
one violates the repo's own rule that no UI text is typed into a component. F2
is where that gets fixed, because it is where they all move anyway.

New `desk.*` namespace in both `fa.json` and `en.json`. Suggested keys:

```
desk.title            desk.navOverview     desk.navContracts    desk.navCustomers
desk.backToPortal     desk.sectionEmpty
desk.invitesTitle     desk.inviteEmail     desk.inviteName      desk.inviteClient
desk.inviteCta        desk.inviteOnce      desk.inviteCopy
desk.colRef           desk.colTitle        desk.colCustomer     desk.colStatus
desk.colUpdated       desk.colPublished    desk.publish
```

`portal.navAdmin` (currently «مدیریت» / "Admin") becomes `portal.navDesk` with
the new label. Keep the key count equal across the two files — nothing tests
that outside the `log.*` namespace, so it is on you.

> **✔ Settled 2026-08-09: «اتاقِ کار»** — the workroom. English "Desk".
>
> *Original note, kept because the constraint still holds:* `portal.workspace`
> is already «میز کار», so the desk cannot take it. «کارگاه» (workshop) shipped
> as the placeholder under a `TODO(label)`.
>
> **Why the answer is better than the placeholder.** «کارگاه» and «میز کار»
> compete — both name the place work happens, so the portal and the desk end up
> arguing about which is the workplace. «اتاقِ کار» *nests* instead: the portal

## 7 · What moves out of `Admin.tsx`

| Today | Goes to |
|---|---|
| The invite form + the customers table | `desk/Customers.tsx`, guarded by `customers.manage` |
| The contracts table + status select + Publish button | `desk/Contracts.tsx`, guarded by `contracts.manage` |
| The `mayUseAdmin` / per-query `skip` logic | `DeskLayout` + per-section guards |
| `<LangSwitch />` in the header | the desk topbar |
| The "run through GraphQL directly for now" help text | delete — V2 replaces it |

**Keep the per-query `skip` pattern** (`Admin.tsx:42-47`). Each query is skipped
on the capability its own resolver guards, rather than on one blanket "is this
an admin", so someone holding half of this screen's remit still gets the half
they may use. Under sections this becomes structural rather than a `skip`, which
is better — but the reasoning is right and worth keeping in a comment.

**Fix D4 while the table moves:** the "Published" column shows `updatedAt`
(`Admin.tsx:189` vs `:222`). Add `publishedAt` to the `ContractFields` fragment
and show the right field, or rename the column. Do not ship one labelled as the
other.

**Fix D8 in `PortalLayout.tsx:73`:** the link to the staff area is gated on
`can(me, 'contracts.manage')` and must become `isStaff(me)`, or a reviewer never
sees a link to the thing they were invited for.

## 8 · Sign-in routing

`SignIn.tsx:26` and `:34` both send the user to `from ?? lp(locale, '/app/contracts')`.
Both become `from ?? lp(locale, homeFor(me))`.

`from` still wins — someone who was bounced off a deep link goes back to it.

**Grep for every other post-auth destination** rather than trusting this list:

```bash
grep -rn "app/contracts" apps/web/src
```

`AcceptInvite.tsx` and `ResetPassword.tsx` almost certainly navigate somewhere
after success, and an invited reviewer landing in an empty contracts list is the
same bug in a different file.

**The desk always links to the portal**, unconditionally, in its own nav. The
alternative — showing it only to people who have contracts — costs a query to
decide whether to render a link, and gets the mechanism wrong besides: whether
you have a portal is an ownership question, not a capability one, and the
portal is not a privileged surface. An empty contracts list for a pure admin is
honest.

## 9 · Traps

### T1 · The e2e suite navigates to `/en/admin` four times

`apps/web/e2e/03-admin.spec.ts` — rename to `03-desk.spec.ts`, update the URLs,
and update `getByRole('heading', { name: 'Admin' })` to the new title. The test
that asserts a customer is bounced through two redirects is the one worth
preserving most carefully; it encodes the behaviour described in §4.

Also grep the whole `e2e/` directory — `01-visitor` and `02-contract-flow` may
touch the admin link in the portal rail.

### T2 · `LocaleLayout` keys its `<Outlet>` on the locale

`components/LocaleLayout.tsx:23` returns `<Outlet key={locale} />`, which
remounts the whole subtree on a language switch — deliberately, so a component
that missed i18next's `languageChanged` event cannot keep rendering the old
copy. The desk lives under it, so **any local state in the shell is lost when
the user switches language.** For F2 that is fine. When V2 adds an editor with
unsaved text, it will not be — note it there rather than working around it here.

### T3 · The desk is inside `/:lang`, so every internal link needs `lp()`

`lp(locale, '/desk/contracts')`, never `'/desk/contracts'`. A bare path drops
the locale prefix, `LocaleRedirect` catches it, and the user is bounced to their
guessed locale mid-session — which in Persian also flips the page direction.

### T4 · `visibleSections(me)` can be empty in exactly one case

A user with roles `[CUSTOMER]` — but `DeskLayout` has already redirected them.
A user with any other role has at least one capability and therefore Overview.
So `visibleSections(me)[0]` is safe *after* the layout guard and unsafe before
it. Order the checks accordingly, and do not write `[0]!` without the guard
above it.

### T5 · `allContracts` is unbounded

`resolvers/query.ts:40` returns every contract with the full detail include —
concepts, pages, articles, comments, the whole change log — per contract
(defect **D10**). The desk's Contracts section renders all of them. Fine at
today's scale; do not add sorting or filtering that fetches *more*. V4 is where
this gets a proper query.

### T6 · Do not build Overview yet

It is V4, and V4 is last because it reads state the earlier stages produce. F2's
Overview is a heading and a sentence saying what will be there. An Overview that
guesses at its content now is one V4 has to unbuild.

## 10 · Tests

There is no unit or integration surface here — the server does not change.

**e2e**, in the renamed `03-desk.spec.ts`:

1. A customer cannot reach `/en/desk` — two redirects, ends at
   `/en/app/contracts`, never sees the desk heading. *(existing test, updated)*
2. An anonymous visitor is sent to `/en/portal`. *(existing, updated)*
3. An admin signing in **lands on `/desk`** without navigating there. *(new —
   this is the sign-in routing change)*
4. An admin sees Overview, Contracts and Customers in the nav. *(new)*
5. An admin can issue an invite and gets a link back. *(existing, moved to the
   Customers section)*
6. An admin sees every contract. *(existing, moved)*
7. **A reviewer sees Overview and nothing else, and typing
   `/en/desk/contracts` bounces them to `/en/desk`.** *(new — this is the
   acceptance criterion, and it is the only test that proves the capability
   filter is a filter rather than an `isAdmin` in disguise)*

Test 7 needs a reviewer account, which nothing creates. Add one to
`prisma/seed.ts` — `reviewer@root.local`, `roles: ['REVIEWER']` — beside the
existing two, and to `e2e/helpers.ts` beside `ADMIN` and `CUSTOMER`. Seeding a
role that has no surface yet is not premature: F3 built the role and this is the
first test that can prove it does what it says.

**Both languages in a browser.** Load `/fa/desk` and `/en/desk` and check the
sidebar sits on the correct side, the tables read in the correct direction, and
no Persian text is letter-spaced or uppercased. This is not covered by any test
and is the most likely thing to be wrong.
