# R2 · Library — public reader, list and search

**Branch:** `stage-r2-reader`
**Needs:** R1 (there is nothing to read until the corpus has entries).
**Blocks:** R3 by preference, R4 by necessity.
**Shape:** medium. Two public queries, a route restructure that touches the nav, one genuinely new layout problem, and the first unauthenticated read in the app.
**Spec:** `root-sot/ecosystem/working/root-website-research-lab.md` §1, §2, §3; build plan §5 R2.

**Acceptance:** an anonymous visitor reaches `/:lang/library`, finds the Research Lab, searches it in either script, opens an entry, and reads the original beside its translation with each in its own script and direction. `/:lang/cast` and `/:lang/blog` redirect rather than 404. Nothing in the desk changes.

---

## 0 · What is different about this stage

**This is the first public, data-driven page in the product.** Everything public so far is static copy from the locale files; everything data-driven so far is behind a session. R2 is the first place an unauthenticated request reaches a resolver and a database. §2 is about that, and it is where the security thinking belongs.

**It is also the stage that opens the content lock**, which means it edits `Nav.tsx` and `App.tsx` — files R1 was forbidden to touch. Now it is your turn, and the constraint inverts: **do not touch `/desk` at all.**

## 1 · Two directions on one page — the problem is real, the fix is small

The spec (§3) and build plan both flag this as the hard part: *"The RTL system assumes one direction per page — locale in the URL prefix drives `<html dir>`, the font, and the line height, all at the document level."*

**Half of that is wrong, and the half that is right is not where they expected.** Verified in the browser on 2026-08-10:

| Inside a Persian page, an English-tagged block gets | | |
|---|---|---|
| `direction` | `ltr` | ✅ per-element `dir` already works |
| `--font-sans` | **Vazirmatn** | ❌ wrong |
| `--leading-body` | **1.8** | ❌ wrong |

**Why.** `tokens.css:176` keys the Persian overrides off **`:lang(fa)`**, not off `dir` and not off `:root`. `:lang()` matches by the nearest `lang` ancestor, so it already scopes correctly — but the things it sets are **custom properties, and custom properties inherit**. An `<div lang="en">` inside a Persian page does not match `:lang(fa)`, so nothing re-sets `--font-sans`; it simply inherits the Persian value from its ancestor. There is no `:lang(en)` rule to inherit *back* from.

**The fix is one block in `tokens.css`**, beside the existing one:

```css
/* The Latin defaults, restated so they can be inherited *back*. Without this
   an English block inside a Persian page (the Library reader, R2) sets Latin
   text in Vazirmatn at Persian leading — which looks almost right, because
   Vazirmatn has Latin glyphs, and is therefore the kind of thing that ships. */
:lang(en) {
  --font-sans:     var(--font-latin);
  --leading-body:  1.55;
  --leading-snug:  1.35;
  --leading-tight: 1.15;
}
```

The values must match `:root`'s. If a token is ever added to the `:lang(fa)` block, it has to be added here too — **say so in a comment in both blocks**, because a one-sided edit is silent.

**Then the reader is ordinary markup:** each of the two columns carries its own `lang` and `dir`, logical properties mirror per block as they already do, and nothing at the document level changes.

```tsx
<div className="reader-col" lang={entry.originalLang} dir={dirFor(entry.originalLang)}>
```

### 1.1 · `dirFor` is new, and `originalLang` is a free string

R1 stored `originalLang` as a free BCP-47-ish string on purpose (its T2): the corpus has as many source languages as it has sources. So R2 needs a direction lookup, and it must **not** be `locale === 'fa'`:

```ts
/** RTL scripts the corpus can plausibly carry. Not an exhaustive list of RTL
 *  languages — an exhaustive list is a library, and this is a lookup with a
 *  safe default. Anything unknown is LTR, which is wrong quietly rather than
 *  catastrophically: Latin text in an RTL block is unreadable, RTL text in an
 *  LTR block is merely poorly aligned. */
const RTL = new Set(['fa', 'ar', 'he', 'ur', 'ps', 'ckb', 'sd', 'yi', 'dv']);
export const dirFor = (lang: string) => (RTL.has(lang.split('-')[0].toLowerCase()) ? 'rtl' : 'ltr');
```

**Do not reach for `dir="auto"`.** It guesses from the first strong character, so a Persian abstract beginning with a Latin acronym — "NVC در عمل" — renders left-to-right and every line lands wrong. The entry already *states* its language; use it.

### 1.2 · Labelling the language is a separate problem

`originalLang` is `"de"`. The reader has to say «آلمانی» / "German". That needs a map in both locale files, plus a fallback for an unknown code (show the raw tag — honest, and visibly a gap to fill rather than a wrong guess).

This is R1.md §11's fourth open question landing exactly where it said it would. **Keep the map small and additive** — the languages actually in the corpus, not a full ISO table.

## 2 · The public read path — the first unauthenticated resolver

Everything in `resolvers/library.ts` today calls `requireCapability(ctx, 'library.write')`. The public queries must not.

```graphql
type Query {
  "Public. Published, public-visibility entries only."
  publicLibraryEntries(search: String, type: EntryType, conceptSlug: String, limit: Int = 24, offset: Int = 0): PublicEntryPage!
  "Public. One entry by its slug. Null for a draft, a private entry, or no such slug."
  publicLibraryEntry(slug: String!): PublicEntry
  "Public. Concepts that have at least one publicly visible entry."
  publicLibraryConcepts: [PublicConcept!]!
}
```

### 2.1 · Write new resolvers; do not add a flag to the staff ones

The temptation is `libraryEntries(publicOnly: true)`. Refuse it. The staff query returns drafts, `searchText`, `createdBy` and the whole entry; the public one must return a curated subset of published rows. **A boolean that changes both the filter and the shape of the result is two functions wearing one name**, and the failure mode is a draft leaking because someone added a field to the shared selection.

Both public resolvers filter through R1's `publiclyVisible` (`lib/library.ts:14`) — which exists for exactly this and is currently used nowhere. Import it; do not inline `publishedAt: { not: null }` beside your own idea of visibility.

### 2.2 · `limit` must be clamped — the helper already exists

**Done for the staff queries on 2026-08-10**, in the R1 review: `lib/pagination.ts` holds `clampLimit(value, fallback, max)` and `libraryEntries`, `needsRootQueue` and `activity` all use it. Read the comment there before adding a fourth list query — it explains why a GraphQL default is not a bound.

```ts
take: clampLimit(args.limit, 24, 60),
```

**Use it on every public query too, and pick a smaller max than the staff ones.** The staff bound (100) is sized for someone scrolling their own corpus; an anonymous list has no such excuse, and 60 is generous for a reader.

This is where the rule stops being hygiene: unbounded was a staff foot-gun while every list query needed a capability. **Made public, it is the cheapest way to make the database work hard from outside.**

### 2.3 · What a public entry may expose

| Expose | Withhold | Why |
|---|---|---|
| titles, authors, venue, year, doi, sourceUrl, abstracts | `searchText` | an implementation detail, and it is the folded concatenation of everything |
| `translationProvenance`, `translationCredit` | `visibility` | a public entry is public by definition; the field only tells you the flag exists |
| `rightsBasis`, `rightsNote` | `publishedAt`? | **expose it** — "published on" is ordinary library metadata |
| `fullTextUrl` (derived) | `fullTextFileId` | the id is internal; the URL is the product |
| concepts | `createdBy` | who at Root filed an entry is not the reader's business |

**`rightsBasis` is public on purpose.** It is how a reader knows whether a missing PDF is an omission or a rights boundary, and R4 will cite it.

### 2.4 · There is no rate limiting anywhere in this app

Not in Nginx, not in Express. Until now everything expensive was behind a session. `publicLibraryEntries` with a `search` term is an anonymous `ILIKE '%…%'` over a growing table.

**This does not have to be solved in R2**, and inventing a rate limiter here is scope creep. But it must be *recorded* — with the clamp in §2.2 as the cheap half that R2 does do, and a note in the deployment runbook that the first public endpoint now exists. If a limit is wanted, Nginx `limit_req` on `/graphql` is the smallest thing that works and needs no code.

## 3 · Routes, and opening the content lock

Today: `cast`, `blog`, `studio`, `journey` are top-level `Reserved` routes; `Nav.tsx:17` renders `cast` as a locked slot.

**After R2:**

```
/:lang/library                  → the umbrella: strands, and the Lab's recent entries
/:lang/library/research         → the list + search
/:lang/library/research/:slug   → the reader
/:lang/library/cast             → Root Cast, still Reserved (locked)
/:lang/cast                     → redirect to /:lang/library/cast
/:lang/blog                     → redirect to /:lang/library/cast
```

**Redirect, never 404** (spec §1): both have been reserved routes since launch, and a public URL that has ever existed is not free to delete. `<Navigate replace>`.

**`blog` folds into Root Cast**, per the spec — it does not survive as its own strand, and it does not get its own locked page.

**The nav slot changes from locked to real.** `Nav.tsx`'s `Slot` type and its `LOCKED` handling stay — `studio` and `journey` still need them. Only `cast` graduates, and its label changes from `nav.cast` to a new `nav.library`. **Leave `nav.cast` in the locale files**: Root Cast is still a real forthcoming strand and `/library/cast` renders its name.

### 3.1 · The slug is the first non-ASCII route segment in the app

R1 chose to keep a Persian title's own script — «یادگیری-ماشین», not `yadgiri-mashin` — and every route segment before it was ASCII by construction. Three things to check rather than assume:

- **React Router** gives `useParams()` values already percent-decoded. The query must therefore match against the decoded string, which is what R1 stored.
- **Links** must be built with `encodeURIComponent(slug)`, or a slug containing a character the router treats as a separator breaks the match.
- **Nginx** `try_files $uri $uri/ /index.html` with a UTF-8 path: this is the deploy-side half and the only part not visible from a dev server. Verify it against the real config before calling the stage done — it is the one thing here that can pass locally and fail in production.

## 4 · The reader

Spec §3: *"places original beside translation, each in its own script and direction, under a provenance line."*

**Provenance leads, not follows.** The spec says translation provenance is "always shown, never implied" — so it is a line above the two columns, not a footnote:

| State | Reads |
|---|---|
| `PUBLISHED` | "Translated by {translationCredit}" — with the source linked if `sourceUrl` |
| `ROOT` | "Root translation" |
| `NONE_YET` | "Original only" + the request affordance below |

**Two columns on desktop, stacked on mobile**, original first in both cases. Each column carries its own `lang`/`dir` (§1).

**`NONE_YET` gets a request affordance**, and here is the honest scope call: spec §3 says reader requests "feed an admin translation queue", and §5 lists that queue as an admin surface. **R1 built no request model.** Either R2 adds one small model (`TranslationRequest`: entryId, requester email or null, createdAt) plus the desk queue, or the affordance is deferred with the rest.

*Recommendation: defer it, and say so.* It is a second data model, a second desk screen, and an anonymous write endpoint — the last of which is a spam surface with no rate limiting (§2.4). Ship the reader; add requests when someone asks. **Do not ship a button that does nothing.**

## 5 · Search — reuse, do not rebuild

R1 did the hard part. `searchText` is stored already folded; `foldPersian` (`lib/library.ts:42`) is the one implementation; the read path folds the needle the same way. **Public search is the same `contains` filter with `publiclyVisible` added.**

**Still `ILIKE`, still no index — and this is where R1's deferral has to be honoured or overturned deliberately.** R1.md §5.3 deferred `tsvector`/GIN with a stated trigger: *when the corpus passes a few hundred entries, or when public search is measurably slow.* **That deferral is now written into `lib/library.ts`**, above `slugify`, having been missed in the R1 build and added in its review — read it there rather than here, and update it if R2 overturns it. Its substance:

- The corpus is tens of entries. A sequential scan over a folded text column is instant at that size.
- The folding is the correctness half and is not thrown away by a later index — a `tsvector` built over **unfolded** Persian has the same equality bug with a faster index on top.
- If you do reach for it: the **two-argument** `to_tsvector('simple', …)`. The one-argument form reads its config from a session GUC, is therefore not `IMMUTABLE`, and is illegal in a generated column or index — with an unhelpful error.

## 6 · Citation — the spec says the entry "holds" one; R1 stores the parts

Spec §3 lists "citation (BibTeX/APA)" among what an entry holds. **R1 added no `citation` column** — it stores `authors`, `titleOriginal`, `venue`, `year`, `doi`, `sourceUrl`.

**Generate it; do not add the column.** A stored citation is a second copy of five fields that will disagree with them the first time a typo in a venue is fixed — the same reasoning that made the contract PDF a rendering rather than the record (F1b). A pure `formatCitation(entry, style)` in `lib/library.ts` is unit-testable and cannot drift.

BibTeX and APA both want a Latin rendering of a Persian author's name, which the entry does not have. **Cite what is there**, in the original script, and do not invent a transliteration — a citation that silently romanises a name is worse than one a human has to touch.

## 7 · Traps

### T1 · The desk's `libraryEntries` must not start serving the reader
Two queries, two shapes, two guards (§2.1). If the public page ever renders from the staff query, a draft is one capability check away from the front page.

### T2 · `publicLibraryEntry(slug)` returns null, never an error
A draft, a private entry and a wrong slug are one answer: **not found**. Distinguishing them turns the endpoint into an oracle for which slugs exist as drafts (house rule 13, applied to an anonymous caller where it matters most).

### T3 · The `:lang(en)` block must list every token `:lang(fa)` sets
§1. A token added to one and not the other is silent, and shows only as slightly-wrong Latin text inside a Persian page.

### T4 · `hreflang` and the language switch on a reader page
`LocaleLayout` remounts on locale change (`components/LocaleLayout.tsx:23`). Switching language on `/fa/library/research/یادگیری-ماشین` must land on the *same entry* in English — the slug is not localised, so it is the same URL with a different prefix. Verify it does not drop to the list.

### T5 · An entry with no translation must not render an empty column
`NONE_YET` means one column, full width — not two with one blank. The layout has to collapse, and it is the common case for a young corpus.

### T6 · SEO is structurally absent, and should be said out loud
The app is an SPA with no server render, so per-entry `<title>` and meta description exist only after JavaScript runs. A public research corpus is exactly the thing people expect to find in a search engine. Setting `document.title` per entry is worth doing and is **not** the same as being indexable. Record it as a known limitation; it closes with the same server-side renderer F1b deferred, and for the same reason.

### T7 · Do not touch `/desk`
The mirror of R1's constraint. If a change seems to require editing a desk screen, it is either wrong or it belongs to a different stage.

## 8 · Tests

**Unit** (`lib/library.test.ts`): `dirFor` for fa/ar/he/en/de and an unknown tag; `formatCitation` for a Persian-authored entry with no DOI and for a full English one.

**Integration:**
1. `publicLibraryEntries` excludes a draft, excludes a `PRIVATE` published entry, includes a published public one — **as an anonymous caller**, with no session at all.
2. The same query returns no `searchText` and no `createdBy` field (assert on the SDL shape, so adding a field later fails here).
3. `publicLibraryEntry` returns null for a draft's slug, for a private entry's slug, and for nonsense — all three indistinguishable.
4. `limit: 999999` is clamped (§2.2).
5. Public search finds an entry typed with Arabic yeh when it was stored with Persian — the R1 property, re-asserted through the public path.
6. `publicLibraryConcepts` omits a concept whose only entry is a draft.

**e2e:** an anonymous visitor (no `signIn`) opens `/en/library/research`, searches, opens an entry, and sees both columns; `/en/cast` and `/en/blog` land on `/en/library/cast` rather than 404.

**Browser, both languages** — and specifically **an English entry viewed on the Persian site**, which is the case §1 exists for. Check the computed `font-family` on the Latin column, not just how it looks.
