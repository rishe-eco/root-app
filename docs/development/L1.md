# L1 · The scope registry

**Status:** built against `root-app` @ `e7fcac5` (`main`), left uncommitted for
review. **Not verified beyond typecheck, build and unit tests — there is no
usable database on this machine.** See §7.
**Spec:** `root-website-project-lifecycle.md` §3 (the registry), §4 (the
lifecycle). **Plan:** `root-studio-lifecycle-build-plan.md` §2 (D1, D6) and
§3 (L1).
**Shape:** the largest stage since V2 — a schema migration re-parenting a
model, a new role and capability, a mechanical split of `admin.ts`, and a
change to the one serialization in the app that is not allowed to change
what it already produced.

---

## 1 · What was built

### 1.1 · `Project` (D1)

A new `Project` model (`schema.prisma`) owning the customer, a minimal
`ProjectStatus` (`ACTIVE`/`ARCHIVED` — deliberately thin; L2's phases are
expected to carry the real lifecycle state, not this enum), and the scope
registry. `Contract` gains a nullable `projectId`.

`createContract` (`resolvers/admin/contracts.ts`) creates a `Project`
alongside every new `Contract` — L1 does not build the Contact/Scoping
screens (lifecycle spec §4 stages 1–2) that would produce a project *before*
a contract exists, so today's shape is one project per contract, created
together. The schema does not enforce that: `Project.contracts` is a list,
and a wedge customer's design-then-build pair (ADR 0001) can share one
project the day something creates the second contract against an existing
`projectId`. **Nothing in this stage builds that "attach an existing project"
screen** — see §3.

The completeness checklist (spec §3) is seeded on every new project, all ten
areas `DECLINED` by default (`lib/templates.ts`'s `CHECKLIST`, keyed
`checklist.*`) — so a hole like Nahal's missing dashboard coverage is a
decision to reverse, not a discovery in review.

### 1.2 · `ScopeItem` grown up

Re-parented from `Contract` to `Project` (`contractId` → `projectId`,
`@@unique([contractId, key])` → `@@unique([projectId, key])` — banked trap
#2). Added:

- `status: ScopeStatus` — `PROPOSED → AGREED → IN_BUILD → IN_DEMO → ACCEPTED`,
  plus terminal `DECLINED` and `TRADED`.
- `temporary`, `outOfScope`, `adminWork` — plain booleans.
- `decidedAt` / `decidedNote` — both or neither, held by a hand-written CHECK
  (`ScopeItem_decided_both_or_neither`). No formal decision-record model
  exists yet (that is L3's round or L3b's build), so the pointer is a
  free-text note rather than a foreign key invented ahead of its target.
- `declinedReason` — recorded when `status` is `DECLINED`, but **not**
  CHECK-enforced. See §3 for why this is a deliberate gap, not an oversight.
- `originNote`, `originRound`, `originAskedAt` — three plain fields standing
  in for "who asked, when, in which round." No `Round` object exists yet.

**`checkedAt` is untouched.** It is not backfilled into `status`, and no code
in this stage writes it except `setScopeItem` (`resolvers/customer.ts`),
exactly as before. The migration's own backfill (§4) sets every pre-existing
row's `status` to `AGREED`, never `ACCEPTED` — banked trap #1, held in three
places: the schema comment, the migration comment, and this file.

### 1.3 · `ScopeTrade` (spec §4)

A new model recording a paired movement — one item traded away, one item
proposed in return — plus who proposed it and two confirmation timestamps,
`rootConfirmedAt` and `customerConfirmedAt`.

Built this stage: `proposeScopeTrade` (creates the new "in" item `PROPOSED`
and the trade row), `confirmScopeTradeRoot`, and `executeScopeTrade` (moves
the out item to `TRADED` and the in item to `AGREED`, and — when the
project's contract has a signed revision — issues a paired, already-published
`Amendment` describing the swap).

**Not built: the customer's confirmation.** `customerConfirmedAt` has no
mutation writing it, anywhere, in either the API or the portal. This means
`executeScopeTrade` is real and gated correctly (`lib/scope.ts`'s
`assertCanExecuteTrade` refuses without both timestamps) but **cannot
currently succeed for any trade**, because nothing ever sets the customer
half. This is the "clearly-marked TODO" the build plan allows for scope
trade when it is larger than the rest of L1 combined (§3 in the plan) — it
was, once the paired-amendment path is included, and this is the seam where
it stops. The portal mutation, its UI, and the notification that would tell
the customer a trade is waiting on them are all L3-shaped work (the
"immediate notification" mechanism the plan reserves for that stage).

### 1.4 · `DEVELOPER` role and `builds.author` (D6)

- `Role` gains `DEVELOPER`. `CAPABILITIES` gains exactly one entry,
  `builds.author`. `GRANTS.DEVELOPER = ['builds.author']` — nothing else.
  `ADMIN` gets it for free, as it gets every capability, by construction.
- `DESK_SECTIONS` gains `{ key: 'builds', capability: 'builds.author' }`,
  between `reviewAdmin` and `apiTokens`. `apps/web/src/desk/Builds.tsx` is a
  stub page (capability-gated, otherwise empty) — L3b fills in the queue and
  the build-authoring form.
- Seeded: a `developer@root.local` account, alongside the existing
  `admin@root.local` / `nahal@example.com` / `reviewer@root.local` /
  `reviewer2@root.local` / `contributor@root.local` fixtures.
- No `inviteDeveloper` mutation was built. There is no generic "invite with
  an arbitrary role" mutation in the codebase today, and `CONTRIBUTOR` has
  none either — `DEVELOPER` is consistent with that, not an omission specific
  to this stage.

### 1.5 · Appendix 1 as a view of the registry (the sharpest trap)

`ContractSnapshot` (`lib/revision.ts`) gains one field, `scopeItems`, defaulted
to `[]`. `buildContractSnapshot` takes it as a third, optional argument;
`draftState` takes it as a fourth. `resolvers/admin/contracts.ts`'s
`publishContractRevision` populates it from `lib/scope.ts`'s
`agreedScopeSnapshot` — the project's registry, filtered to `AGREED` or
further along, in registry order.

**Why this does not touch an already-published revision's hash.**
`ContractRevision.snapshot` is written once, at publish time, and is never
recomputed from live rows afterward — every read (`readContractSnapshot`)
returns exactly the JSON that was stored, and `contentHash` was computed, at
the time, over whatever object `buildContractSnapshot` produced then. A
snapshot published before this stage was built from a two-argument call and
has no `scopeItems` key at all; nothing in this stage rewrites that row or
recomputes its hash. Adding the field changes what gets *produced* for
revisions published *from now on* — it is a new input feeding new output,
never a reinterpretation of old output. This is asserted, not merely argued:
`revision.test.ts` gained five tests, including one that hashes a snapshot
built with no third argument against one built with an explicit `[]` and
requires them equal — the exact shape every pre-L1 call site produces.

The view surfaces two places:
- `Contract.agreedScopeItems` (GraphQL), reading the frozen snapshot, exactly
  like the existing `Contract.articles` field reads it for the free-text
  articles.
- The printed contract (`portal/ContractPrint.tsx`) gained an "Appendix 1 —
  agreed scope" section rendering that list, next to (not replacing) the
  numbered articles section. The **live** scope checklist elsewhere in the
  portal (`ContractDetail.tsx`) is untouched — it is still the customer's
  working to-do list, per V2.md §5's explicit instruction not to merge the
  two.
- `Contract.draft` and `publishContractRevision`'s `NO_CHANGES` guard both now
  read the current agreed set, so marking one more item `AGREED` with
  nothing else changed correctly registers as publishable — before this,
  `draftState` had no way to see that move at all.

### 1.6 · Desk surface: registry editing

`ScopeTab.tsx` (contract workspace) now supports, per item: edit labels
(existing), delete (existing), **set status** (a `<select>` over all seven
values), **set flags** (three checkboxes, one call), **decide / reopen**
(a note field plus the CHECK-backed pair of fields), and **reorder** (up/down
buttons swapping `position` with a neighbour — `position` carries no
uniqueness constraint, unlike `Article.number`, so this needs no temporary
value the way article reordering would, which is why T6 in V2.md never
applies here). A compact "propose a trade" form and a read-only list of a
project's trades (with a "confirm as Root" button, and a plain badge saying
the customer half is not built) round out the tab.

New mutations, all `contracts.manage`: `setScopeItemStatus`,
`setScopeItemFlags`, `decideScopeItem`, `undecideScopeItem`,
`setScopeItemOrigin` (built at the API layer; **no desk UI control for
origin was built** — see §3), `reorderScopeItem`, `proposeScopeTrade`,
`confirmScopeTradeRoot`, `executeScopeTrade`.

### 1.7 · `resolvers/admin.ts` split

The former 951-line file is now `resolvers/admin/{customers,contracts,design,
amendments,registry}.ts` plus `shared.ts` (the small cross-cutting helpers:
`requireDraft`, `asConcurrentPublish`, `resolveDesignImage`) and `index.ts`
(a barrel re-exporting the same flat `adminMutations` object
`resolvers/index.ts` already imported). This was mechanical — no resolver's
guard, transaction shape, or return value changed while moving. The only
files a reviewer needs to diff against the pre-split behaviour are the ones
listed in §1.1–§1.6 above; everything else in the new files is a verbatim
move.

## 2 · Decisions taken inside the stage

The plan and the spec left several shapes open. Recorded here so they are
visible rather than discovered by reading five files:

1. **`Contract.scopeItems` was kept, as a proxy.** Rather than remove the
   field now that the registry lives on `Project`, `fields.ts`'s
   `Contract.scopeItems` resolver returns `project.scopeItems`. This kept
   every existing GraphQL query and the whole pre-L1 `ScopeTab.tsx` shape
   compiling unchanged, at the cost of a contract "having" scope items in the
   API surface when it is really the project that does. `Contract.project`
   is the honest edge for new code to use.
2. **Registry mutations still return `Contract!`, not a project- or
   trade-shaped payload**, matching this codebase's established rule (T9 in
   V2.md: every mutation returns the whole contract, so Apollo's normalized
   cache stays consistent without any tab calling `refetch`). This is why
   `proposeScopeTrade`, `confirmScopeTradeRoot` and `executeScopeTrade` all
   return `Contract!` and reach the trade through `project.scopeTrades`,
   rather than returning `ScopeTrade!` directly (which is what a first draft
   of the schema did — changed after checking `ContractWorkspace.tsx`'s own
   comment about why no tab calls `refetch`).
3. **`firstContractId(projectId)`** — every registry mutation that needs to
   return a `Contract!` picks the project's earliest-created contract. This
   is exactly right while a project has at most one contract (true of
   everything this stage creates) and is a named, commented shortcut for the
   day a project has two. It throws `NO_CONTRACT` rather than guessing if a
   project somehow has none.
4. **`addScopeItem` and the `SCOPE` template create items `AGREED`, not
   `PROPOSED`.** Root typing an item into the contract through the desk *is*
   the agreement act; a genuinely proposed-but-undecided item is a
   scoping-stage shape (spec §4 stage 2) with no screen yet. The completeness
   checklist is the one exception, seeded `DECLINED` on purpose (§1.1).
5. **The checklist's keys are namespaced `checklist.*`** specifically so
   `applyContractTemplate`'s existing "refuse if scope items already exist"
   guard could keep working — it now counts only non-`checklist.*` rows.
   Without the namespace, every contract would already "have" ten scope
   items the moment its project exists, and the template button would refuse
   unconditionally.
6. **`declinedReason` has no CHECK**, unlike L3b's `Build.declined` (which the
   plan does hold to one). The completeness checklist is seeded `DECLINED`
   with no reason at all, on purpose — the whole point is that its absence
   is visible before anyone has explained it. Requiring a reason at the
   database level would mean inventing a placeholder string at seed time,
   which is exactly the "defaulted value is omission with a friendly face"
   pattern R1's rule warns against. This can be tightened later if it proves
   too loose in practice.
7. **The ownership check in `setScopeItem`** (`resolvers/customer.ts`) goes
   through `loadForActor(contract.id, user)` — an ownership edge on
   `Contract.customerId` — rather than checking `item.project.customerId`
   directly. In every shape this stage can produce, the two are identical
   (`createContract` sets both from the same input), and `loadForActor`
   already carries the staff bypass and the "published only" rule a from-
   scratch check would have to reinvent. It is documented in the code as a
   read against an ownership edge, not a role, so house rule 2 is not broken
   in kind — the letter (literally `project.customerId`) is the one place
   this stage did not chase, and is worth revisiting once a project can
   genuinely span more than one contract.
8. **No new `ChangeAction` values.** Status changes, flag changes, decide/
   undecide and origin edits on a `ScopeItem` do not write to `ChangeLog`.
   Adding one touches five files by house rule 10, and nothing in the plan
   asked for scope-registry activity in the desk's activity feed this stage.
   Flagged here so it is a decision, not a thing nobody noticed was missing.
9. **`ProjectStatus` is two values.** The plan names "state" as one of four
   things a project owns, without specifying its shape. `ACTIVE`/`ARCHIVED`
   is the minimum that is not obviously wrong; L2's phases are expected to
   carry whatever finer lifecycle state actually matters.

## 3 · What was deliberately not built

- **The customer's half of a scope trade** — no mutation, no portal UI, no
  notification. See §1.3. `executeScopeTrade` exists and is correctly gated,
  but cannot succeed today because of this.
- **A screen to attach a second contract to an existing project.** The model
  supports it (`Project.contracts` is a list); nothing creates that second
  edge. Needed for ADR 0001's two-agreement wedge shape, owed at or before L8.
- **A desk control for `originNote`/`originRound`.** The mutation
  (`setScopeItemOrigin`) exists; `ScopeTab.tsx` does not expose it. Cut for
  time inside an already large tab, not because it is unimportant — "where
  did bilingual come from" is the whole reason `origin` exists.
- **Scope-registry entries in the desk activity feed / `ChangeLog`.** See
  decision 8 above.
- **Any lifecycle-stage screen (Contact, Scoping) that would create a
  `Project` before a `Contract` exists.** `createContract` is still the only
  door into a new project.
- **A `Signature`-adjacent record for scope trade confirmation.** Given the
  customer half is not built at all yet, this did not need deciding this
  stage; when it is built, V2.md's caution about not overloading `Signature`
  for a non-legal-instrument act is exactly the argument to reread first.

## 4 · The migration

Hand-authored: `apps/api/prisma/migrations/20260920120000_l1_project_registry/migration.sql`.

`npx prisma migrate diff --from-schema-datamodel <pre-L1 schema.prisma>
--to-schema-datamodel <post-L1 schema.prisma> --script` was run first (no
database needed) to get the full, correct set of DDL operations Prisma
believes are required. That raw output is **not** what shipped: it adds
`ScopeItem.projectId` as `NOT NULL` with no default in the same `ALTER TABLE`
that drops `contractId`, which fails outright the moment the table has a
single row, because there is no value that could stand in for "which
project." The shipped migration reorders and splits that into:

1. Create `Project`, empty.
2. `INSERT` one `Project` per existing `Contract` (id `'proj_' || contract id`
   — a deterministic, one-shot string, not a cuid, because nothing but this
   migration ever produces a row shaped like this).
3. Add `Contract.projectId` nullable, backfill it, then add the foreign key.
4. Add `ScopeItem.projectId` nullable, backfill it from the row's own
   (still-present) `contractId`, **then** set it `NOT NULL`, **then** drop
   `contractId` and its old constraint/index.
5. Add the new `ScopeItem` columns (`status` defaulting to `PROPOSED` — the
   schema's own ongoing default for a genuinely new row), then `UPDATE
   "ScopeItem" SET "status" = 'AGREED'` unconditionally — banked trap #1,
   enforced as a real statement, not only as a comment.
6. Add the `decided`-pair CHECK, create `ScopeTrade` and its constraints, and
   a CHECK that a trade cannot name the same item on both sides.

Every data-preserving step above is a real `INSERT`/`UPDATE` in the file, not
asserted only in this document — read the migration itself.

**§7.1 of the plan applies exactly as written:** there is no production data
on the VPS, so today this backfill only ever touches the seed fixture. It is
written as though a real engagement depended on it, because that is the day
this file could no longer be rewritten.

## 5 · Traps, checked against what was actually built

1. **`checkedAt` not backfilled into `accepted`.** Confirmed: the migration's
   only write to `status` is the unconditional `UPDATE … SET "status" =
   'AGREED'`; nothing in the migration or the resolvers touches `checkedAt`.
2. **`@@unique` moved to `[projectId, key]`.** Confirmed in both
   `schema.prisma` and the migration's `CREATE UNIQUE INDEX
   "ScopeItem_projectId_key_key"`.
3. **The appendix-as-view change and hash-sealed snapshots.** See §1.5.
   Argued in code comments, held by five new unit tests in
   `revision.test.ts`, **not** verified against a live database — no
   integration test exists that publishes a real revision before and after
   this change and diffs the bytes. The reasoning is sound because
   `ContractRevision.snapshot` is write-once by construction (grep confirms
   `buildContractSnapshot` has four callers total: the publish path and the
   seed pass the registry's agreed set explicitly; `prisma/backfill-revisions.ts`
   and the integration test fixture (`src/test/db.ts`) still call it with two
   arguments and default to `[]` — correctly, for the backfill script, since
   it reconstructs a *historical* v1 that predates the registry concept
   entirely, and `[]` is exactly the true statement "no scope items were part
   of this document." Nothing reads a snapshot by recomputing it from live
   rows), but "sound reasoning, unexecuted" is exactly the distinction §7 of
   this file insists on, so it is repeated here rather than only claimed once.
4. **`lib/gate.ts` untouched.** Confirmed: `git diff` on this file is empty.
   `grep -rn "chosenAt\|approvedAt" apps/api/src/graphql/resolvers/admin/
   apps/api/src/lib/scope.ts` finds no write from any L1 code — the only
   writers of `PageDesign.approvedAt` and `DesignConcept.chosenAt` remain
   `resolvers/customer.ts` and `resolvers/admin/design.ts`'s
   `publishDesignRevision` (both pre-existing, both untouched in behaviour).
   `gate.test.ts` was not modified and is green (see §7).
5. **House rule 2 (ownership vs. capability).** Every new mutation gates on
   `requireCapability(ctx, 'contracts.manage')` — a capability check — and the
   one place an ownership edge is the actual question
   (`resolvers/customer.ts`'s `setScopeItem`) uses one, not a role test. See
   decision 7 in §2 for where it is indirect rather than literal.
6. **House rule 6 (API code, web sentence).** No new GraphQL error in this
   stage carries user-facing Persian or English prose beyond what every
   existing error in this codebase already does (an English `message` plus an
   `extensions.code`) — this is the app's pre-existing, uneven convention on
   the desk side (`ScopeTab.tsx` shows `err.message` directly, exactly as it
   did before this stage), not a new violation introduced here.
7. **House rule 14 (digits).** `ScopeItem.key` stays a Latin machine key,
   unchanged. No new UI in this stage prints a bare count or position as a
   number — reordering is two arrow buttons, not a rendered index.

8. **Every contract published before L1 reads as `dirty` the moment this
   migration runs** — and that is correct, not a defect, but it is a surprise
   worth stating because nobody will expect it. `draftState` now folds the
   agreed set into the hash it computes for the working draft, while the
   stored `contentHash` of a pre-L1 revision was computed over an object with
   no `scopeItems` key at all. The two cannot match, so the desk will show
   "unpublished changes" on contracts nobody has edited. The registry genuinely
   *is* content that the live document has and the sealed one does not, so the
   honest reading is that these contracts really do have something unpublished;
   the remedy is to publish a new revision, which seals the appendix for the
   first time. On this machine the only rows affected are the seed fixture's
   (§7.1 of the build plan — production carries no data), which is exactly the
   window in which this costs nothing.

```
npx prisma format                 # schema.prisma reformatted, no manual drift
npx prisma validate               # schema is internally consistent
npx prisma generate                # client regenerated against the new schema
npx prisma migrate diff --from-schema-datamodel <pre-L1 schema> \
  --to-schema-datamodel <post-L1 schema> --script
                                   # used to derive, then hand-reconcile against,
                                   # the migration in §4 — no database touched
npm run typecheck                 # apps/web and apps/api, both clean
npm run build                     # apps/web (vite) and apps/api (tsc), both clean
npm test                          # apps/api: 205 passed, 0 failed
                                   # apps/web: 31 passed, 0 failed (includes the
                                   # locale-parity suite, which the new i18n
                                   # keys had to pass — two Persian strings were
                                   # rewritten to drop Latin doc-stage codenames
                                   # that do not belong in product copy anyway)
```

**Not run, and why — none of these are claimed as tested:**

- `npx prisma migrate dev`, `npx prisma db push` — would need the database
  this machine does not have a role for.
- `npm run test:integration` — same reason; this is also the suite that would
  actually exercise every new resolver (`registry.ts`'s reorder swap, the
  trade lifecycle, `createContract`'s project creation, `applyContractTemplate`'s
  checklist-exclusion guard) against real Postgres constraints, including the
  two new hand-written CHECKs. **None of that ran.** The CHECK constraints'
  SQL was reviewed by eye against the migration's own column definitions and
  against the three existing hand-written CHECKs already in the codebase for
  syntax parity, not against a live Postgres.
- `npm run e2e` — same reason, and it never touches the new `builds` desk
  section or the scope tab's new controls either way.
- `prisma migrate diff --from-migrations ./prisma/migrations --to-schema-
  datamodel ./prisma/schema.prisma` — the form of drift-checking that would
  most directly answer "does applying every migration in order produce
  exactly `schema.prisma`" needs a shadow database to replay migration
  history against, which this machine cannot provide either. Not attempted.
- The plan's own P0 (§7/§8: try creating a `root`/`gholi` Postgres role) was
  not attempted in this session — it was not asked for, and the sandboxed
  `sudo` this environment offers has no password to give it.

**The honest summary:** every command that needs no database ran and is
green. The migration's SQL, the two new CHECK constraints, and every
resolver's behaviour under real concurrent writes are reviewed by reading,
not by execution. Say so plainly to whoever reviews this — "read carefully"
and "tested" are different claims, and this file only makes the first one.
