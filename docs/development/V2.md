# V2 · Admin contract workspace

**Branch:** `stage-v2-workspace`
**Needs:** F1 ✔, F3 ✔, V1b, F2. **Blocks:** V3, V4.
**Shape:** the largest stage. New mutations, one migration, a new screen with
four tabs, and the first file input in the app.
**Spec:** versioning §3 (Contract workspace) and §2.2/§5.3 (amendments);
build plan §4 V2.

**Acceptance:** Root can take a contract from nothing to signed without touching
the database or the GraphQL sandbox — create it, fill in articles, upload
concept and page images, publish both lineages, hand it over, and afterwards
issue an amendment that the customer can approve and sign. **This stage retires
the last three "not built" items in the repo README.**

> This is a big stage and it is worth cutting rather than rushing. If time runs
> short, cut in this order: the template button (§3.9), then reordering
> (do not build it at all — see **T6**), then the Activity tab's lineage panel
> (V1b already returns it; a plain change log is enough). Do **not** cut the
> amendment lifecycle: without it V2 ships a feature nobody can complete, which
> is the mistake V1 avoided by putting the publish mutations in V1 rather than
> here.

---

## 1 · The shape

One contract at `/:lang/desk/contracts/:id`, with four child routes so a tab is
a link someone can send:

```
/desk/contracts/:id            → redirect to contract
/desk/contracts/:id/contract   title, fee, articles, publish, amendments
/desk/contracts/:id/design     concepts, pages, image upload, publish, discard
/desk/contracts/:id/scope      the checklist items
/desk/contracts/:id/activity   change log + both revision lineages
```

The two lineages behave differently and the screen must not pretend otherwise:

| | Contract tab | Design tab |
|---|---|---|
| Where the draft lives | the mutable `Article` rows + title/fee on `Contract` | a `DesignRevision` with `publishedAt: null` |
| How it comes into being | it is always there | created on the first edit |
| How to discard it | edit it back (the hash decides) | `discardDesignDraft` |
| What publish does | freezes a JSON snapshot + sha256 | flips `publishedAt`, carries approvals forward |
| After signature | terminal — amendments only | unaffected; keeps revising |

**The Scope tab is a third thing and the odd one out — see §5.**

## 2 · Server work: what is missing

Everything in the "the mutations largely exist" line of the spec is true for
*adding* and false for *editing and removing*. The full list of what V2 has to
add:

### 2.1 · Contract draft

| Mutation | Notes |
|---|---|
| `updateContractDraft(contractId, titleFa, titleEn, amount: String)` | **`ref` is not editable** — see **T1** |
| `deleteArticle(contractId, number)` | legal even when the article is in a published snapshot — see **T5** |

`setArticle` already exists and upserts by `(contractId, number)`.

### 2.2 · Design draft

| Mutation | Notes |
|---|---|
| `updateConcept(conceptId, labelFa, labelEn)` | `requireDraft` |
| `deleteConcept(conceptId)` | `requireDraft`; pages cascade |
| `updatePageDesign(pageId, labelFa, labelEn)` | `requireDraft` |
| `deletePageDesign(pageId)` | `requireDraft` |
| `discardDesignDraft(contractId)` | deletes the unpublished revision and its concepts/pages |

`addConcept`, `addPageDesign`, `setConceptImage`, `setPageImage` exist.
`updateConcept`/`updatePageDesign` deliberately do **not** let `key` change:
`key` is what `design.ts` matches on to decide carry-forward, so renaming a key
silently resets an approval and looks like a bug in the gate.

### 2.3 · Scope

| Mutation | Notes |
|---|---|
| `updateScopeItem(scopeItemId, labelFa, labelEn)` | live to the customer immediately — §5 |
| `deleteScopeItem(scopeItemId)` | same |

`setScopeItem` (the tick) already exists and stays the **customer's**. Do not
put a control for it in the desk — see §5.

### 2.4 · Amendments — the whole lifecycle

Nothing writes an `Amendment` today. The model and the GraphQL type exist and
are read-only.

| Mutation | Guard |
|---|---|
| `issueAmendment(contractId, titleFa, titleEn, bodyFa, bodyEn, relatesToArticle: Int)` | `contracts.manage`; the current contract revision must be **signed** |
| `updateAmendment(id, …)` | `contracts.manage`; refuse when `publishedAt != null` |
| `deleteAmendment(id)` | `contracts.manage`; refuse when published |
| `publishAmendment(id)` | `contracts.manage`; logs `CONTRACT_AMENDED`, nudges `WAITING_ON_CUSTOMER` |
| `approveAmendment(id)` | customer, via `loadForActor`; must be published, not already approved |
| `signAmendment(id, typedName)` | customer; must be approved, not already signed |

`approveAmendment` and `signAmendment` are customer mutations and belong in
`resolvers/customer.ts`. Their UI is V3 — but build the mutations here, so V2's
own acceptance test can drive an amendment to signature. This mirrors V1's
choice to land the publish mutations before the workspace that calls them:
without them the model is inert and there is nothing to test.

### 2.5 · Migration

One migration, three things:

```sql
-- Spec §5.3: an optional, non-authoritative display hint. The print still
-- shows the sealed article untouched and renders the amendment beside it,
-- marked. It is deliberately not a supersede: recomputing the effective
-- article set would make the readable contract a *computed* document, which
-- is the second candidate for "the document" that lib/revision.ts exists to
-- prevent, and would mean a screen showing something other than what the
-- signature attests to.
ALTER TABLE "Amendment" ADD COLUMN "relatesToArticle" INTEGER;

-- Defect D5. The code assumes at most one unpublished design revision per
-- contract ("There is at most one", resolvers/contracts.ts:98) and nothing
-- held it up. A second one becomes an invisible orphan that keeps StoredFile
-- rows alive through onDelete: Restrict.
CREATE UNIQUE INDEX "DesignRevision_one_draft_per_contract"
  ON "DesignRevision" ("contractId") WHERE "publishedAt" IS NULL;
```

Prisma cannot express a partial unique index, so it goes in by hand — the same
route the three existing CHECK constraints took. Add a comment in
`schema.prisma` on `DesignRevision` pointing at it, or the next person to run
`migrate dev` will not know it exists.

The third thing depends on §2.6 below.

### 2.6 · Two defect fixes that belong here

- **D2** — `publishContractRevision` (`admin.ts:323-346`) creates the revision
  outside its transaction. Rewrite both publish mutations as one interactive
  transaction covering create/supersede/repoint/log. See **T9**.
- **D6** — `publishDesignRevision` has no `NO_CHANGES` guard. Add one, using
  `diffDesign` from `lib/design.ts` (never a second comparison). This is what
  makes `discardDesignDraft` necessary rather than optional: without a discard,
  an admin who opens the design tab, triggers a draft and changes their mind is
  stuck with a draft they cannot publish and cannot remove.

## 3 · Server work: how

### 3.1 · The carry-forward preview — the non-obvious requirement

`draftDesignRevision` clones concepts and pages from the published revision but
**not** `approvedAt` or `chosenAt` (`resolvers/contracts.ts:114-144`), because
an approval belongs to a revision and the draft is a different one. That is
right, and it means **the draft always shows zero approvals — which is not what
the customer will see after publish.** Carry-forward restores them at publish
time.

An admin looking at a draft where four pages are unapproved, publishing it, and
then seeing three of them approved, will reasonably conclude the app is
guessing. So show the answer before the action. `carryForward` and `diffDesign`
are pure functions on data the resolver already has — this is nearly free.

Extend V1b's `DesignDraft`:

```graphql
enum PageChangeKind { ADDED CHANGED REMOVED UNCHANGED }

type PageChange {
  conceptKey: String!
  pageKey: String!
  kind: PageChangeKind!
}

"""
What publishing this draft would do, computed with the same carryForward the
publish path runs. Two implementations of this would drift, and the visible one
would be the one that looks right while the gate did something else.
"""
type CarryForwardPreview {
  "The concept whose choice survives, or null if the customer must choose again."
  chosenConceptKey: String
  carriedPageCount: Int!
  resetPageCount: Int!
  changes: [PageChange!]!
}

type DesignDraft {
  id: ID!
  version: Int!
  concepts: [DesignConcept!]!
  carryForward: CarryForwardPreview!
}
```

`design.ts`'s `PageChange.kind` is `'added' | 'changed' | 'removed' | 'unchanged'`
in lower case. **Map to the enum at the field resolver; do not change the
literals** — they are covered by unit tests and used on the publish path.

### 3.2 · The amendment hash invariant — the dangerous one

`Amendment.contentHash` is `String` **not null**. So an amendment is sealed the
moment it is created, unlike a contract revision, which is nullable-until-sealed.

If an amendment is editable while unpublished — and it must be, or a typo means
burning an ordinal — then **the hash has to be recomputed on every write.** An
amendment whose text has moved past its hash is a legal instrument that attests
to bytes nobody wrote.

State it as an invariant and hold it with a test:

> For every `Amendment` row, at all times:
> `contentHash === contentHash(buildAmendmentSnapshot(row))`.

`buildAmendmentSnapshot` already exists (`lib/revision.ts:116`). Every write path
— `issueAmendment` and `updateAmendment` — goes through it. Do not compute the
hash in the resolver from the arguments; compute it from the row you are about
to write, so the two cannot disagree.

### 3.3 · The amendment mini-gate

Spec §2.4: amendments "run their own mini-gate — approve → sign the amendment —
without reopening the base. The base contract stays `signed`."

Put the assertions in `lib/gate.ts` beside the existing two, not in the
resolvers. That file is the one place the sequence lives (house rule 3) and it
takes structural types rather than Prisma types, so this fits:

```ts
export function assertCanApproveAmendment(a: { publishedAt: Date|null; approvedAt: Date|null }): void
export function assertCanSignAmendment(a: { approvedAt: Date|null; signature?: unknown|null }): void
```

**Do not add fields to `Gate`.** `Gate` is the three-step rule the portal's
stepper renders; growing it a fourth meaning makes every reader of `computeGate`
wonder which of two things it now answers. V3 surfaces the pending amendment as
its own field on `ContractRevision`.

### 3.4 · One new `ChangeAction`, and it costs five files

There is `CONTRACT_AMENDED` and `AMENDMENT_SIGNED`. There is **no
`AMENDMENT_APPROVED`**. `RE_APPROVED` means "re-approved a contract revision"
and using it here would put a false sentence in the customer's own history.

Add it, and touch all five (house rule 10):

1. `apps/api/prisma/schema.prisma` — the enum, and a migration
   (`ALTER TYPE "ChangeAction" ADD VALUE 'AMENDMENT_APPROVED'`; note that
   Postgres permits `ADD VALUE` in a transaction only if the value is not
   *used* before commit, which is why the F3 migration could do two at once).
2. `apps/api/src/graphql/typeDefs.ts`
3. `apps/web/src/portal/ContractDetail.tsx` — the `logText` key map
4. `apps/web/src/i18n/locales/en.json` under `log.`
5. `apps/web/src/i18n/locales/fa.json` under `log.`

…and the sixth place the test does not know about: the `ChangeAction` union in
`apps/web/src/lib/queries.ts` (defect **D3**, fixed in V1b — keep it fixed).

`lib/changeAction.test.ts` will fail until all five agree. That is the feature.

### 3.5 · The Signature CHECK constraint

`Signature` binds to a contract revision **or** an amendment, exactly one, held
by a CHECK constraint the migration added by hand. `signAmendment` sets
`amendmentId` and leaves `contractRevisionId` null. Getting this wrong produces a
constraint violation, not a wrong signature — which is the constraint working.
`signedHash` is the amendment's own `contentHash`.

### 3.6 · Contract handover and the empty-document problem

`publishContract` sets `publishedAt` and makes the contract visible. Nothing
requires a published contract revision first. A contract handed over with no
revision shows the customer a title and **no articles at all** —
`Contract.articles` reads the snapshot and there is none
(`fields.ts:33`). The portal handles it honestly (empty rather than mixing draft
into published) but it is a bad handover.

**Recommendation: warn in the workspace, do not guard on the server.** Root may
legitimately hand over a contract whose text is still being written, and this
product's stated posture is permissive with a manual override. A confirm dialog
naming what the customer will see is enough.

> ⚠ Judgement call. If the founder would rather the server refuse, that is a
> three-line guard in `publishContract` and this note is where the decision
> should be recorded.

### 3.7 · Both publish paths become one interactive transaction

Defect **D2**. Current shape:

```ts
const revision = await prisma.contractRevision.create({ … });   // outside
await prisma.$transaction([ supersede, repoint ]);              // inside
await log(…); await nudgeStatus(…);                             // outside
```

Becomes:

```ts
await prisma.$transaction(async (tx) => {
  const latest = await tx.contractRevision.findFirst({ … });
  const revision = await tx.contractRevision.create({ … });
  if (current) await tx.contractRevision.update({ … supersededAt });
  await tx.contract.update({ … currentContractRevisionId: revision.id });
  await tx.changeLog.create({ … });
});
```

`log()` and `nudgeStatus()` take `prisma` implicitly today; either give them an
optional transaction client or inline their bodies inside the transaction. The
first is better — V3 and V4 will want the same.

`publishDesignRevision` gets the same treatment, including the draft lookup and
the `carryForward` computation, which currently run outside.

### 3.8 · The version race

Both publish paths read `max(version)` and write `version + 1`. Two concurrent
publishes hit `@@unique([contractId, version])`, which is exactly right — the
constraint is the protection. But the caller sees `DUPLICATE_KEY`
("Something with that key already exists"), which is unreadable in context.

Catch Prisma's `P2002` on that constraint and rethrow as
`CONCURRENT_PUBLISH` with "Someone else published while you were working —
reload and try again." Cheap, and with one admin it will never fire; with two
it fires on the day both are looking at the same contract.

### 3.9 · The article and scope templates — cuttable

`prisma/seed.ts:29-67` holds the fifteen article titles, six scope items and
four page keys, hardcoded. A contract created through the workspace has **zero**
articles, so publishing it produces an empty snapshot and the admin faces
fifteen forms.

Move `ARTICLES`, `SCOPE` and `PAGES` into `apps/api/src/lib/templates.ts`, have
`seed.ts` import them, and add:

```graphql
"Fills an empty contract with the standard article titles, scope items and page keys."
applyContractTemplate(contractId: ID!): Contract!
```

Refuse when the contract already has articles or scope items, rather than
merging — a merge has to decide what to do about a number that already exists,
and every answer to that is a small surprise.

This is the one part of V2 that is convenience rather than capability. Cut it
first if the stage is running long; it is a clean follow-up.

## 4 · The upload flow

The first file input in the product. The mechanism is built and tested
(`routes/files.ts`); what is missing is a form.

```
POST /upload?class=DESIGN_IMAGE&contractId=<id>
  multipart/form-data, field name "file"
  → 201 { id, url, mime, bytes, originalName }

then: setConceptImage(conceptId, fileId) | setPageImage(pageId, fileId)
      (fileId: null clears the image)
```

**T2 · Upload errors are not GraphQL errors.** They come back as
`{ error, message }` JSON with an HTTP status — `401 UNAUTHENTICATED`,
`403 FORBIDDEN`, `404 NOT_FOUND`, `413 FILE_TOO_LARGE`, `415 UNSUPPORTED_TYPE`,
`415 NOT_MULTIPART`, `400 NO_FILE | MALFORMED_UPLOAD | EMPTY_FILE`. Apollo's
error handling never sees them. Write one small `uploadFile()` helper in
`apps/web/src/lib/upload.ts` that maps those codes to i18n keys, and use it
everywhere. The `message` field is English prose from the server and should not
be shown to a Persian user.

**T3 · The two-step flow can orphan a file.** If the upload succeeds and
`setConceptImage` fails, a `StoredFile` row and its bytes exist with nothing
pointing at them — unreachable, unowned, counted by nothing.

Do **not** delete the file on attach failure: a retry is the likely next action
and deleting races with it. Instead keep the returned `id` in component state
and offer "retry attach" with the same id. Add a `TODO(orphans)` comment naming
a future sweep (`StoredFile` where nothing references it and `createdAt` is
older than a day). The build plan's §6.6 already notes that `STORAGE_DIR` is
outside the Postgres backup; orphans belong in the same paragraph of the runbook.

**T4 · `accept` on the input is a hint, never validation.** The server decides
what a file is from its own leading bytes (`lib/files.ts:129`), never from the
`Content-Type` or the filename. Mirroring the allowlist client-side as a *hint*
is friendly; mirroring it as *validation* creates a second copy of a policy that
lives in `POLICY` (house rule 3). Show the 2 MB limit and the accepted types
from a single constant, and let the server refuse.

**Re-uploading an image is what makes carry-forward work.** `setConceptImage`
and `setPageImage` write `imageUrl` and `imageFileId` together, so a new upload
changes `imageUrl`, so `design.ts` sees the page as changed, so its approval
resets at publish. That chain is deliberate. The carry-forward preview (§3.1) is
where the admin sees the consequence before committing to it.

## 5 · The Scope tab is the odd one out, and the screen must say so

`ScopeItem` hangs off `Contract` directly. It is **not versioned, not
snapshotted, and not hashed.** Editing a scope item's label is visible to the
customer the instant it is saved — no draft, no publish.

Three consequences the workspace has to handle:

1. **The tab needs a line of copy saying these are live.** An admin who has
   spent ten minutes learning "edit the draft, then publish" will carry that
   model into this tab and change what a customer is looking at mid-conversation.

2. **The desk does not toggle the checkboxes.** `checkedAt` is the customer's
   tick. `setScopeItem` goes through `loadForActor`, which an admin passes, so
   an admin *can* toggle it — there is just no reason to put that control on
   this screen. Show the state read-only.

3. **The scope checklist is not the contractual Appendix 1.** Article 15 in the
   seed is «پیوست ۱ — فهرست ویژگی‌ها» / "Appendix 1 — Feature list", and *that*
   is the one inside the snapshot, hashed and signed. The `ScopeItem` rows are a
   working checklist rendered from the same idea. Someone will eventually notice
   the duplication and try to unify them. Do not — one is a legal document and
   the other is a to-do list, and merging them puts a customer's tick inside the
   thing a signature attests to.

## 6 · Remaining traps

### T1 · `ref` is not editable, ever

`Contract.ref` is `@unique`, shown to the customer, and **frozen into every
snapshot** (`revision.ts:100`). Editing it after a revision is published makes
the printed page — which carries `ref`, version and sha256 for exactly this
purpose — disagree with the live contract, while the hash still verifies. Set it
at creation; show it read-only afterwards.

### T5 · Deleting an article that is in a published snapshot is legal

The snapshot is frozen; deleting the draft row does not touch it. The customer
keeps reading the published text. The *next* publish produces a contract without
that article. This is correct and will look alarming — put a confirm on it and
say what will happen.

### T6 · Do not build article reordering

`@@unique([contractId, number])` means swapping two articles' numbers violates
the constraint halfway through unless it is done in one transaction with
temporary negative numbers. Articles are 1–15 by convention and the numbering is
the contract's own. If reordering is genuinely wanted later, it is its own small
piece of work with its own test — not something to slip into a form.

### T7 · The design draft is created by the first *edit*, not the first *look*

V1b's `Contract.designDraft` is a pure read that returns `null` when there is no
draft. `draftDesignRevision` — the creating one — is only ever called from a
mutation. **Do not call it from a query, a loader, a `useEffect`, or "to make
the tab simpler".** See V1b **T1** for what happens: every contract Root has
ever opened grows a draft, and D6's guard is then the only thing between that
and a stream of no-op v2 publishes telling customers the design changed.

The Design tab therefore has two states: "no draft — showing the published
revision, read-only" and "editing draft vN". The first edit is what crosses
between them, and the button that does it should say so.

### T8 · Language switching remounts the whole subtree

`LocaleLayout` returns `<Outlet key={locale} />` (`LocaleLayout.tsx:23`) —
deliberately, so no component can keep rendering a stale language. It means
**any unsaved editor state is lost on a language switch.**

The mitigation is the editor's shape, not a workaround: `setArticle` takes a
whole article, so make each article a card with its own Save button and no
long-lived unsaved state elsewhere. Do not build a single "Save all changes"
form over the whole tab.

### T9 · Every mutation returns the whole contract

Each resolver ends in `reload(id)`, which refetches `contractInclude` — concepts,
pages, all articles, all comments, the whole change log. Saving one article
refetches all of it. That is what keeps the gate, the status and the history
consistent without the client recomputing anything, and it is the right trade at
this scale. Do not "optimize" it into partial returns; do notice it if the
workspace starts feeling slow on a contract with a long history (defect **D10**).

### T10 · `updatedAt` moves on every write

Anything sorting or displaying "last change" is sorting on "any write at all",
including an autosave. V4 needs a real answer to this (defect **D7**); V2 just
needs to not build a UI that implies more than the field means.

## 7 · Tests

**Unit** (`apps/api/src/lib/`):

1. `assertCanApproveAmendment` / `assertCanSignAmendment` — each refusal path
   and its code.
2. The `PageChangeKind` mapping is total: every literal `design.ts` can produce
   has an enum value. A four-line test that will fail the day someone adds a
   fifth kind.
3. `buildAmendmentSnapshot` + `contentHash` are stable across key order — the
   same property `revision.test.ts` already asserts for contracts.

**Integration** (`apps/api/src/test/`):

4. `updateContractDraft` changes the draft and **not** `Contract.articles`.
5. `deleteArticle` on a published article: the customer still reads it; the
   draft no longer has it; the next publish produces a snapshot without it.
6. `discardDesignDraft` removes the draft and its concepts, and
   `Contract.concepts` still shows the published revision.
7. `publishDesignRevision` refuses `NO_CHANGES` on an untouched draft (**D6**).
8. Two `draftDesignRevision` calls in sequence return the same revision; the
   partial unique index refuses a hand-inserted second draft (**D5**).
9. **The amendment hash invariant:** issue, then update three times, and assert
   after each write that `contentHash` equals a freshly computed one.
10. `updateAmendment` on a published amendment is refused.
11. The full amendment path: sign the base contract → `publishContractRevision`
    is refused with `CONTRACT_SIGNED` → `issueAmendment` → `publishAmendment` →
    customer sees it in `revision.amendments` → `approveAmendment` →
    `signAmendment` → the base signature is **untouched** and
    `gate.signed` is still true. This is V2's acceptance test.
12. A customer cannot see an unpublished amendment (already held by
    `fields.ts:72` — assert it still holds after the mutations land).
13. A customer calling any of the new admin mutations gets `FORBIDDEN`; a
    customer calling `approveAmendment` on someone else's gets `NOT_FOUND`.

**e2e** (`apps/web/e2e/`): one new spec driving the workspace as an admin —
create a contract, apply the template (or add two articles), publish the
revision, upload a PNG to a concept, publish the design, publish the contract,
then sign in as the customer and see it. The PNG can be a few bytes of a real
PNG header written by the test; `lib/files.ts` sniffs magic bytes, so a
hand-built 8-byte header plus a valid tail is enough — or check in one small
fixture image under `e2e/fixtures/`.

**Browser, both languages.** The design tab in RTL with image thumbnails is the
single most likely place for a logical-property mistake to show.
